## خطة العمل — Role-Aware Task Groups للكيرنل

### السياق والتشخيص
آخر audit في brain file سجّل صراحةً: **"Role-aware nav غير منفّذ — measured: CISO=Analyst، نفس الـ 19 رابط"**. الـ role selector موجود في `KernelSidebar` ويحفظ `body[data-role]` في `localStorage` (key: `brightai-kernel-role`)، لكن **ما في أي مستهلك فعلي** — لا reorder ولا إبراز. الـ 4 مجموعات الحالية (`operations/oversight/proof/infra`) ثابتة للجميع. الفجوة في الـ AC: CISO/compliance/developer/operator ما يوصلون لأهم مهامهم خلال actionين.

### الـ Mapping المقترح (6 مجموعات على الـ 20 وحدة)
أرتّبها حسب الفهم الفني من محتوى كل صفحة في `kernel.ts`:

| المجموعة | العربية | الوحدات (slugs) |
|---|---|---|
| **Monitor** | المراقبة | `index`, `chat`, `scenarios`, `redteam`, `datasets` |
| **Investigate** | التحقيق | `audit`, `replay`, `approvals` |
| **Govern** | الحوكمة | `policies`, `compliance` |
| **Evaluate** | التقييم | `eval`, `scorers`, `stats`, `reports` |
| **Integrate** | الربط | `connectors`, `models`, `api`, `playground`, `evidence` |
| **Admin** | الإدارة | `quota` (admin-only، noindex — يظهر بس للدور operator/admin) |

> `evidence` يروح لـ Integrate لأنه عمليًا أداة تصدير/ربط بالجهات الرقابية، مو تحقيق.

### الـ Role-Aware Prioritization (Reorder + Pinned)

**1. Reorder للمجموعات** (حسب الدور):
- `ciso` → Investigate, Govern, Monitor, Evaluate, Integrate, Admin
- `compliance` → Govern, Investigate, Evaluate, Monitor, Integrate, Admin
- `developer` → Integrate, Monitor, Evaluate, Govern, Investigate, Admin
- `employee`/`dpo` (default) → Monitor, Investigate, Govern, Evaluate, Integrate, Admin

**2. Pinned Top Tasks** (3 مهام علوية فوق كل المجموعات، حسب الدور):
- `ciso` → compliance, audit, evidence
- `compliance` → compliance, evidence, reports
- `developer` → api, playground, connectors
- `employee`/`dpo` → chat, playground, stats

**النتيجة:** كل دور يلقى أهم 3 مهامه في أول section بصريًا (action 1: فتح السايدبار / action 2: click). باقي المهام متاحة كاملة في الـ 6 مجموعات = **full discoverability preserved**.

### الملفات اللي بتتعدّل (SCOPE توسّع ضروري)

المهمة حددت 3 ملفات (`KernelLayout, KernelSidebar, kernel.ts`)، لكن التنفيذ الفعلي يتطلب ملفين إضافيين. السبب: الـ reorder + pinned يحتاجون (a) بيانات الـ mapping/priorities، (b) DOM يرسمها السايدبار، (c) JS يبدّلها عند تغيير الدور، (d) CSS للأنماط.

| الملف | السبب | التعديل |
|---|---|---|
| **`src/data/kernel.ts`** | مصدر بيانات واحد | إضافة `taskGroups` (6 مجموعات بـ slugs) + `roleConfig` (reorder + pinned لكل دور) كـ exports جديدة. ما أمسح الـ GROUPS القديمة في Sidebar أولًا (alias لفترة انتقالية). |
| **`src/components/kernel/KernelSidebar.astro`** | DOM + SSR | (1) استبدال GROUPS الثابتة بـ import من `taskGroups`. (2) إضافة `<section class="kernel-sidebar__pinned">` فوق الـ nav — يرسم Pinned Top Tasks (server-side يرسم pinned للدور الافتراضي dpo، JS يبدّلها). (3) يرسم الـ 6 مجموعات بالترتيب الافتراضي. |
| **`public/js/kernel-sidebar.js`** | JS consumer جديد | إضافة logic: يقرأ `body[data-role]` → يعيد ترتيب الـ `.kernel-sidebar__group` في DOM حسب `roleConfig[role].order` → يحدّث الـ pinned section. يتكامل مع `kernel:role-change` event اللي يطلقه `KernelRoleSelector`. |
| **`src/styles/kernel.css`** | pinned section styling | إضافة `.kernel-sidebar__pinned` + `.kernel-sidebar__pinned-item` styles (consistent مع `kernel-sidebar__item` الموجود، بس بـ accent border أو icon pin صغير). |
| **`src/layouts/KernelLayout.astro`** | لا تعديل جوهري | الـ layout ما يتغير — السايدبار يرث كل شي. أتأكد بس إن الـ role event يوصل بشكل صحيح. (ممكن ما يحتاج أي تعديل فعلي.) |

> **ملاحظة على SCOPE:** `KernelLayout` في الـ task spec بس عمليًا ما يحتاج تعديل جوهري. التعديل الفعلي على 4 ملفات (`kernel.ts`, `KernelSidebar.astro`, `kernel-sidebar.js`, `kernel.css`). لو تبي ألتزم بحرفية الـ 3 ملفات وأدمج CSS في scoped `<style>` داخل `KernelSidebar.astro`، قلي — لكن `kernel.css` هو المكان الصحيح عشان الـ layer system.

### تفاصيل التنفيذ التقنية

**1. `kernel.ts` — exports جديدة (server-safe، ما تأثر على SEO/schema):**
```typescript
// Task groups — IA layer (6 groups, 20 units)
export const taskGroups = [
  { id: 'monitor', label: 'المراقبة', slugs: ['index','chat','scenarios','redteam','datasets'] },
  { id: 'investigate', label: 'التحقيق', slugs: ['audit','replay','approvals'] },
  { id: 'govern', label: 'الحوكمة', slugs: ['policies','compliance'] },
  { id: 'evaluate', label: 'التقييم', slugs: ['eval','scorers','stats','reports'] },
  { id: 'integrate', label: 'الربط', slugs: ['connectors','models','api','playground','evidence'] },
  { id: 'admin', label: 'الإدارة', slugs: ['quota'] },
] as const;

export const roleConfig: Record<string, { order: string[]; pinned: string[] }> = {
  dpo:      { order: ['monitor','investigate','govern','evaluate','integrate','admin'], pinned: ['chat','playground','stats'] },
  ciso:     { order: ['investigate','govern','monitor','evaluate','integrate','admin'], pinned: ['compliance','audit','evidence'] },
  compliance: { order: ['govern','investigate','evaluate','monitor','integrate','admin'], pinned: ['compliance','evidence','reports'] },
  developer:  { order: ['integrate','monitor','evaluate','govern','investigate','admin'], pinned: ['api','playground','connectors'] },
  employee:   { order: ['monitor','investigate','govern','evaluate','integrate','admin'], pinned: ['chat','playground','stats'] },
};
```
> `quota` slug مو في `kernelUnits` (صفحة admin منفصلة) — `buildItem()` يحتاج fallback: لو ما لقى unit، يبني item يدويًا للـ quota (label/icon مخصص) أو يتجاوزها بأمان. **قرار:** أضيف `quota` كـ meta-entry جنب الـ groups (مش في kernelUnits عشان ما يأثر على SEO/schema اللي يعتمد عليها)، أو ببساطة أخفي مجموعة Admin لغير operator. الخيار الثاني أنظف — Admin group تظهر بس إذا الدور له صلاحية (نضيف `roles: ['operator','admin']` على المجموعة، ونضيف `operator` للـ select في Sidebar لو لازم).

**2. `KernelSidebar.astro` — pinned section (SSR default + JS swap):**
```astro
{/* Pinned top tasks — يرسم للدور الافتراضي (dpo)، kernel-sidebar.js يبدّلها */}
<section class="kernel-sidebar__pinned" data-kernel-pinned hidden>
  <span class="kernel-sidebar__section-label">مهامك السريعة</span>
  {/* تُرسم بـ JS عند init حسب الدور المحفوظ — hidden افتراضيًا حتى لا يظهر خاطئ */}
</section>
```
> **لماذا `hidden` افتراضيًا؟** عشان نتجنب FOUC (flash of wrong pinned tasks) لو الدور المحفوظ ≠ الافتراضي. `kernel-sidebar.js` يبني المحتوى ويشيل `hidden` فورًا. لو JS معطّل: ما في pinned (مقبول — الـ 6 مجموعات كاملة تظهر، full discoverability محفوظ).

**3. `kernel-sidebar.js` — reorder + pinned logic (إضافة لما هو موجود):**
- على `astro:page-load`: يقرأ `body[data-role]` (المحفوظ من kernel-shell.js) → يعيد ترتيب الـ groups في DOM (`appendChild` بالترتيب الجديد) → يبني الـ pinned section.
- يستمع لـ `kernel:role-change` event (يطلقه `KernelRoleSelector` + أعدّل `kernel-shell.js` يطلقه عند تغيير الـ select) → يعيد الترتيب.
- منطق إعادة الترتيب: `roleConfig[role].order.forEach(gid => nav.appendChild(groupEl[gid]))` — DOM order native، RTL-safe.

**4. `kernel.css` — pinned styling:**
- `.kernel-sidebar__pinned`: فاصل بصري خفيف (border-block-end) فوق الـ nav.
- `.kernel-sidebar__pinned-item`: نفس `kernel-sidebar__item` + accent: `border-inline-start: 3px solid var(--interactive-primary)` أو خلفية `var(--brand-soft)` خفيفة.
- محترم لـ `prefers-reduced-motion` و `body[data-sidebar="collapsed"]` (نفس الـ collapsed behavior).

**5. ربط الـ event:** أعدّل `kernel-shell.js` (خارج الـ SCOPE المحدد بس ضروري — 3 أسطر): عند `select.addEventListener('change')`، بعد ما يضع `body[data-role]`، يطلق `window.dispatchEvent(new CustomEvent('kernel:role-change', { detail: { role: v } }))`. بدون هذا، الـ select في السايدبار ما يبدّل الترتيب (فقط الـ KernelRoleSelector في الفهرس يطلق الحدث حاليًا).

### المخاطر والـ Mitigations
- **FOUC (flash of wrong order):** الـ reorder بـ JS يعني أول paint يكون بالترتيب الافتراضي. Mitigation: الـ groups كلها مرئية دايمًا (ما نخفي شي)، الـ reorder تشاز بصري بسيط. الـ pinned `hidden` حتى يبنيه الـ JS. مقبول.
- **quota slug مش في kernelUnits:** Mitigation — مجموعة Admin إما skip لو الـ unit ناقص (buildItem يرجع null) أو نضيف meta-entry. أنزل للـ skip (أنظف).
- **JS معطّل:** الـ pinned ما يظهر، الـ 6 مجموعات بالترتيب الافتراضي تظهر كاملة — full discoverability محفوظ.
- **تأثير الـ reorder على الـ active item:** الـ `aria-current="page"` محفوظ على الـ item مهما تنقل. أتأكد بـ test.
- **View transitions:** `astro:page-load` hook موجود في `kernel-sidebar.js` — الـ reorder يعيد التطبيق بعد كل تنقل.
