## Documented decisions (will be recorded in the mind/brain entry)

1. **`lab_sample_identifiers` not created** — folded into `lab_test_samples.sample_identifier` (a separate table would duplicate `lab_test_samples` 1:1; page ref §48 stores the identifier on the sample).
2. **`lab_calendar_items` not created** — calendar events are derived at read time from calibration/maintenance/review-due/acknowledgement dates (contract §14: "no separate calendar table unless proven"; prompt's own conditional "only if genuinely needed").
3. **`lab_saved_views` as a new table** (D-3 schema resolution) — prompt lists it; avoids touching `saved_filters` used by existing task-search flow.
4. **`qc_audit_log` rebuild inside 011** per contract §8 — destructive marker + auto backup + row-preservation test; fallback (separate lab audit table) only if testing proves the rebuild riskier, and then documented, never silent.
5. **Forward FKs across migrations** (`lab_test_records.sop_version_id/wi_version_id → lab_document_versions`, `lab_products.applicable_sop_id/wi_id → lab_documents`) — legal in SQLite (FK targets resolved at DML; tables empty until 013 applies in the same startup); preserves the contract's binding migration order.
6. **Equipment seed data deferred to PROMPT 11** — full dataset (serials/statuses) does not exist in the repo; PROMPT 11 owns "seed the supplied 24 records exactly as provided"; fabricating codes/serials now is forbidden.
7. **Snapshot strategy** — equipment + document snapshots as tables (prompt entities 13–14); product/template/parameter snapshots as JSON columns on `lab_test_records` (contract §7.2). All written once, inside the approval transaction (enforced in later workflow prompts; schema stores them nullable until then).
