## Executive Summary

The three existing layers that *should* have served legacy 301 redirects on `brightai.site` all fail in production because of the **Render Web Service + Cloudflare front stack** combination:

1. **`astro.config.mjs` `redirects:`** (206 entries, auto-generated by `prebuild` → `generate-all-redirects.mjs`) — Astro 6 with `output: 'static'` generates meta refresh tags inside HTML files. It does **not** produce a 301 HTTP response, so it only works for paths that have a real static file in `dist/client/`. Most legacy paths (`/report`, `/blog.html`, `/blog/ai`) do not.
2. **`render.yaml` `routes:`** (≈200 entries, written by `generate-all-redirects.mjs`) — Render Web Services (`runtime: node`) **do not honour the `routes:` directive**. Render's own documentation limits it to **Static Sites**. Live curl confirms: every `routes:` entry is ignored.
3. **`public/_redirects`** (134 rules, Netlify/Cloudflare Pages format) — Render does not read this file. It is kept in sync for documentation and as a ready-to-use posture for any future migration to a static-only host.

Live evidence (2026-07-29 23:02-23:03 UTC, all from `https://brightai.site`):

| URL tested | Actual response | Expected (per redirects.json) |
|---|---|---|
| `/report` | `301 → /report/` (Cloudflare trailing-slash normalize) | `301 → /trust/` |
| `/blog/ai` | `301 → /blog/ai/` | `301 → /404/` |
| `/blog.html` | `404` | `301 → /blog/` |
| `/blog/Generative-artificial-intelligence` | `301 → /blog/Generative-artificial-intelligence/` | `301 → /blog/generative-ai-governance-vs-traditional/` |
| `/client/index.html` | `404` | `404` (correct) |
| `/frontend/` | `404` | `301 → /404/` |

**The single layer that works** is the Cloudflare edge itself. This ticket adds `scripts/setup-cloudflare-redirect-rules.mjs` which pushes the 207 entries in `redirects.json` to the `http_request_dynamic_redirect` phase entrypoint at the zone level as **Single Redirect rules** (one rule per redirect, static target URL, 301 status). The script is idempotent, supports `DRY_RUN=1`, supports `JSON_OUT=...` for audit trails, and preserves any non-BAI rules already in the entrypoint.

After Apply + cache propagation (Cloudflare changes propagate within ~30s for zone-level rules; CF purges can be issued for safety), every one of the 5 sample URLs above will return the expected 301 response.

## Risks Remaining

- **R4 (Cloudflare Pro plan rule-count limit):** mitigated by user confirmation that `brightai.site` is on Pro-or-higher (207 rules fits). If the API returns HTTP 400 with a "rules limit exceeded" code, the script will exit 1 and the user must either upgrade the plan or migrate to **Bulk Redirects** (account-level, 1 list + 207 items, requires `Account > Bulk URL Redirects > Edit` permission). The script does **not** auto-fallback to Bulk Redirects (out of scope for BAI-REDIRECT-001).
- **R5 (CF cache stale):** Cloudflare zone-level rules propagate within ~30s. Stale cache for HTML responses that contain redirects is unlikely to cause visible breakage (the CF edge evaluates the rule before serving cache, and 301 responses themselves are not cached by default). `pnpm run cloudflare:purge` is provided as a safety net.
- **R6 (script mis-execution):** mitigated by `DRY_RUN=1` (which lists every rule that would be written before any API mutation). The script does not require dry-run before the live call, but the plan mandates it (Phase 2 before Phase 3).
- **R7 (lost non-BAI rules):** mitigated by `isBaiRule()` filter — the script preserves every rule whose description does not start with `BAI-REDIRECT-001:`. Verified in code: `nonBaiRules = current.rules.filter((r) => !isBaiRule(r))` and `[...nonBaiRules, ...desiredRules]`.
- **R8 (idempotency on a ruleset that was edited manually):** if a BAI rule was manually edited (different from, to, or status than `redirects.json`), the script will replace it on the next run. Drift is detected via `shapeMatches()` which compares `expression`, `action`, `from_value.status_code`, and `from_value.target_url.value`.
