Section 01 · Executive Summary

01. الملخص التنفيذي للإدارة

يقدّم هذا التقرير النسخة الأشمل من تقييم مشروع BrightAI — منصة SaaS متعددة المستأجرين لحوكمة وامتثال الذكاء الاصطناعي في السوق السعودي. التقرير يغطي 8 مسارات كاملة في المستودع، استناداً إلى قراءة عميقة لأكثر من 200 ملف برمجي: قاعدة البيانات packages/db (Prisma + RLS)، الإعدادات packages/config (RBAC + Env)، لوحة التحكم apps/dashboard (Next.js)، AI Firewall libs، البناء والنشر، 97 سكريبت SEO، طبقة المحتوى (57 مقال + 41 دليل + 26 صفحة مُهاجَرة)، والأصول العامة.

الشكل 1 — درجة الصحة الإجمالية المحدّثة (منخفضة عن التقدير السابق)

النتيجة الحرجة: درجة الصحة الإجمالية للمشروع هي 42.5% فقط — منخفضة عن التقدير السابق (56.7%) الذي ركّز على سطح Astro التسويقي. عند فحص المسارات الداخلية (db، dashboard، firewall libs) اكتشفنا أن الأساس التقني للمنتج نفسه لا يعمل. التطبيق بين Prisma schema والكود المستهلك يختلف في 11 حقل على الأقل، مما يعني أن لوحة التحكم لا تستطيع الإقلاع، والـ seed لا يعمل، واختبار RLS isolation يفشل من السطر الأول.

⚠ اكتشاف حرج — السطح التسويقي يعمل، المنتج لا يعمل
الموقع التسويقي (147 صفحة Astro) production-grade فعلاً: 57 مقال، SEO ممتاز، أمان رأسياً (CSP/HSTS)، PWA كامل. لكن منصة SaaS نفسها (Dashboard + AI Firewall) هي Phase 0 scaffolding لا يشتغل. ادعاءات "Saudi AI Safety OS" على الموقع التسويقي غير مدعومة ببرنامج يعمل.

الرسالة الاستراتيجية للإدارة

المشروع يعيش انقساماً حاداً: نصفه التسويقي (Astro + Kernel + Content) جاهز للإنتاج بمستوى 85%+. نصفه المنتجي (Dashboard + AI Firewall + DB + Deploy) غير قابل للتشغيل بمستوى 15-35%. هذا يعني أن أي زيارة للـ marketing site تعمل بشكل ممتاز، لكن أي محاولة لتسجيل الدخول أو استخدام المنتج ستفشل. الفجوة بين الادعاء التسويقي والواقع التقني هي المشكلة الأساسية.

الطريق للريادة الإقليمية يتطلب 3 جبهات متوازية: (1) إصلاح الـ schema drift وجعل dashboard يقلع (أسبوعان)، (2) تأمين AI Firewall من الـ 5 ثغرات الحرجة (3 أسابيع)، (3) بناء طبقة الامتثال السعودي PDPL/SDAIA/NCA (3 أشهر). الاستثمار الإجمالي المقدّر: $186,000 على 365 يوماً، يرفع الصحة من 42.5% إلى 92%.

8 ملفات · ~2,400 LOC · أساس عزل الـ tenants · حرج جداً

يمثل packages/db أساس عزل الـ tenants في كل منصة SaaS متعددة المستأجرين. يحتوي على: Prisma schema (852 LOC) مع الـ models والعلاقات، rls.sql (538 LOC) لـ Postgres Row-Level Security policies، client.ts (142 LOC) مع db + dbServiceRole + withTenant، seed.ts (320 LOC)، واختبار RLS isolation. المعمارية ممتازة على الورق، لكن التنفيذ يعاني من 3 ثغرات Critical + 4 High تجعل الـ db package غير قابل للتشغيل.

الثغرات الحرجة في packages/db
DB-001 Critical
TokenMapping غير مُفعَّل عليه RLS — عزل PII مكسور
📁 rls.sql:96-114 vs schema.prisma:705-735 🔒 كل token_mappings ✓ Confirmed
جدول token_mappings الذي يخزّن PII مُشفَّر ليس في قائمة RLS-enable في rls.sql. الـ DO block يذكر 16 جدول لكنه يهمل token_mappings. مع dbServiceRole (BYPASSRLS) المستخدم في token-vault.ts، أي tenant يمكنه نظرياً قراءة tokens tenant آخر. عزل multi-tenant مكسور على مستوى الـ crypto + DB.
-- rls.sql:96-114 DO $$ DECLARE t text; BEGIN FOR t IN VALUES ('organizations', 'users', 'memberships', ...16 tables...) -- token_mappings IS MISSING from this list LOOP EXECUTE format('ALTER TABLE %I ENABLE ROW LEVEL SECURITY', t); END LOOP; END $$;
الإصلاح: إضافة 'token_mappings' إلى قائمة الـ VALUES في الـ DO block. سطر واحد. ثم db:setup لإعادة التشغيل.
DB-002 Critical
Hash-chain audit log مكسور — DB trigger يتعارض مع JS hash
📁 rls.sql:472-504 (compute_audit_hash) vs lib/firewall/audit/hashchain.ts:117 🔒 كل الـ audit records ✓ Confirmed
الـ DB trigger compute_audit_hash() يحسب: hash = SHA-256(prev || org_id || action || actor_id || created_at). الـ JS hashchain.ts يحسب: hash = SHA-256(prev + canonicalJson(payload)) حيث payload يشمل metadata, targetType, targetId. الخوارزميتان تنتجان hash مختلف. الـ trigger يعمل BEFORE INSERT فيُعيد كتابة الـ hash الذي حسبه الـ JS. النتيجة: verifyChain() سيرى كل صف كـ "tampered".
الإصلاح: إما حذف الـ DB trigger (الـ JS يمتلك الـ hash) أو حذف حساب الـ JS (الـ DB يمتلكه). + اختبار integration يكتب صف عبر appendAuditLog ويتحقق عبر verifyChain.
DB-003 Critical
Schema ↔ Seed ↔ Test drift — الـ seed والـ test لا يعملان
📁 schema.prisma vs seed.ts:117, 155, 158, 168 vs rls-isolation.test.ts:77, 86, 133, 146 🔒 الـ db package كله ✓ Confirmed
الـ seed.ts يستخدم: primaryLocale: 'ar', timezone: 'Asia/Riyadh', fullName, fullNameAr, emailVerified: new Date() — كلها لا وجود لها في الـ schema. الـ schema يستخدم name/nameAr، locale، و emailVerified: Boolean. كما يستخدم الـ seed enum values خاطئة (DOMAIN_ALLOW, CONNECTED, CONNECT_INTEGRATION). الـ rls-isolation.test.ts له نفس المشكلة.
الإصلاح: قرار واحد: إما تحديث الـ schema لقبول الأسماء الجديدة، أو تحديث الـ seed + test لاستخدام أسماء الـ schema. ثم pnpm typecheck كـ CI gate.
ثغرات High في packages/db
DB-004 — dbServiceRole silent fallback
client.ts:49-64 يرجع إلى DATABASE_URL لو DATABASE_URL_SERVICE غير موجود — حتى في الإنتاج. لا guard يمنع NODE_ENV=production + missing service URL. الـ dashboard سيعمل بصمت في وضع degraded.
DB-005 — Audit chain fork under concurrency
rls.sql:479-483: الـ trigger's SELECT a.hash ... ORDER BY a.created_at DESC LIMIT 1 لا يستخدم FOR UPDATE أو advisory lock. concurrent inserts يمكن أن يقرآ نفس "previous" hash وينتجا forked chain.
DB-006 — db:rls:test script path خاطئ
package.json:23: "db:rls:test": "tsx prisma/tests/rls-isolation.test.ts" — لكن الملف الفعلي في tests/rls-isolation.test.ts (بدون prisma/ prefix). pnpm db:rls:test يخطئ ENOENT.
DB-007 — bcryptjs version mismatch
@brightai/db يصرّح bcryptjs ^2.4.3، @brightai/dashboard يصرّح bcryptjs ^3.0.2. major version mismatch + لا ملف يستورده فعلياً (الـ seed يستخدم node:crypto).
