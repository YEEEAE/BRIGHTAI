# تغييرات التوافق وترحيل عقد API

## التغييرات التي تتطلب تحديث العميل

| السلوك الجديد | تحديث العميل |
|---|---|
| أخطاء HTTP تتكون من `code` و`message` و`dependencyStatus` و`requestId`. أزيلت حقول الخطأ القديمة مثل `contract` و`authorizationCode` و`setup` و`fallback` | اعتمد على HTTP و`code`. استخدم `X-Request-ID` في التشخيص |
| `GET /readyz/` و`GET /app/api/kernel/health/` في حالة 503 يعيدان عقد الخطأ | اجعل الإنذار يستند إلى رمز HTTP. اقرأ هوية البناء من 200 على `/healthz/`؛ تبقى بيانات الحالة العامة متاحة على `/status/` |
| رفض Firewall Guard يعيد غلاف الخطأ دون حقول القرار أو نتيجة التنفيذ المضمنة سابقًا | اعرض الرفض وسببه واطلب تحديث سجل القرارات. لا تُعد إرسال طلب غير مؤكد تلقائيًا. تبقى مخرجات المراجعة المعلقة على 202 |
| رفض حقول الاستعلام المجهولة أو المكررة وأجسام JSON غير المطابقة | أرسل الحقول المعرفّة لكل طريقة فقط. أبقِ مرشحات القائمة خارج طلبات الكتابة |
| رفض Origin غير المسجل ورفض CORS preflight | شغّل عملاء المتصفح من أصل التطبيق. اضبط الأصول المرحلية الموثوقة في الخادم بصيغة أصل كامل. يسمح Firewall Guard بعميل Bearer دون Origin وفق عقده |
| سجل سياسة Kernel يعيد 50 نسخة و50 إجراء موافقة في كل استجابة | تابع المجموعتين كلًا على حدة باستخدام مؤشري المتابعة ورقمي الصفحة |
| صفحة الأعضاء تُعيد أول 100 عنصر افتراضيًا، ويعرض Kernel أزرار الانتقال | اتبع `page` و`hasMore` حتى انتهاء النتائج. تطبق واجهة Operator API بنفسها حجم الصفحة 100 |
| مسار غير معروف يعيد 404 JSON في مدخل Node وطريقة غير مدعومة تعيد 405 | استخدم المسار والطريقة من سجل العقود. حدّث العملاء الذين كانوا يتوقعون HTML أو 404 للطرق غير المدعومة |
| Auth يرفض حقولًا إضافية وأنواعًا لم تكن مضبوطة عند الوكيل. قيمة `callbackURL` النصية المسموح بها في عمليتي البريد تُحذف قبل تمرير الطلب للمزوّد | طابق مخطط عملية Auth. استخدم واجهة OTP والدعوة الحالية لمسارات الإكمال |

إضافة `X-Request-ID` وحقول متابعة صفحات Operator ودعم `Idempotency-Key` لإنشاء مساحة العمل وطلب المراجعة وأصل المخاطر متوافقة مع العملاء الذين يستعملون العقود الجديدة للطلبات والاستجابات.

## ترتيب التنفيذ

1. **قبل النشر.** احصر عملاء API ومراقبي الجاهزية، وعدّل قراءة الخطأ والمرشحات وأسلوب إعادة الكتابة. نفّذ اختبارًا مرحليًا لنسخة SDK وChrome وOrigin وCSP على أصل معتمد.
2. **تهيئة البيئة المرحلة.** اضبط قائمة `AIGAS_API_ORIGINS` للأصول الفعلية المعتمدة. راجع مرور `Host` وHTTPS وترويسات منع الكاش من الحافة. تحقق من عدم إضافة CORS عند Cloudflare أو أي وسيط.
3. **قاعدة البيانات.** بعد موافقة تطبيق ترحيل البيئة المستهدفة، طبّق `0042_aigas_workspace_idempotency.sql` ثم `0043_aigas_risk_assist_attempts.sql` قبل تشغيل نسخة الواجهة التي ترسل المفتاح. تحقق من RLS ومنحتي `SELECT` و`INSERT` لـ`aigas_runtime` واختبر طلبين متزامنين بحساب اصطناعي. سجّل وضع الترحيل قبل الانتقال للخطوة التالية.
4. **نشر التطبيق والواجهة معًا.** اختبر على المنشأ المباشر ثم النطاق العام. تحقق من 200 و503 للجاهزية، وHEAD فارغ، ورفض Origin دخيل وOPTIONS، وتطابق معرّف الخطأ مع الترويسة. راجع نجاح عمليات المصادقة والمنتجات الأساسية ببيانات اصطناعية. تحقق أن السياسات الحالية تظل مطبقة وأن سجل القرار متاح بعد رفض Guard.
5. **المراقبة والرجوع.** راقب زيادة 400 و403 و405 و409 و503 حسب المسار والكود، مع معرّف HTTP فقط. عند فشل السلوك المتفق عليه، ارجع بنسخة التطبيق والواجهة ومراقب الجاهزية إلى الإصدارات المتوافقة. احتفظ بجداول منع التكرار وسجلاتها أثناء الرجوع حتى تظل مفاتيح المحاولات السابقة قابلة للتحقق عند إعادة النشر.

نجاح التحقق المحلي لا يثبت تهيئة الحافة أو موفر Auth الحقيقي أو ترحيل قاعدة منشورة. لا توجد خطوة نشر ضمن التسليم المحلي.

## التحقق من خدمة Render الحالية

أظهر Render أن الالتزام `e8ce76bdc23982db50097346fb5bb5dd3005c334` منشور على خدمة BRIGHTAI من نوع Static Site التي تنشر `dist/client`. أعاد النطاق العام ومنشأ تلك الخدمة الصفحة الرئيسية بحالة 200، وأعاد كل من `/healthz/` و`/readyz/` و`/api/measurement-status/` و`/app/api/kernel/health/` حالة 404 بصيغة HTML. يتطلب تحقق API الحي خدمة Node Web Service تشغّل `npm start`، وفق `render.yaml`. تُختبر الخدمة على منشئها قبل أي تغيير في ربط النطاق.
