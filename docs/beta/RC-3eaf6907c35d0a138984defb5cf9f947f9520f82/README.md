## 4. بوابات Go/No-Go التسع

التفصيل الآلي في `GO-NO-GO-GATES.yaml`، وخطة الأدلة في `VERIFICATION-PLAN.md`. الملخص:

| Gate | الاسم | الحالة | صاحب القرار | الدليل المطلوب للإغلاق |
|---|---|---|---|---|
| G1 | وصول الموقع | `PASS` بنطاق ضيق | مالك المنصة + مشغّل النشر | استجابة 200 للمسارات العامة من host معروف، مع تسجيل التاريخ |
| G2 | مطابقة Source/Artifact | `BLOCKED` | مالك المنصة + مشغّل النشر | SHA المنشور = مرشح، digest/معرّف artifact، استجابة Origin |
| G3 | App SSR + Auth | `BLOCKED` | الأمن + مالك المنصة | `503` متوقع قبل الفتح، ثم جلسة حقيقية وHealth API من Origin |
| G4 | RLS role + tenant isolation | `BLOCKED` | الأمن + مشغّل قاعدة البيانات | دور `NOBYPASSRLS`، سياسات كافية، سيناريو Tenant A/B ناجح |
| G5 | Schema staging | `BLOCKED` | مشغّل قاعدة البيانات + مالك المنصة | فرع staging معتمد، تطبيق الترحيلات، فحص post-migration |
| G6 | Providers and privacy approvals | `BLOCKED` | مالك المنتج + الأمن/الخصوصية + القانوني | قوائم معتمدة، منطقة، No-Training، احتفاظ، مفاتيح في secret store |
| G7 | Backups/restore | `BLOCKED` | مشغّل قاعدة البيانات + مالك المنصة | snapshot + استعادة فعلية إلى فرع منفصل مع أعداد مطابقة |
| G8 | Incident monitoring | `BLOCKED` | التشغيل + الأمن | on-call، تنبيهات 5xx/زمن الاستجابة، قناة حوادث، Runbook |

**ملاحظة G1:** نجاح المسارات العامة لا يثبت أن الخدمة المنشورة هي هذا المرشح، ولا يفتح البوابة. لذلك G2 يبقى `BLOCKED`.

**ملاحظة وصول محمية:** خلل `aria-expanded` في قائمة الجوال قائم في المصدر: القيمة الابتدائية `true` بينما القائمة مغلقة، وتُصحح فقط عند التبديل. لا يُعدّل الهيدر المحمي في هذه المهمة؛ يُسجَّل كشرط وصول يجب معالجته بتفويض منفصل قبل أي Beta عام.

### 5.2 ما هو مسموح في Beta

1. عرض مسار المنتج وواجهته على بيانات اصطناعية بعد فتح G3.
2. تشغيل قرار Firewall محلي بلا شبكة، وإثبات `DENY/WARN/ESCALATE/ALLOW/REDACT` من harness معتمد.
3. إنشاء أحداث Ledger اصطناعية، تصديرها، وتشغيل الفاحص المستقل، مع إثبات `MATCH` و`MISMATCH`.
4. سيناريو Human Gate بحسابين: مقدم ومراجع مستقل، مع رفض المراجعة الذاتية وانتهاء الصلاحية.
5. سجل Risk Engine اصطناعي مع خطر متبقٍ وقبول مستقل للخطر العالي.
6. فحص واجهة Secure Chat أنه يفشل مغلقًا برسالة واضحة عند غياب النموذج/الحصة.

### 5.3 ما هو ممنوع

- أي بيانات عميل حقيقية أو نسخ من `production`.
- أي إرسال إلى مزود AI خارجي.
- أي ادعاء `Available` أو `Live` أو `Beta` عام أو شهادة.
- أي تفعيل ذاتي أو منح منتج بلا `approval_reference`.
- أي `AIGAS_APP_ENABLED=true` على الإنتاج.
- أي فتح Data API أو تغيير GRANT/RLS خارج نافذة معتمدة.
- أي استخدام لـ48h PoV كالتزام تعاقدي قبل التوقيع.

### 5.4 شروط الخروج من Beta

1. اجتياز كل بوابات P0 التسع مع أدلة مؤرخة على نفس المرشح.
2. تقرير Pilot معتمد بلا عيوب حرجة، حسب القرار 104.

4. قرار مالك منفصل بالتوسع. نجاح Beta لا يمنح توسعًا تلقائيًا.

## 6. Rollback

### 6.1 triggers

| الحالة | الإجراء |
|---|---|
| فشل نشر أو فحص صحة | إبقاء `AIGAS_APP_ENABLED=false`، والعودة إلى آخر deploy سليم معروف |
| ظهور بيانات مؤسسة أخرى | إيقاف الكتابة فورًا، عزل الجلسات، إبلاغ الأمن، عدم إعلان نجاح |
| فشل migration | `ROLLBACK` داخل المعاملة، أو roll-forward بترحيل تصحيحي معتمد |
| فشل Restore rehearsal | منع بدء PoV |
| تسريب سر | تدوير فوري، إبطال الجلسات/المفاتيح، إشعار حسب السياسة |
| عيب وصول حرج | إيقاف عرض المنتج المعني، لا تعطيل الحماية الأساسية |

### 6.2 خطوات rollback المعتمدة

1. سجّل الوقت UTC، deploy ID الحالي، SHA، والحالة قبل التغيير.
2. أوقف حركة Beta: أبقِ البوابة مغلقة، وألغِ نافذة PoV.
3. أعد نشر آخر deploy سليم للخدمة من مزود الاستضافة، أو أعد توجيه الدومين إلى origin السابق المعروف.
4. امسح كاش `/app/*` عند الحاجة، ثم أعد فحص الصفحات العامة و`/app/` وHealth API.
5. إن كان السبب قاعدة البيانات: استعد من نقطة معتمدة إلى فرع منفصل، تحقق، ثم أعد الخدمة.
6. دوّر أي سر لامس البيئة المتأثرة.
7. وثّق السبب الجذري والإجراء في سجل الحوادث.

**لا يُنفّذ أي بند أعلاه في هذه المهمة.** لا حذف خدمة أو فرع أو DNS record دون موافقة مالك المورد.

## 9. On-call والتشغيل

**الحالة:** خطة فقط. لا جهة on-call معتمدة بعد.

| الدور | المسؤولية | الحد الأدنى |
|---|---|---|
| Incident Commander | قيادة الحادث وقرار الإيقاف | شخص واحد معروف بالاسم والدور |
| Security on-call | تقييم أمني واحتواء وتدوير أسرار | مسار تصعيد مكتوب |
| Platform on-call | الخدمة والنشر وCDN | صلاحية rollback |
| DB on-call | النسخ/الاستعادة/الترحيلات | صلاحية فرع staging والاستعادة |
| Product owner | قرار تعطيل منتج والإشعار | متاح خلال نافذة PoV |
| Legal/Privacy | تقييم الإشعار والالتزام | مسار اتصال معتمد |

**حدود الاستجابة:** أهداف داخلية غير تعاقدية تُعتمد قبل PoV. لا SLA معلن.

**التنبيهات المطلوبة قبل PoV:**
- 5xx ومعدل الأخطاء على `/app/api/*`.
- زمن استجابة وحدود الاتصال.
- فشل تسجيل الدخول/الدعوات.
- محاولات وصول عبر مؤسسة أخرى (رفض متكرر).
- فشل التحقق من Ledger أو تصديره.
- نفاد الحصة أو رفض المزود.

**قناة الحوادث:** بريد أمني معتمد + قناة داخلية. لا تُنشأ قناة أو عنوان في هذه المهمة.
