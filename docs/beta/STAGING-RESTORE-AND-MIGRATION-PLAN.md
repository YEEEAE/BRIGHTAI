## 1. تصميم Staging قابل للعزل

### الخيار الموصى به: مشروع Neon مستقل

| الخاصية | القرار المقترح | السبب |
|---|---|---|
| المشروع | مشروع مستقل (`aigas-staging`) لا فرع من `production` | فرع Neon يرث بيانات الأصل وmetadata الخاصة بـAuth. المشروع المستقل يمنع الوراثة من الأساس. |
| البيانات | اصطناعية فقط، تُنشأ من migrations | لا نسخ بيانات عملاء ولا Auth metadata |
| الاعتماديات | `DATABASE_URL` مستقل، اعتماد Neon Auth مستقل، JWT secret مستقل | لا مشاركة أسرار مع الإنتاج |
| مزودو AI | `APPROVED_MODELS=[]`, `approvedProviders=[]`, بلا مفاتيح | لا إرسال خارجي |
| Data API | معطّل على `public` | سطح وصول عميل مباشر غير مطلوب لاختبار الخادم |
| الاتصالات | `block_public_connections=true` مع `allowed_ips` محددة أو Private Link | تقليل سطح الشبكة |
| الحماية | `protected=true` بعد الإنشاء | منع الحذف/التصفير العرضي |
| دورة الحياة | `expires_at` معلنة أو مراجعة دورية | منع تراكم نسخ |
| التحليلات | بلا GA4/PostHog أو مفاتيح منفصلة | لا خلط قياس |

### خيار مرفوض افتراضيًا
إنشاء فرع staging من `production` مباشرة. رغم أن عدّ المستخدمين/الجلسات الحالي صفر، فالفرع ينسخ schemas وmetadata، وسياسة Beta تقتضي بيانات اصطناعية. لا يُستخدم إلا بقرار استثنائي موقّع ومسار تنقية موثق.

### بناء المخطط على staging
- تطبيق migrations بالترتيب المعتمد من `0001` إلى `0027` على قاعدة staging الفارغة، لا نسخ dump.
- إبقاء `0001`…`0012` كأساس fresh-install الحالي، ثم الترحيلات التالية وفق §3.
- التحقق بعد كل ملف: كائنات موجودة/غائبة، لا تصادم فهارس، ونتيجة المعاملة.

## 2. خطة التحقق من الاستعادة (Restore Rehearsal)

### قبل الإنشاء (بوابة إلزامية)
1. توقيع المالك على إنشاء snapshot/restore point ونافذة العمل.
2. تسمية منفّذ DBA مستقل عن كاتب الترحيلات.
3. تسجيل نقطة البداية: الفرع، الوقت UTC، LSN، عدد الجداول (31)، حالة RLS، وحالة كل migration.
4. لا أسرار ولا DSN في المستودع أو الدليل؛ فقط مرجع المخزن السري.

### خطوات التمرين (على فرع منفصل)
```text
1) create_snapshot(project, branch=br-young-bird-b43proeb, name=<dated>, timestamp/LSN)
2) restore_snapshot(snapshot_id, name="restore-check-<date>")   # فرع مستقل، لا finalize على production
3) تحقق الكتالوج على فرع الاستعادة:
   - 31 جدول public
   - عدد السياسات = 2
   - RLS enabled = 31/31، FORCE = 0
   - الجداول والعدّ المتوقع (حاليًا 0 في العينة)
   - أعلى migration متحققة: 0020/0021 PRESENT، 0013 PARTIAL
4) قياس الزمن من بدء الاستعادة إلى اكتمال التحقق → RTO فعلي
5) احتساب RPO: الفارق بين آخر كتابة مقبولة ونقطة الاستعادة
6) حذف فرع الاستعادة أو إبقاؤه وفق سياسة معلنة
```

### معايير القبول
- الكائنات أعلاه مطابقة للمتوقع قبل التمرين.
- استعلامات المؤسسة تعمل بالدور المقصود، والكتابة ممنوعة حيث يجب.
- لا يظهر مستأجر آخر في أي استعلام.
- RTO/RPO **مقيسان** ومكتوبان؛ لا أهداف مُختلقة.

### قيود حالية
- `history_retention_seconds=21600` (6 ساعات) و**لا snapshots ولا جدول نسخ**. الاستعادة بعد 6 ساعات غير مضمونة.
- أي snapshot يدوي يجب أن يُنشأ قبل أي تغيير مخطط على الفرع المخوّل.

## 3. جدول الاعتماديات والترتيب وخطة Rollback

### الترتيب المقترح على staging
```text
0013 → 0014 → 0016 → 0017 → 0018 → 0022 → 0026 → 0023 → 0025 → 0027
(0020, 0021 مطبّقان مسبقًا — تحقق فقط)
0019: لا يُطبّق عند اعتماد 0025 (0025 يستبدل دوره وسياساته)
0024: تحقق لاحق فقط؛ يجب أن يكون no-op إذا طُبّق 0013 و0017 صحيحًا
```

### المصفوفة

| الملف | يعتمد على | الكائنات التي ينشئها/يغيّرها | التحقق بعد التطبيق | Rollback |
|---|---|---|---|---|
| `0013` | `0003` | يستبدل قيد `aigas_ld_events_check` (خمس حالات + `request_fingerprint`)، ينشئ `aigas_ld_events_chain_guard` وtrigger | القيد يحتوي `request_fingerprint`، والدالة/الـtrigger موجودان | احفظ تعريف القيد القديم بـ`pg_get_constraintdef`؛ ثم DROP TRIGGER/FUNCTION وأعد القيد. **إن وُجدت صفوف بالحالات الجديدة، استخدم roll-forward لا تراجعًا.** |
| `0014` | `0004`, `0006`, `0007` | أعمدة `review_level/separation_of_duties/delegation_enabled` في `hg_policies`، وأعمدة إلغاء/`provider_ref` في `hg_requests`، وجداول `aigas_hg_delegations` و`aigas_hg_grants`، وتحديثات بيانات + `NOT NULL` | الجداول والأعمدة موجودة، والـguards مقبولة | **لا down migration.** اعتمد على restore point؛ عكس DDL بعد `NOT NULL` وتحديث الصفوف غير آمن. |
| `0016` | `0009` | `aigas_sc_usage_window_v2(uuid,uuid)` SECURITY DEFINER | الدالة موجودة، و`EXECUTE` غير ممنوح لـ`PUBLIC`/`authenticated` | `REVOKE ALL` ثم `DROP FUNCTION` إن لم يوجد اعتماد. |
| `0017` | `aigas_audit_events` | 3 أعمدة + قيدا صيغة + فهرس unique جزئي | الأعمدة/القيدان/الفهرس موجودة | DROP INDEX + DROP CONSTRAINT + DROP COLUMN. **يفقد بيانات السياق المكتوبة؛ لا ينفّذ بعد كتابة إنتاجية.** |
| `0018` | — (يسبق 0019/0025) | REVOKE على الجداول/التسلسلات/الدوال من `authenticated`/`anonymous` + تعديل default privileges | `information_schema.role_table_grants` خالٍ لأدوار العميل | أعد المنح من لقطة ACL محفوظة (`role_table_grants` + `pg_default_acl`) حرفيًا. |
| `0022` | `0002`, `0009` | فهرسان unique: `aigas_fw_decisions_request_scope_idx`, `aigas_sc_requests_scope_idx` | الفهارس موجودة | `DROP INDEX`. **إن وُجد تصادم بيانات، لا تنشئه أصلًا؛ أصلح البيانات أولًا.** |
| `0023` | `0001`, `0006`، واعتمادات منتج/مالية/قانونية | `aigas_trial_requests`, `aigas_trial_events`, `aigas_trial_entitlements` | الجداول والفهارس موجودة | `DROP TABLE` بالترتيب (events → entitlements → requests). فقدان بيانات؛ staging فقط. |
| `0025` | `0018`, `0022`، ويفضّل بعد `0023` | دور `aigas_runtime` (NOLOGIN)، دوال النطاق الخمس، سياسات catalog-driven، سياسة `RESTRICTIVE`، فهارس المراجع | الدور `NOBYPASSRLS`، السياسات على كل جدول `aigas_*`، `FORCE RLS` حيث ينطبق | DROP السياسات (`aigas_runtime_tenant*`, `aigas_client_deny`)، REVOKE، DROP الدوال، DROP ROLE (بعد إثبات عدم وجود اعتماد)، ثم أعد ACL من لقطة 0018. |
| `0026` | `0005`, `0008`, `0015`, `0021` | أعمدة الخطر المتبقي و`acceptance_policy_version`، قيود `NOT VALID`، يستبدل `aigas_re_guard_treatment` | الأعمدة/القيود موجودة، والدالة محدّثة | DROP القيود والأعمدة، وأعد تعريف دالة 0021 من `pg_get_functiondef` المحفوظ مسبقًا. |
| `0027` | `0025` | سياسات participant-only على جدولي المحتوى، `FORCE RLS`، REVOKE على جدولي المتن | لا سياسة مؤسسة على المحتوى، لا SELECT لـ`aigas_runtime` على المتن | **Roll-forward مفضل.** التراجع يعيد تعريض المحتوى لسياسة المؤسسة؛ يحتاج قرار أمني صريح. |

### قواعد عامة
- كل ملف داخل معاملة واحدة؛ `BEGIN/COMMIT` كما في المصدر.
- لا إعادة تشغيل ملفات غير idempotent (`0017`, `0023`) بعد إصلاحات لاحقة.
- `0024` لا يستبدل `0013`/`0017`، ولا يُعاد `0017` بعده.
- لا `DROP` على `production`؛ التراجع على الإنتاج = roll-forward أو استعادة كاملة.

## 4. RPO / RTO — طريقة القياس لا أهداف مُختلقة

| المقياس | المصدر | الحالة |
|---|---|---|
| أقصى نافذة استعادة | `history_retention_seconds=21600` | `VERIFIED` |
| snapshots دائمة | لا يوجد | `VERIFIED` |
| نسخ مجدولة | لا يوجد | `VERIFIED` |
| RPO مقيس | يحتاج أول دورة كتابة + نقطة استعادة | `NOT_VERIFIED` |
| RTO مقيس | يحتاج تمرين استعادة فعلي | `NOT_VERIFIED` |

لا توجد أهداف RPO/RTO معتمدة في المستودع. تُسجّل بعد التمرين، وتُعتمد من المالك والـDBA.
