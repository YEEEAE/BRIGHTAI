## 1. المشكلة بدقة

SQL لا يستطيع تعطيل Data API ولا تغيير `db_schemas`؛ هذه إعدادات control plane. الحالة الحالية على production:

1. نقطة REST عامة `https://<endpoint>/neondb/rest/v1` تعرض مخطط `public` حيث تعيش جداول `aigas_*`.
2. الضوابط المستهدفة ثلاث طبقات: صفر منح لـ`authenticated`/`anonymous`، وسياسة `aigas_client_deny` RESTRICTIVE، وRLS. هذه مثبتة على Staging بعد T02، **وليست مطبقة على production** (124 منحة authenticated وسياسات2).
3. `db_aggregates_enabled=true` يسمح لـPostgREST بتجميعات؛ الضوابط المستهدفة تمنع الوصول؛ لا ينطبق افتراض صفر المنح على الإنتاج الحالي، والتجميعات تزيد السطح.
4. `public` ليس مخططًا مخصصًا للعميل، بل مخطط التطبيق الخادمي. تعريضه للإنترنت قرار معماري خاطئ حتى لو كانت المنح مغلقة اليوم.

**الخلاصة:** لا يوجد اليوم دليل على تسريب (لم يُختبر REST فعليًا)، لكن التعرّض نفسه سطح هجوم مستقل عن SQL. إغلاقه مطلوب قبل Beta.

## 2. الخيارات

### الخيار A — تعطيل Data API (موصى به للإنتاج)

- الإجراء: `delete_data_api` على `production/neondb` (أو إبقاء endpoint معطّلًا).
- الأثر: لا مسار REST خارجي إلى القاعدة. Neon Auth يعمل عبر مساره المستقل، ولا يعتمد على Data API.
- الإيجابيات: أقوى ضمان، ولا يعتمد على صحة المنح أو السياسات.
- السلبيات/المخاطر: أي عميل مستقبلي يعتمد على REST سيتوقف. ينطبق فقط إن لم يكن هناك مستهلك حقيقي (لا يوجد اليوم مستهلك معروف).
- التحقق بعد التطبيق: `get_data_api` يعيد 404، وطلب REST بلا JWT يعيد فشل اتصال/404، ولا صف من `public.aigas_*`.
- التراجع: إعادة `provision_neon_data_api` بنفس `db_schemas` بعد اعتماد مكتوب؛ الترحيلات لا تتأثر.

### الخيار B — تقييد `db_schemas` إلى مخطط غير AIGAS

- الإجراء: `update_data_api` بـ`db_schemas=["api"]` (مخطط مخصص فارغ أو لعرض عام مُصمم)، مع `db_anon_role` كما هو.
- الأثر: يبقى REST متاحًا لسطح مستقبلي، لكن `public` و`neon_auth` خارج التعرّض.
- الإيجابيات: يسمح بمسار API لاحق دون إعادة إنشاء endpoint.
- السلبيات: يحتاج تصميم مخطط `api` وVIEWs ومراجعة منح منفصلة؛ يظل السطح الخارجي قائمًا. `available_schemas` تضم `auth` و`neon_auth` حاليًا، لذا يجب التأكد أن الاختيار لا يضمهما.
- التحقق: `get_data_api.settings.db_schemas == ["api"]`، وطلب `/rest/v1/aigas_tenants` يعيد 404، وطلب جدول `api` المسموح يعمل حسب التصميم.
- التراجع: إعادة `db_schemas=["public"]` خلال نافذة معتمدة.

### الخيار C — إبقاء `public` مكشوفًا (مرفوض)

- مرفوض كحالة نهائية. يظل مقبولًا **مؤقتًا فقط** إذا كان مالك Neon يوقّع على قبول المخاطرة كتابةً، ومعه: صفر منح مثبت، `aigas_client_deny` على 36/36، ومراقبة أي تغيير في `pg_default_acl` أو المنح.
- لا يجوز استخدامه ذريعة لتأجيل cutover إلى `aigas_runtime`.

---

## 3. التوصية

1. **الخيار A على production قبل أي Beta**، لأنه لا يوجد مستهلك REST معروف، ولأن التطبيق يمر عبر Node/WASM server فقط.
2. إن ظهر مسار عميل حقيقي لاحقًا: **الخيار B** بمخطط `api` مستقل، مع منح وسياسات منفصلة ومراجعة أمنية.
3. لا يُعتمد الخيار C إلا كحالة انتقالية موقّعة زمنيًا.
