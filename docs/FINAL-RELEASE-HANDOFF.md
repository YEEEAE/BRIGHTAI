### Gate 12 — Operations / Restore

## 7. Runbook مختصر للمشغّل المخوّل لاحقًا

> **لا يُنفَّذ أي بند هنا من الوكيل.** هذا تسلسل تشغيلي مشروط، وكل خطوة تتوقف إن غاب اعتمادها.

### المرحلة A — الاعتمادات قبل أي تغيير

1. توقيع المالك على نطاق الإطلاق والمنتج المحدد (ليس كل المنتجات دفعة واحدة).
2. اعتماد الأمن/الخصوصية لـ: الهوية، RLS/GRANT، Data API، الاحتفاظ، الحذف، وإقامة البيانات.
3. اعتماد القانوني/المالي لـ: Privacy/Terms، DPA، الأسعار، التجربة، والترخيص.
4. تعيين Operator مستقل عن كاتب المهاجرة (فصل واجبات).
5. تسجيل نافذة تنفيذ وخطة تراجع.

### المرحلة B — الأسرار والبيئة

1. تدوير أي سر لامس بيئة تطوير أو محادثة: `DATABASE_URL` و`NEON_AUTH_*` وأي `AIGAS_SC_*_API_KEY` مستقبلًا. لا تُطبع القيم.
2. إنشاء القيم في Secret Store الخاص بالخدمة فقط (`sync: false`). لا `.env` متتبع، ولا ملف في المستودع.
3. ضبط `NEON_AUTH_BASE_URL` و`NEON_AUTH_JWKS_URL` من أصل HTTPS معتمد.
4. إبقاء `AIGAS_APP_ENABLED=false` حتى نهاية المرحلة E.

### المرحلة C — قاعدة البيانات على staging

1. إنشاء فرع staging معزول (بيانات اصطناعية فقط) وحمايته.
2. أخذ نسخة/نقطة استعادة، ثم **اختبار استعادة فعلي** في فرع منفصل.
3. تطبيق الترحيلات غير المطبقة بالترتيب المعتمد على staging: `0013` → `0014` → `0016` → `0017` → `0018` → `0022` → `0025` → `0023`، ثم تشغيل سيناريو Tenant A/B. (`0021` و`0020` مطبقتان؛ راجعهما قبل الاعتماد.)
4. فحص بعد كل ترحيل: الأعمدة/الدوال/الفهارس/السياسات/المنح، ثم اختبار سلبي لمؤسستين.
5. نقل `DATABASE_URL` إلى دور تشغيل `NOBYPASSRLS` بعد حل bootstrap أول مساحة عمل وقبول الدعوات.
6. تعطيل/تقييد Data API على `public` بإجراء control-plane معتمد.

### المرحلة D — الهوية والمنتج

1. إنشاء أول مؤسسة وعضوية `OWNER` عبر المسار المعتمد (لا SQL يدوي غير مراجع).
2. إنشاء مستخدم اختبار اصطناعي وجلسة، ثم اجتياز: دخول → عضويات → إتاحة منتج → رفض مؤسسة أخرى.
3. منح منتج واحد فقط (مثل Human Gate) للتجربة؛ لا منح شامل.
4. اعتماد النموذج/المزود/المنطقة/No-Training **قبل** أي إرسال Secure Chat أو Firewall.

### المرحلة E — فتح البوابة

1. على staging: `AIGAS_APP_ENABLED=true`، ثم فحص `/app/` و`/app/api/kernel/health`.
2. تأكيد `no-store` و`noindex` و`Vary` و`X-Frame-Options: DENY` من الاستجابة الفعلية.
3. تشغيل سيناريوهات القبول المحددة للنطاق فقط، وتسجيل الأدلة.
4. بعد اعتماد النتائج: نشر نفس الحزمة على production، ثم `AIGAS_APP_ENABLED=true` هناك.
5. لا يُفتح العلم في production قبل اعتماد البوابات الاثنتي عشرة، وبالحد الأدنى Gate 1 وGate 3 وGate 12.

### المرحلة F — DNS / SSR

1. ربط الدومين بخدمة Node web service، لا بـ`dist/client` أو استضافة ثابتة.
2. تمرير `/app/*` و`/app/api/*` دون rewrite إلى `index.html`، وتعطيل كاش CDN لهذا البادئة.
3. التحقق من استجابة الخادم عبر `curl` من المشغّل؛ 404 من المزود تعني مسارًا/أصلًا خاطئًا لا خطأ صفحة.

### المرحلة G — المراقبة والدعم

1. تفعيل مراقبة توفر واستجابة `/app/api/kernel/health` (لا `/` فقط).
2. تنبيهات أخطاء 5xx ومعدل الرفض وحدود الاتصال.
3. جهة on-call وبريد أمني وبريد أعطال، بحسب القرارات 96/97.
4. سياسة احتفاظ مطبقة، ومراجعة وصول دورية، وتمرين استعادة دوري.
5. أي حادث: احتواء، تدوير أسرار، إشعار حسب العقد/القانون، تقرير سبب جذري.

**شروط توقف فورية:** فشل ترحيل، ظهور مؤسسة أخرى في استعلام، استجابة `/app` من CDN، غياب استعادة ناجحة، أو غياب اعتماد النموذج/المزود.
