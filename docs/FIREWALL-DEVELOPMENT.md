# Firewall — local policy evaluation and guarded execution

Status: **IMPLEMENTED_NOT_VERIFIED / PARTIAL**, 2026-11-03. Current changes have not been built or exercised, at the owner's explicit request. Earlier local results concern earlier source only. The Firewall upgrade `0012` and Kernel policy hierarchy `0010` were applied to Neon `production` by explicit owner instruction; no deployment, provider approval, policy publication or runtime verification is implied.

Decision vocabulary: the service emits five states — `ALLOW`, `WARN`, `REDACT`, `ESCALATE`, `DENY`. These are the implementation names for the approved product-spec decisions; `ESCALATE` is the same concept as `REQUEST_APPROVAL`, and `DENY` is the same concept as `BLOCK`/Hard Deny. There is no sixth state.

## Current routes and authorization

`/app/firewall/` uses AppLayout and the shared Kernel session/institution selector. Every API authenticates the existing Neon Auth bearer JWT, loads the user's membership and rechecks Firewall access through Kernel's administrative grant. OWNER/ADMIN manage rules; MEMBER can read and evaluate. Other product licenses are not required.

- `GET /app/api/firewall/rules/?workspace=<membership>`: rules, all-time counts, provider status and decision history, 12 entries per page. Optional `action`, `reason`, `mode=LAB|GUARD`, `from`/`to` inclusive UTC dates and `page=1..10000` filter the history, not counts. Times display in Asia/Riyadh. Only decision-time rule ID/version are displayed; a renamed rule does not rewrite the historical label.
- `POST /app/api/firewall/rules/`: `{template}` or `{name,pattern,action,priority}`. `{duplicate_of:<rule id>}` creates a server-named copy as a new custom rule that starts disabled. The 25-rule limit includes disabled rules. Names are unique within the institution. Custom rules are editable; protected server templates are toggle-only.
- `PATCH /app/api/firewall/rules/`: `{id,version,enabled?}` and custom rule fields. Updates increment the version; concurrent changes return `409 RULE_CHANGED`.
- `DELETE /app/api/firewall/rules/`: `{id,version}`. Server templates are never deleted (`409 TEMPLATE_IMMUTABLE`); disable them instead. A rule cited by any saved decision is never deleted (`409 RULE_HAS_HISTORY`) so append-only history stays intact; disable it instead. Concurrent changes return `409 RULE_CHANGED`.
- `POST /app/api/firewall/evaluate/`: `{text,synthetic:true}`. Evaluates and persists metadata, returns the decision, rule reference, reason, evaluation time and a transient output, `execution_status=NOT_EXECUTED`, and never calls a provider. No match remains `ALLOW / NO_MATCH_LAB_ONLY`, explicitly not a safety judgment. `DENY` and `ESCALATE` never return the submitted or blocked text in the response.
- `POST /app/api/firewall/guarded-executions/`: `{text,synthetic:true,request_id:<new UUID>}`. Evaluates and saves the decision, the effective `policy_version`, a server-computed `request_fingerprint` and mandatory Kernel audit in one transaction, then invokes the server guard only after COMMIT. No client decision, destination URL, provider override or alternate text is accepted.

Separate modes are explicit: `/evaluate/` is a theoretical, non-executing evaluation (`mode=LAB`, always `NOT_EXECUTED`), while `/guarded-executions/` is the only enforcement mode (`mode=GUARD`) and returns `request_id`, `policy_version` and `request_fingerprint` so a saved decision can be traced to one tenant, one policy revision and one single-use request.

All requests use JSON; body size is capped at 18000 bytes and input at 4000 characters. Browser mutations require the same Origin. The guarded endpoint also permits an absent Origin for bearer-authenticated application integrations; it does not support service credentials, CORS or cookie authentication. Evaluation writes are capped at 60 per institution per rolling 60 seconds (`429 RATE_LIMITED`), in addition to the per-request UUID replay guard. `workspace` selects an actual membership and grants no authority. Authenticated responses are private/no-store/noindex. No content is sent to Analytics or logging.

## Enforcement boundary

Precedence is defense-first: `DENY` > `ESCALATE` > `REDACT` > `WARN` > `ALLOW`, regardless of numeric priority. Priority selects the cited rule within the winning action. `WARN` is not an unconditional allow: in the guard path it stops forwarding. Rules match escaped, case-insensitive literals, never arbitrary regular expressions. Redaction merges matching spans from the original text, including overlapping matches, before replacement with `[نص منقّح]`.

The guard blocks missing/invalid policy and unmatched input (`NO_MATCH_ENFORCED`). A Kernel policy that is not `ALLOW` becomes `DENY / KERNEL_POLICY_DENIED` and is never softened by product rules. The guard independently requires a stored Kernel `ALLOW` before **any** remaining path — including `ESCALATE` — so a human approval can satisfy `REQUEST_APPROVAL` but can never lift a mandatory Kernel block; without it the response is 409 `KERNEL_POLICY_REQUIRED` and no review request is created. It also rechecks that a well-formed tenant/request/policy binding exists before provider lookup; a missing authorizer or binding returns a fail-closed error. For `DENY` it returns 403 `POLICY_BLOCKED` without a provider call. `ESCALATE` returns 409 `HUMAN_GATE_NOT_CONFIGURED` in this release (no approved review integration, no created request, no provider call), and `WARN` returns 409 `WARNING_NOT_FORWARDED`; neither reaches a provider. For `REDACT` only the evaluator's redacted output is available to the adapter. For `ALLOW` only evaluated output is forwarded. Evaluation/saving/COMMIT failure prevents invocation.

The dashboard returns a single `enforcement` object describing the one enforcement route, the non-executing evaluation route, the durable binding, the provider/review integration codes and `execution: BLOCKED|AVAILABLE`. It is computed from the live registries, never asserted in HTML: with the empty provider registry the only truthful value is `BLOCKED` / `PROVIDER_NOT_CONFIGURED`. The guarded response also carries the Kernel policy decision, its reason, obligations, mandatory flag and the policy chain so the operator can see which policy produced the outcome.

`src/server/firewall/provider.mjs` deliberately contains an empty approved registry. Consequently a permitted policy decision returns **503 PROVIDER_NOT_CONFIGURED**, `persisted=true`, and `external_action_executed=false`; `providerState()` reports `approval=NOT_APPROVED` and `execution=BLOCKED`. A key in the environment is not provider approval. A future reviewed entry must bind exact institutions, model, processing region, approval reference/expiry, no-training terms and a bounded server adapter, and must declare `external:true`; a non-network local adapter can never be registered as an approved AI provider. It must not obtain destination or alternate content from the client. The approved model, region, tenant and approval reference are passed to the adapter as a frozen call descriptor so an adapter cannot substitute a destination. No adapter or provider has been approved or connected in this change.

The guard has no automatic retry or provider fallback and uses a 15s local `PROVIDER_TIMEOUT_MS`; no per-operation timeout has been approved, so this default must be reviewed before any adapter is enabled. A request UUID is consumed when its decision commits; reusing it with the same binding returns 409 `REQUEST_ALREADY_EVALUATED` and reusing it for a different decision returns 409 `REQUEST_ID_CONFLICT`; neither invokes a provider again. If an eventual approved adapter fails after invocation, the response reports `execution_status=UNKNOWN` and `external_action_executed=null`, since a timeout cannot prove non-delivery. A process crash after COMMIT can leave a saved decision without execution; the decision history is a policy history, not a delivery receipt.

This boundary governs **input on this endpoint only**. It does not intercept direct provider calls from other applications, inspect provider output, support streaming, implement full DLP or semantic prompt-injection detection, or enable a human approval workflow/commercial trials. `src/server/firewall/escalation.mjs` mirrors the provider registry: no approved Human Gate operation type or review payload contract exists for Firewall decisions (0004/0007 accept only `INTERNAL_DEMO_NOTE` and `KERNEL_WORKSPACE_RENAME`). Therefore `ESCALATE` stops before any provider call, creates no Human Gate request, and reports `HUMAN_GATE_NOT_CONFIGURED`; it never executes first and asks approval afterwards.

## Local no-egress verification

`src/server/firewall/local-adapter.mjs` is a fixed-response adapter with `external:false` and `localSandbox:true`. It performs no fetch, DNS, socket or key read, never echoes the evaluated text, and is **not** in `approvedProviders`; the dashboard therefore keeps reporting `PROVIDER_NOT_CONFIGURED` / `BLOCKED`. `enforceDecision(payload, { resolveProvider })` exposes a server-only seam for local verification and accepts an injected adapter only when it declares `localSandbox:true` and `external:false`; any injected external adapter is refused as `PROVIDER_NOT_CONFIGURED`. Sandbox success reports `external_action_executed:false` and `execution_status:LOCAL_SANDBOX_COMPLETED` (never `EXECUTED`), and sandbox failure reports `LOCAL_SANDBOX_FAILED` / `NOT_EXECUTED` because there is no egress to be uncertain about.

`scripts/firewall-local-verify.mjs` asserts the guard order with no database, network, key or deployment: DENY, WARN and ESCALATE make zero adapter calls; ALLOW forwards the evaluated text; REDACT forwards only the redacted output; an injected external adapter and a broken binding are both refused before lookup. It is not a substitute for authenticated staging evidence, tenant isolation proof or provider approval.

Both files were added locally on 2026-11-08 and were syntax-checked only; the harness and the staging matrix were **not run** in this change. See `docs/products/firewall/STAGING-VERIFICATION.md`.
