## 1. Executive summary

The repository's visual layer is structurally sound but has a systemic class of
defect that automated builds cannot see: **content that is present in the HTML,
occupies layout space, and renders nothing.** Three separate mechanisms did this,
two of which were fixed during this task and one of which remains partially open.

The single most consequential finding is that **the design system's entrance
animation is load-bearing for content visibility.** A card is `opacity: 0` by
default and becomes visible only if a dynamically imported IntersectionObserver
boots — no earlier than `load` + `requestIdleCallback(2500 ms)` — and then
happens to see that card intersect. Every failure mode of that chain is silent:
the import is wrapped in `.catch(() => {})`.

Second: `apps/dashboard` **does not build**. Twenty routes cannot be audited at
all. This predates the task and blocks any completion claim about them.

Third: **text zoom to 200% degrades sharply** while every other condition holds.
123 elements leave the viewport and 88 are clipped, against 20 and 30 at default
zoom — a WCAG 1.4.4 / 1.4.10 gap.

**Verdict: CONDITIONAL GO.** The public site renders correctly at every tested
viewport, the background contract holds on 2,608 measured runs with zero
violations, and no regression was introduced. Conditions in §16.

## 8. P0 — must fix before any release claim

### RDX-P0-001 · `apps/dashboard` does not build; 20 routes unauditable

- **Field:** Design System / Service Design · **Type:** Root issue
- **Routes:** all 20 dashboard routes · **Role:** tenant-user · **Viewport:** all
- **Evidence:** `next build` exits 1, `next dev` returns HTTP 500 on `/`,
  `/sign-in`, `/dashboard` and a 404 path.
  ```
  ⨯ node:crypto — UnhandledSchemeError
  app/api/firewall/redact/route.ts → lib/firewall/audit/durable.ts
    → lib/observability/sentry.ts → @sentry/nextjs → @sentry/opentelemetry
    → @opentelemetry/instrumentation → require-in-the-middle → node:crypto
  ```
- **Pre-existing:** yes. `git status apps/dashboard` was empty before any
  dashboard file was touched.
- **Root cause:** `serverExternalPackages` in `next.config.mjs` lists
  `@huggingface/transformers` and `onnxruntime-node` but not the Sentry /
  OpenTelemetry chain, so webpack tries to bundle Node built-ins.
- **User impact:** no dashboard at all in development; production deploy of this
  app is broken.
- **Effort:** S · **Regression risk:** medium (changes how observability is bundled)
- **Prompt:** `RDX-P0-DASH-BUILD` · **Status:** open, deliberately not fixed here

### RDX-P0-002 · Content visibility depends on a silent, late, best-effort script

- **Field:** Motion / Accessibility / Indexability · **Type:** Root issue
- **Routes:** every main-site route using `.card--feature`, `.feature-card`,
  `.inner-card`, `.home-stat-card`, `.home-faq-item`, `.home-evidence-mockup`,
  `.home-comparison-wrap`, `.inner-reveal` — 80 of 80 templates
- **Evidence:** on `/about/` at 1440×1000, 104 text nodes across 26 cards measured
  effectively invisible (cumulative ancestor opacity < 0.05) while occupying full
  layout height. `public/js/noncritical-init.js` imports the reveal module inside
  `import(moduleUrl).catch(() => {})` — every failure is swallowed by design,
  with the comment "Enhancements must never affect the document's primary
  content", which is precisely what this enhancement does.
- **Partially fixed in this task** (`BAI-REVEAL-FALLBACK-001`): the entry state is
  now gated on `html.reveal-ready`, which the observer sets as its first action,
  so a never-booting script leaves content visible. `.gsap-fade` — which revealed
  on a `[data-revealed]` attribute nothing in the repository ever sets, hiding the
  entire `/kernel/` unit-card grid — had its entry state removed outright.
- **Still open:** the architecture. Visibility remains conditional on a chain that
  boots >2.5 s after `load`, can lose its root class across Astro `ClientRouter`
  view transitions, and reveals only what intersects after boot. **The residual is
  real, not a harness artifact.** An earlier draft dismissed it as one; that was
  wrong. The harness already waits up to 6 s for `html.reveal-ready`, then sweeps
  the whole page in 90%-viewport steps and returns to the top — i.e. it does what
  a reader does. In the latest 640-run template pass, `reveal-ready` was present
  on 608 runs (absent only on the 32 standalone-`<html>` runs, correctly) and
  **170 runs still reported hidden content, 9,581 nodes in total.** The
  IntersectionObserver is not delivering for those elements. Worst routes: `/`
  (287 nodes), `/demo/` (156), `/services/` (144), `/kernel/` (126), `/about/` (96).
- **Measurement instability, disclosed.** Three nominally identical 640-run passes
  reported `stuck` = 3, 4 and 5, and `invisibleContent` = —, 184 and 170. The
  numbers above cite the most recent pass (`verify-site`). The spread is itself
  evidence that visibility here is timing-dependent, which is the defect.
- **Effort:** M · **Regression risk:** low · **Prompt:** `RDX-P0-REVEAL-ARCH`

### RDX-P0-003 · The background video loaded but never played (fixed)

- **Field:** Motion & Digital Art · **Type:** Root issue · **Routes:** all 273
- **Evidence:** across 2,184 after-runs the video reported `paused: true` on
  **2184/2184**, while the byte-identical component in `apps/qc-task-manager`
  reported `paused: false` on **424/424** under the same harness. A dedicated
  6-second probe confirmed the site's video reached `readyState: 4`, intrinsic
  `1600×1200`, HTTP `206`, no media error — and still sat at `currentTime: 0`.
- **Root cause:** Astro's `ClientRouter` re-inserts body nodes on
  `astro:page-load`; Chromium honours `autoplay` only for an element inserted
  during parsing, so a re-inserted `<video>` stays paused with a full buffer. QC
  has no `ClientRouter`, which is why identical code played there.
- **Fixed** (`BAI-BG-VIDEO-002`): an explicit `play()` kick in all three
  implementations, with the rejection deliberately ignored so blocked autoplay and
  `prefers-reduced-motion` both fall back to the poster. Re-verified: site
  `/about/` `currentTime: 1.48`, site `/500.html` `1.68`, qc `/login` `0.95`.
- **Note:** the first draft of the implementation report asserted the video was
  "playing" and quoted intrinsic `1600×1200` for all 2,184 runs. Both were false —
  the first outright, the second because `readyState: 0` in 2,178 runs meant no
  intrinsic size existed to measure. An independent verification pass caught it.

### RDX-P1-LAYOUT-001 · Content clipped by overflow ancestors — 30 runs

Concentrated in kernel cards (`span.kernel-activity-item__time`,
`__trace-id`, `span.kernel-risk-row__value` clipped by `article.kernel-card`),
table headers clipped by `thead`/`tr`, and anchors clipped by
`section.brightai-raw-internal-links`. Timestamps and trace ids are truncated
without an ellipsis, so information is lost silently. Effort M · Prompt
`RDX-P1-CLIP`.

### RDX-P1-LAYOUT-002 · Content escaping the viewport — 20 runs

After excluding wide tables and code blocks that sit inside deliberately
scrollable wrappers (correct responsive behaviour), 20 runs still place content
outside the viewport with no scrollable ancestor. Document-level horizontal
overflow is **0 everywhere**, so this is contained but reachable only by
selection, not by scrolling. Effort M · Prompt `RDX-P1-ESCAPE`.

### RDX-P1-SEC-001 · `X-Frame-Options` delivered as a `<meta>` tag

All 2,184 runs log: *"X-Frame-Options may only be set via an HTTP header… It may
not be set inside `<meta>`."* `astro.config.mjs`'s `injectSecurityMeta()` emits
it as meta, where browsers ignore it. The real header is set by
`patch-server-entry.mjs`, so protection exists in production — but the meta tag
is dead weight and a misleading signal in any audit. Effort S · Prompt
`RDX-P1-XFO-META`.

## 16. Final verdict

### CONDITIONAL GO

**Supporting the GO:** 100% route and template coverage on the public site with
zero horizontal overflow, zero missing assets, exactly one `h1` per page, and
zero structural background-contract violations across 2,608 measured runs. The
qc-task-manager app is clean on every metric across 424 authenticated runs.
Three content-hiding defects (`.gsap-fade`, the reveal entry state, and a video
that loaded but never played) and a 269 KB CSS-delivery regression were fixed and
are now guarded by 95 automated checks.

**Regressions in the matched before/after pair, stated plainly:**

| Metric | before-site | after-site | |
|---|---|---|---|
| `groupSplits` | 41 | **43** | regression, +2 |
| `errored` | 0 | **1** | +1 — a 30 s screenshot timeout; the after run had `--shots`, the before run did not |
| `stuck` | 5 | 3 | improved |
| `lostCss` | 416 | 192 | improved |
| `noVideo` | 2184 | 0 | improved |

An earlier draft claimed "no regression was introduced". That was wrong:
`groupSplits` rose by 2 in the only directly comparable pair. The corrected
empty-band metric reports 10, but it was written **after** the change, so no
corrected "before" figure exists and the +2 is neither reproduced nor refuted.
The two runs also did not use identical harness flags (`--shots` differs), which
alone accounts for `errored`.

**Guard caveat.** `scripts/qa/verify-background-contract.mjs` reports 95/95, but
its denominator is derived from the checks executed (`total = pass + failures`),
most assertions are string-presence rather than behaviour, the reduced-motion and
print checks only prove the at-rule text exists rather than that the video is
hidden inside it, and nothing checks stacking or `z-index`. It is a
regression tripwire, not proof of correctness. Strengthening it is folded into
`RDX-P0-REVEAL-ARCH`'s acceptance criteria.


**Conditions that must clear before an unconditional GO:**

1. `RDX-P0-001` — `apps/dashboard` builds and its 20 routes are audited.
2. `RDX-P0-002` — entrance animation no longer gates content visibility.
3. `RDX-P1-A11Y-001` — 200% zoom reflows.
4. `RDX-P1-A11Y-002` — axe, keyboard and screen-reader evidence exists.
5. `RDX-PERF-001` — the 7.96 MB background's effect on LCP is measured and
   accepted with numbers rather than assumed.

**Why not GO:** Evidence Confidence is 50%, Human Validation is 0%, and one
workspace does not build. Declaring GO would mean asserting quality for 20 routes
that were never rendered.

**Why not NO-GO:** nothing found is a data-loss or security breach, no primary
journey on the public site is impossible, and the two P0s are a build
configuration line and an animation architecture — both bounded and understood.
