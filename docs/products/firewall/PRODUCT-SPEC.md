## 1. التعريف والقيمة

**AIGAS Firewall** طبقة حماية وإنفاذ لطلبات الذكاء الاصطناعي واستجاباته **التي تمر عبر نقطة تكامل معتمدة ومفعّلة**. يقيّم الطلب وفق هوية المستأجر، صلاحيات الفاعل، سياسة المؤسسة، تصنيف البيانات، مقصد الطلب والنموذج/الأداة، ثم يطبّق القرار المناسب. يحمي أيضًا جانب المخرجات ضمن حدود البروتوكول ونمط البث المعتمد.

**القيمة الأساسية:** تحويل سياسات استخدام AI من تعليمات مكتوبة فقط إلى قرارات تقنية قابلة للتطبيق والتدقيق على مسارات تكامل محددة.

**المشكلة التي يعالجها:** قد تُرسل التطبيقات أو الوكلاء معلومات داخلية أو شخصية إلى مزود غير مصرح له، أو تستقبل تعليمات عدائية من مصادر غير موثوقة، أو تستخدم أدوات بصلاحيات أوسع من المسموح. الاكتفاء برسالة تحذير أو فحص نصّي خارج مسار التنفيذ لا يمنع الفعل الحقيقي.

**ما لا يعد به المنتج:** لا يراقب تلقائيًا كل حساب ChatGPT أو تطبيق SaaS أو أجهزة العاملين، ولا يضمن كشف 100% من محاولات Prompt Injection، ولا يمنح شهادة امتثال، ولا يحوّل المحاكاة المرئية إلى محرك تشغيل.

## 3. حدود المنتج ومنظومته

- هو **منتج مستقل وظيفيًا وتجاريًا**؛ يُباع وحده أو ضمن باقة، ولا يُشترط شراء Ledger أو Risk Engine أو Human Gate لوظيفته الأساسية.
- **AIGAS Kernel** مكوّن تأسيسي مشترك لتفويض الهوية والمستأجر والسياسة والترخيص والتدقيق الأمني الأدنى **دون رسم ترخيص منفصل**.
- تكامل **Risk Engine** لإغناء سياق المخاطر، و**Human Gate** لسلاسل الاعتماد المؤسسية المتقدمة، و**Ledger** لتوثيق قابل للتحقق بعمق، كلها إضافات اختيارية مرخصة.
- إذا احتاجت سياسة Firewall قرارًا بشريًا في المسار الأساسي، يجب أن يوجد **مسار مراجعة أساسي مأمون** في عقد المنتج/Kernel أو يُرفض الإجراء بأمان حتى تكتمل الصلاحية؛ لا يجوز إجبار العميل على شراء Human Gate للحصول على منع آمن.
- الأمن الأدنى لـSecure Chat لا يعتمد على شراء Firewall التجاري.

### 3.1 حدود التغطية

```text
[تطبيق / وكيل / خدمة عميل]
  → [نقطة تكامل موثقة: API / SDK / Proxy / Connector]
  → [AIGAS Kernel: هوية، صلاحية، سياسة عليا، ترخيص، tenant]
  → [AIGAS Firewall: DLP + Injection/Tool checks + decision]
  → [ALLOW / WARN / REDACT / REVIEW / BLOCK]
  → [تنفيذ مسموح إلى مزود/أداة معتمدة + فحص المخرجات عند الحاجة]
  → [سجل أمان أساسي؛ Ledger اختياري]
```

**تحذير معماري:** Endpoint يقدم تقييمًا فقط (`evaluate-only`) **ليس** إنفاذًا تلقائيًا. لا تُسوّق الحماية التشغيلية حتى يثبت أن نقطة التكامل تمنع فعلًا عبور الطلب المحظور أو المخرجات المحظورة، بما في ذلك عند الفشل والتجاوز ومحاولات إعادة المحاولة.

## 4. القدرات المعتمدة في الماستر

| المعرف | القدرة | السلوك المطلوب | شرط إثبات أساسي |
|---|---|---|---|
| `FW-01` | نقاط حماية فعلية | API/SDK/Proxy/Connector ضمن نطاق معلوم | طلب حقيقي يسير عبر نقطة تكامل، ويتعذر تجاوزه ضمن النطاق المفوض |
| `FW-02` | قرارات حماية خمسة | `ALLOW`, `WARN`, `REDACT`, `REQUEST_APPROVAL`, `BLOCK` | قرار معلّل يؤدي إلى أثر تنفيذ حقيقي كما هو معلن |
| `FW-03` | السياسة العليا | Hard Deny لا يُنسخ بسياسة عميل أدنى أو خرج نموذج | اختبار تجاوزات وأدوار وسياسات متعارضة |
| `FW-04` | DLP عربي/إنجليزي | فحص إدخال/إخراج؛ معرّفات، أسرار، فئات محكومة | عينات اصطناعية معروفة النتيجة، تقارير FP/FN وحدود الكشف |
| `FW-05` | Prompt Injection & Tools | فصل مصدر المحتوى عن السلطة؛ تحقق صلاحيات الأدوات | هجمات مقيّدة تمنع الوصول غير المخول ولا تدعي كشفًا كاملًا |
| `FW-06` | وضع مراقبة | Shadow/Monitor بموافقة العميل عند ملاءمة الخطر | إثبات عدم تفعيل إجراءات مؤثرة دون موافقة، وعدم تجاوز Hard Deny |
| `FW-07` | ضوابط الضغط والتعطل | عزل وRate Limiting وFail-Closed عند الإلزام | انقطاع تبعيات وطلبات متوازية دون سماح صامت |
| `FW-08` | تدقيق أساسي | Event minimal مع سبب القرار ونسخة السياسة | سجل موثوق محدود البيانات حتى بدون ترخيص Ledger |

**كل هذه القدرات معتمدة كـمتطلبات، لكن الحالة التشغيلية الحالية `NOT_VERIFIED`.** راجع `FEATURE-STATUS.yaml` لتفصيل المرئي مقابل المشغّل.

## 5. عقد القرارات

| القرار | المعنى | أثر الإنفاذ | ضابط أساسي |
|---|---|---|---|
| `ALLOW` | الطلب ضمن الصلاحيات والسياسة | الاستمرار في المسار المحدد | لا يُستنتج من خطأ نظام |
| `WARN` | مسموح بشروط/تحذير محدد | إظهار/تمرير التحذير وفق سياسة معتمدة | لا يستخدم إذا تتطلب السياسة الإيقاف |
| `REDACT` | إزالة/تبديل عناصر بيانات محددة | **المرور بالنص المنقح فقط** عند السماح | لا تُخزن النسخة الخام في السجلات بلا تصريح |
| `REQUEST_APPROVAL` | تحتاج العملية موافقة بشرية مخولة | `PENDING` وتعليق التنفيذ حتى قرار صالح | لا تعتبر المهلة أو عدم الرد موافقة |
| `BLOCK` | انتهاك سياسة أو ضابط إلزامي | منع الإرسال/الإجراء أو حجب المخرج المحكوم | لا يمكن تخطي Hard Deny بموافقة أدنى |

في الطلبات ذات المخرجات المتدفقة (SSE/stream)، لا يجوز بث محتوى لم يُفحص إذا كان مخرجًا خاضعًا لفحص ملزم. يعتمد التصميم نمط حجز/تجميع محدود أو فحص آمن قبل الإفراج؛ حدود الكمون والذاكرة وسياسة رفض المحتوى غير المفحوص تتطلب اعتمادًا هندسيًا.

## 6. نطاق MVP الحقيقي

### 6.1 داخله (ملزم)

1. نقطة تكامل موثوقة واحدة على الأقل مع طلب AI حقيقي في بيئة غير إنتاجية معتمدة.
2. هوية مؤسسة ومستخدم/خدمة موثقة، وترخيص Firewall، ومنع عبور Tenant.
3. تحميل سياسة صالحة ذات نسخة وهرمية محكومة، وتطبيق Hard Deny.
4. **إنفاذ حقيقي** لـAllow وBlock، ثم Redact وRequest Approval وWarn حسب ما سيُعلن عن توفره، دون وعود قبل إثباتها.
5. DLP عربي/إنجليزي على نطاق بيانات معتمد، مع إيضاح حدوده.
6. منع استخدام الأداة/المزود غير المصرح ولو تضمن النص تعليمات تطلب ذلك.
7. سجل الحد الأدنى للقرار ولو لم يرخص العميل Ledger.
8. فشل آمن عند مهلة فحص، أو غياب سياسة، أو عطل تبعية مطلوبة.
9. سياسات حصص ومنع إساءة استخدام قابلة للضبط ومبرهنة.
10. توثيق حدود التغطية والسلوك وفروق أنماط النشر.

### 6.2 خارج MVP أو اختياري

- Risk Engine التجاري لدرجات مخاطر متقدمة.
- Human Gate المتقدم لسير الموافقات متعددة المراحل.
- Ledger المتقدم لسلسلة التوقيع/التحقق والتصدير المتخصص.
- دعم كل مزود AI وكل تنسيق/لغة/بروتوكول من يوم الإطلاق.
- اكتشاف شامل لأدوات الظل غير المدمجة أو التحكم بشبكة أجهزة العميل خارج التفويض.
- ضمان منع كل Prompt Injection / Jailbreak أو ضمان امتثال قانوني تلقائي.

## 7. سياسة الأمن والخصوصية

- **No-Training مطلق:** لا تستخدم BRIGHT AI أو المورد بيانات عميل لتدريب/تحسين نماذج. إذا تعذر إثبات الالتزام تعاقديًا وتقنيًا، يُمنع استخدام ذلك المزود لبيانات العميل.
- افصل بيانات المستأجرين عبر كل مسار: قواعد بيانات، سجلات، Cache، Queue، تقارير، مفاتيح، دعم.
- هوية المستأجر تُشتق من سياق موثق؛ لا تعتمد على `tenant_id` داخل Body وحده.
- حظر عالي الأولوية/FW-03 لا يتغير بوضع Shadow أو سياسة محلية أو fallback.
- بيانات التتبع `metadata` أولًا، وبدون إدخال Prompt أو مفاتيح أو PII في URL أو Analytics أو Logs.
- MFA/SSO والأدوار المخصصة ومراجعة صلاحيات التشغيل والإدارة، مع هوية محلية للبيئات المعزولة.
- التشفير في النقل والتخزين وحماية مفاتيح العملاء وBYOK وفق بيئة معتمدة، ولا ترسل المفاتيح إلى العميل دون ضرورة.
- إدارة الاحتفاظ والحذف وLegal Hold بحقول اعتماد صريحة؛ لا اختلاق مدد زمنية.
- استضافة SaaS السعودية افتراضيًا وفق القرار؛ معالجة المزوّد/البيانات خارج المملكة لا تحدث إلا بموافقة وعقد ونطاق نظامي مناسب.
- لا يسمح خطأ نظام أو انقطاع Ledger اختياري بحظر غير منطقي إلا إذا كان التسجيل إلزاميًا، ولا يسمح عطل التسجيل الإلزامي بالتجاوز.

## 9. التكامل والتسعير والتجربة

- أنواع التكامل المستقبلية: `SDK`, `Gateway/Proxy`, `Direct API`, `Approved Connector`، مع صلاحيات ومصدّرات معروفة. ليست جميعها منفّذة.
- وحدات الفوترة المرشحة: `PROTECTED_AI_REQUEST` **مبدئية**؛ لا تُحسب إعادة المحاولة أو مراحل داخلية مرتين دون أساس تعاقدي.
- فصل رسوم BRIGHT AI عن تكاليف مزود AI والتكامل والدعم حيث ينطبق، وميزانيات إنفاق وحصص معتمدة.
- تجربة 48 ساعة متصلة من `activated_at` بعد جاهزية البيئة. بيانات اصطناعية افتراضيًا، ولا اشتراك مدفوع تلقائيًا أو احتساب صامت.
- الحكومة وحالات البيانات الحقيقية والتكاملات الحساسة تحتاج الموافقات المقررة؛ عدم إمكانية تجربة 48 ساعة في بيئة عميل معينة يتطلب Pilot منفصلًا لا تسويق Trial غير متاح.
- لا وجود لسعر أو SKU أو حصة نهائية معتمدة في المصدر؛ جميعها `TBD / APPROVAL_REQUIRED`.
