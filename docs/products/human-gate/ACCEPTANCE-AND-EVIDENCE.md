## 0. معنى القبول

هذه الوثيقة تضبط **كيف نثبت** أن Human Gate يوقف فعلًا تنفيذ عملية قبل اعتماد بشري مخول، ويتحقق من مستوى الصلاحية والتفويض والمدة، ويرفض إكمال المهمة عند غياب الشرط، ويسجل الدليل الأساسي دون فرض ترخيص Ledger. **زر الموافقة التوضيحي في `ProductExperience.astro` أو بيانات Mock أو نجاح بناء Astro ليست إثباتًا لتشغيل المنتج.**

مصدر المتطلبات: `docs/MASTER-PROJECT-BLUEPRINT.md` §03.4 و`docs/PRODUCT-MASTER-CATALOG.yaml` (`AIGAS-HG`). مصدر المراجعة الحالي: GitHub `main` قراءة فقط، دون تحقق من API/بيئة مؤسسة تشغيلية. **النتيجة الابتدائية لكل معايير التشغيل أدناه هي `NOT_VERIFIED`، وليست `PASS`.**

## 4. البوابات التي تمنع الإطلاق (Release Blockers)

1. **لا يوجد دليل فعل حقيقي متوقف:** أي واجهة تقول `APPROVED` لكن العملية تنفذ قبلها أو بغيرها.
2. **SoD مكسور:** مقدم الطلب يعتمد ذاته أو يجمع مراحل مستقلة رغم سياسة منع ذلك.
3. **انتهاء صامت:** المهلة/عدم الرد/تعطل الاتصال يحول الحالة تلقائيًا إلى سماح.
4. **Replay أو تعديل النطاق:** ينجح Grant مستهلك، أو ينفذ مبلغ/مورد/أمر غير الموافق عليه.
5. **مراجعة غير مخولة:** Token صادر لكن دوره، بيئته، مؤسسته، MFA أو تفويضه غير ساري.
6. **حظر إلزامي متجاوز:** قبول بشري يفتح عملية ممنوعة بسياسة أعلى.
7. **إلزام شراء منتج إضافي:** Ledger/Firewall/Risk مطلوبون للـMVP الأساسي خلافًا للـBlueprint.
8. **تسرب بيانات أو تدريب:** أسرار/بيانات حقيقية في Logs أو Providers بلا موافقة، أو مستخدمة في تدريب نموذج.
9. **خروج بين المستأجرين:** قرار أو دليل أو Grant يرى مستخدمًا آخر من Tenant مختلف.
10. **إطلاق تجارب دون جاهزية:** 48 ساعة مفعلة دون حصة/ترخيص/اتفاق حماية أو دون انتهاء تلقائي.
11. **تدقيق غير موثوق:** لا يوجد دليل قابل للتتبع لهوية ونسخة سياسة وتاريخ ونتيجة.
12. **مخالفة مجال الإقامة/المعالجة:** نشر أو توجيه بيانات أو دعم خارج النطاق المعتمد.

## 6. إجراءات التحقق المطلوبة

### 6.1 تحقق إنشاء الطلب

- وجود Tenant مشتق من هوية موثوقة.
- بصمة Operation قابلة للمقارنة مع المصدر عند الإنفاذ.
- Policy Version معتمدة ومثبتة مع الطلب.
- انتهاء وسبب وسياق محدودان بقرارات سياسة معتمدة.
- Idempotent POST لا ينشئ مكررات؛ المحاولات المتزامنة نتيجتها واضحة.

### 6.2 تحقق الموافقة والصلاحية

- دور Reviewer لا يكفي دون صلاحية على نوع العملية والنطاق والمرحلة.
- يقاس قرار reviewer وفق الوقت وموافقة متعدد المراحل وSoD.
- step-up MFA عند السياسة لا يُلتف عليه بنسخة API مختلفة.
- المتزامنون لا يصنعون قرارين نهائيين متناقضين.
- الرفض النهائي يمنع إنشاء Grant؛ تغيير النص أو المورد بعد القرار يلزم طلبًا جديدًا.

### 6.3 تحقق التفويض

- التفويض لا يملك سطوة خارج صاحب الصلاحية الأصلي.
- لا يمكن تفويض مستخدم يكسر SoD إذا كانت السياسة تمنعه.
- صلاحية Delegate لا تمتد بعد `valid_until` أو الإلغاء أو خفض صلاحية الموكل.
- التصعيد لا يمدد انتهاء المهلة تلقائيًا أو يغير مستوى السلطة دون سياسة.

### 6.4 تحقق الإنفاذ

- Point of Enforcement متكاملة فعليًا بالمنفذ الحامل للأثر، وليست مجرد واجهة منفصلة.
- `APPROVED` لا يُنهي العملية إلا بعد ربط Grant محدد واستهلاكه بصورة ذرية.
- لا تنفيذ قبل `CONSUMED` المسموح، لا استهلاك ثانٍ، ولا تعديل Operation.
- غياب الخدمة/فشل قاعدة البيانات أو الشبكة أو الهوية = Safe Stop.
- توجد أدلة من النظام الأصلي (لا من Human Gate فقط) أن الرفض أو الانتهاء أوقف الأثر.
- التفريق بين **منح إذن** و**نجاح فعل العمل**: يجب توثيق فشل Downstream أو تكراره منفصلًا دون إطلاق أثر مزدوج.

### 6.5 تحقق السجل الأساسي

- قرار واحد مرتبط بمستأجر، reviewer، مرحلة، policy revision، time، reason، type.
- طباعة/تصدير أدلة أساسية متاحة دون Ledger مرخص.
- لا تعديل صامت للتاريخ، وتقييد وصول التدقيق والاحتفاظ والحذف.
- إمكان إعادة إنتاج سبب القبول/الرفض من سجل منشور ضمن حدود البيانات والامتثال.

## 7. المراجعة حسب البيئة

| البيئة | ما يثبت فيها | حدود النتيجة |
|---|---|---|
| Local dev | صحة المنطق الأساسي والاستدعاءات الجزئية | لا يثبت SaaS أو توافر إنتاج |
| Isolated staging | دورة طلب/مراجعة/إنفاذ على Synthetic Workload | لا يُعلن إطلاقًا دون موافقة أمن/تشغيل |
| SaaS Saudi | عزلة Tenant وحماية المفاتيح والمراقبة والهوية والحصص | مصدر بيانات الإنتاج ومناطق المعالجة يجب إثباتهما |
| On-Premise | ترخيص مستقل وصلاحيات وربط local identity وrollback | يحتاج تحقق مستقل في بيئة العميل |
| Air-Gapped | كل وظيفة الموافقات والتحقق والتراخيص والتوقيت محلية | لا DNS/API/هاتف منزلي يفرض اتصالًا خارجيًا |

## 8. مطابقة OpenAPI للتنفيذ

- العقد في `API-CONTRACT.yaml` **تصميم مقترح** يتضمن خطأ صريحًا للحالات المغلقة `403/409/410/412/423/503`.
- ربط كل Endpoint بالفعل الذي يحكمه، وراجِع موضع Enforcement Boundary، لا مجرد نتيجة JSON.
- `Idempotency-Key` يجب أن يمنع الأثر المكرر دون تعطيل فتح طلب مشروع منفصل.
- آلية إصدار Grant الداخلية لا تُستخدم من متصفح عام أو بحساب عادي.
- أية هوية، Origin، Tenant، Permissions تُستمد من رمز موثوق، لا من حقول يدّعيها طالب الموافقة.
- لا تعتبر اختلاف صيغة API عن وثيقة التصميم خطأ وحده؛ يُراجع القرار المعماري قبل تثبيت العقد.
