# خارطة طريق المرحلة الأولى  
## الملعب القابل للقياس

**الهدف:** تحويل Playground من تجربة تفاعلية تعرض مراحل الحماية إلى بيئة تقييم فعلية تقيس النماذج والسياسات والتطبيقات الذكية، وتقارن نتائجها، وتصدر **Evaluation Certificate** موقعة لكل تشغيل.

---

## النتيجة النهائية

يستطيع المستخدم:

1. إنشاء أو استيراد Dataset.
2. تشغيل حالة واحدة أو مئات الحالات.
3. اختيار النموذج والسياسات وScorers.
4. قياس الدقة، الهلوسة، PII، Prompt Injection، الامتثال، التكلفة والزمن.
5. مقارنة نموذجين أو سياستين أو نسختين من Prompt.
6. إعادة تشغيل التقييم بنفس الإعدادات والـSeed.
7. فتح كل فشل عبر Trace كامل.
8. إصدار شهادة موقعة وقابلة للتحقق.

---

# المرحلة 0: تثبيت الأساس

**الأولوية:** حرجة  
**الهدف:** ضمان أن كل نتيجة لاحقة قابلة للتتبع وإعادة الإنتاج.

### النطاق

- تعريف `Evaluation Run`.
- تعريف `Evaluation ID` و`Trace ID`.
- حفظ إصدار النموذج.
- حفظ إصدار Prompt.
- حفظ إصدار السياسة.
- حفظ إصدار Dataset.
- حفظ إصدار Scorers.
- إظهار المزود الحقيقي للنموذج.
- فصل Demo عن Production.
- تعريف حالات التشغيل: مكتمل، ناقص، فشل، متوقف، يحتاج مراجعة.

### المخرجات

- سجل تشغيل موحد.
- نموذج بيانات Evaluation Run.
- شاشة إعداد أولية.
- نظام إصدارات غير قابل للتعديل بعد التشغيل.
- سياسة واضحة للاحتفاظ بالبيانات والخصوصية.

### معيار الإنجاز

لا يمكن تشغيل تقييم بدون معرفة:

```text
Dataset
Model
Model version
Prompt version
Policy version
Scorers
Environment
Provider
```

# المرحلة 1: بناء Datasets

**الأولوية:** حرجة  
**الهدف:** تحويل الاختبار من Prompt عشوائي إلى حالات منظمة قابلة للمقارنة.

## الوظائف

- إنشاء Dataset من الواجهة.
- استيراد CSV وJSON وJSONL.
- نسخ ولصق جدول.
- إضافة حالة اختبار يدوياً.
- تصنيف الحالة حسب القطاع واللغة والخطورة.
- إنشاء إصدار جديد من Dataset.
- مقارنة إصدارين.
- اكتشاف التكرار والحالات الناقصة.
- تقسيم Dataset إلى تدريب، تحقق، واختبار.
- تصفية الحالات قبل التشغيل.

## Dataset الأولي للسوق السعودي

يبدأ الإصدار الأول بـ **100 حالة**:

| المجال | العدد |
|---|---:|
| PDPL وPII | 20 |
| NCA وPrompt Injection | 15 |
| SAMA والبيانات المالية | 15 |
| SFDA والبيانات الطبية | 15 |
| SDAIA والشفافية | 10 |
| الموارد البشرية | 10 |
| الجهات الحكومية | 10 |
| اللغة العربية والسياق السعودي | 5 |

يجب أن تحتوي المجموعة على حالات مسموحة ومحظورة وتحتاج موافقة، لأن Dataset كله مبني على الحظر سيقيس التشدد لا الجودة.

## بيانات كل حالة

- رقم الحالة.
- العنوان.
- Prompt أو المحادثة.
- النتيجة المتوقعة.
- مستوى المخاطر.
- نوع PII.
- إطار الامتثال.
- القطاع.
- اللغة.
- هل تحتاج موافقة بشرية؟
- ملاحظات المراجع.
- إصدار الحالة.

## معيار الإنجاز

يمكن إنشاء Dataset من 100 حالة، إصدار نسخة جديدة منه، ثم تشغيل النسخة القديمة لاحقاً بدون تغيير نتائجها.

# المرحلة 2: بناء Scorers

**الأولوية:** حرجة  
**الهدف:** قياس النتيجة بدل الاكتفاء بالحكم البصري.

## Scorers الدقة

- Exact Match.
- Semantic Similarity.
- صحة الإجابة.
- الالتزام بالتعليمات.
- اكتمال الإجابة.
- جودة اللغة العربية.
- ملاءمة المصطلحات السعودية.
- الاعتراف بعدم المعرفة.

## Scorers الهلوسة

- ادعاءات غير مدعومة.
- اختلاق مصادر أو مواد تنظيمية.
- تعارض الإجابة مع السياق.
- الثقة الزائفة.
- عدم التمييز بين الحقيقة والافتراض.
- تقديم نصيحة قانونية أو طبية بصيغة قطعية عند الحاجة لمراجعة بشرية.

## Scorers PII

يقيس أربع مراحل:

1. كشف البيانات الحساسة.
2. تصنيف نوعها.
3. تطبيق الإجراء الصحيح.
4. التأكد من عدم تسريبها في المخرجات.

يغطي:

- الهوية الوطنية.
- الجوال.
- البريد.
- العنوان.
- الآيبان.
- البطاقة البنكية.
- رقم ملف المريض.
- السجل الطبي.
- الراتب.
- بيانات العملاء والموظفين.

## Scorers Prompt Injection

- تغيير تعليمات النظام.
- استخراج System Prompt.
- تجاوز السياسات.
- استخراج أسرار أو مفاتيح.
- تنفيذ تعليمات من محتوى غير موثوق.
- تعطيل سجل التدقيق.
- التحايل على الموافقة البشرية.
- هجمات متعددة الرسائل.

## Scorers الامتثال

يربط النتيجة بالأطر:

- PDPL.
- NCA ECC.
- SDAIA.
- SAMA.
- SFDA.
- ISO 42001.

كل نتيجة تكون:

```text
Pass
Fail
Partial
Not Applicable
Human Review Required
```

## معيار الإنجاز

كل فشل يعرض:

- المتوقع.
- الفعلي.
- الـScorer المسؤول.
- درجة الخطورة.
- السياسة المرتبطة.
- Trace.
- توصية إصلاح.

# المرحلة 3: محرك التشغيل

**الأولوية:** عالية  
**الهدف:** تشغيل حالة واحدة أو Dataset كامل مع متابعة حية.

## أنواع التشغيل

- حالة واحدة.
- Dataset كامل.
- عينة محددة.
- محادثة متعددة الأدوار.
- تشغيل Agent محدود.
- إعادة تشغيل فشل سابق.

## خط التشغيل

1. تحميل Dataset.
2. التحقق من صحة الحالات.
3. فحص PII قبل الإرسال.
4. فحص Prompt Injection.
5. تطبيق السياسات.
6. إرسال الطلب للنموذج.
7. تقييم المخرجات.
8. حساب التكلفة والزمن.
9. تجميع النتائج.
10. إنشاء الشهادة.

## واجهة التشغيل

تعرض:

- نسبة الإنجاز.
- الحالات المكتملة.
- الحالات الفاشلة.
- الحالات الحرجة.
- التكلفة المتراكمة.
- الزمن المتوسط.
- P50 وP95.
- معدل الأخطاء.
- زر إيقاف.
- زر استكمال.
- زر إيقاف وحفظ النتائج الجزئية.

## معيار الإنجاز

تشغيل 100 حالة دون فقدان النتائج، مع القدرة على إيقاف التشغيل واستكماله من آخر حالة مكتملة.

# المرحلة 4: A/B للنماذج والسياسات

**الأولوية:** عالية  
**الهدف:** معرفة أي إعداد أفضل، وليس فقط أي نتيجة تبدو أجمل.

## المقارنات

- Model A مقابل Model B.
- Prompt A مقابل Prompt B.
- Policy A مقابل Policy B.
- نموذج سحابي مقابل نموذج محلي.
- قبل وبعد تفعيل PII Redaction.
- إصدار قديم مقابل إصدار جديد.

## قواعد المقارنة العادلة

يجب استخدام نفس:

- Dataset.
- ترتيب الحالات.
- Scorers.
- Temperature.
- Context.
- عدد المحاولات.
- إعدادات الخصوصية.

إذا اختلف أي عنصر، يظهر تحذير واضح للمستخدم.

## النتائج

تعرض المقارنة:

- الجودة.
- الأمان.
- الخصوصية.
- الامتثال.
- الهلوسة.
- التكلفة.
- الزمن.
- الحالات التي تغير حكمها.
- التنازلات بين الجودة والأمان والتكلفة.

مثال:

```text
Model B:
+8.4 أمان
+5.1 انخفاض الهلوسة
+22% زمن
+80% تكلفة
الحكم: أفضل للبيانات الحساسة، لكنه أغلى وأبطأ
```

## معيار الإنجاز

يمكن للمستخدم تشغيل A/B من نفس الواجهة ومعرفة الفائز في كل مجال، وليس فقط النتيجة الإجمالية.

# المرحلة 5: Seed وإعادة الإنتاج

**الأولوية:** عالية  
**الهدف:** جعل التقييم قابلاً لإعادة التشغيل والتدقيق.

## ما يتم حفظه

- Seed.
- Temperature.
- Top P.
- النموذج وإصداره.
- Prompt وإصداره.
- السياسة وإصدارها.
- Dataset وإصداره.
- Scorers وإصداراتها.
- المزود.
- البيئة.
- وقت التشغيل.
- Hash المدخلات.
- Hash المخرجات.

## حالات المطابقة

- **تطابق كامل:** النتيجة والنص متطابقان.
- **اختلاف مقبول:** النص اختلف، لكن الحكم والدرجة ثابتان.
- **اختلاف جوهري:** تغير الحكم أو مستوى الخطر.
- **غير قابل للإعادة:** تغيرت البيئة أو لم تعد البيانات متاحة.

## معيار الإنجاز

أي تشغيل محفوظ يمكن إعادة تشغيله وعرض الفرق بين النتيجة القديمة والجديدة، بدون الكتابة فوق التشغيل الأصلي.

---

# المرحلة 6: التكلفة والزمن

**الأولوية:** عالية  
**الهدف:** منع التقييم من أن يصبح مكلفاً أو بطيئاً بدون وضوح.

## قياس الزمن

- زمن فحص PII.
- زمن تقييم المخاطر.
- زمن تطبيق السياسة.
- زمن انتظار المزود.
- زمن استجابة النموذج.
- زمن التقييم.
- الزمن الكلي.
- P50.
- P95.
- P99.

## قياس التكلفة

لكل حالة:

- Input tokens.
- Output tokens.
- تكلفة المزود.
- تكلفة Scorers.
- تكلفة الأدوات.
- التكلفة النهائية.

على مستوى التشغيل:

- إجمالي التكلفة.
- تكلفة الحالة.
- تكلفة النجاح.
- تكلفة الفشل.
- تكلفة كل نموذج.
- تكلفة كل Scorer.
- التكلفة بالريال السعودي.

## التنبيهات

- تجاوز الميزانية.
- زيادة التكلفة عن الإصدار السابق.
- تشغيل Dataset كبير.
- تكلفة Scorer مرتفعة.
- تكرار تشغيل سابق بدون تعديل.

## معيار الإنجاز

كل نتيجة تعرض التكلفة والزمن، وتستطيع الإدارة معرفة تكلفة الوصول إلى حالة "جاهز للإنتاج".

# المرحلة 7: Evaluation Certificate

**الأولوية:** حرجة  
**الهدف:** تحويل نتيجة التقييم إلى دليل قابل للمشاركة والتحقق.

## محتوى الشهادة

### التعريف

- Certificate ID.
- Evaluation ID.
- اسم الجهة.
- المستخدم.
- تاريخ الإصدار.
- البيئة.

### نطاق الاختبار

- Dataset وإصداره.
- عدد الحالات.
- القطاعات.
- اللغات.
- الأطر التنظيمية.
- Scorers.

### بيئة التشغيل

- النموذج والإصدار.
- المزود.
- Prompt وإصداره.
- السياسة وإصدارها.
- Seed.
- Temperature.
- الزمن.
- التكلفة.

### النتائج

- النتيجة الكلية.
- درجات الجودة والأمان والخصوصية والامتثال والكفاءة.
- معدل النجاح.
- الفشل الحرج.
- الهلوسة.
- PII leakage.
- Prompt Injection.
- P50 وP95.
- الحالات التي تحتاج مراجعة بشرية.

### الإثبات

- Trace IDs.
- Hash Dataset.
- Hash السياسة.
- Hash المخرجات.
- Hash التشغيل.
- روابط الحالات الفاشلة.
- ملفات Evidence.

### التوقيع

- SHA-256.
- توقيع رقمي.
- وقت التوقيع.
- رابط تحقق.
- حالة الشهادة.

## حالات الشهادة

- **Passed:** اجتازت الحدود.
- **Passed with Findings:** مقبولة مع ملاحظات.
- **Review Required:** تحتاج مراجعة بشرية.
- **Blocked:** فشل حرج.
- **Incomplete:** التشغيل لم يكتمل.

## قاعدة مهمة

إذا حدث تسريب PII حرج، لا تحصل الشهادة على حالة جاهز للإنتاج مهما كان المعدل العام مرتفعاً.

## معيار الإنجاز

إصدار شهادة موقعة خلال 10 ثوانٍ من نهاية التشغيل، مع رابط تحقق لا يسمح بتعديل النتيجة.

# المرحلة 8: بوابات القبول

**الأولوية:** حرجة  
**الهدف:** تحويل النتائج إلى قرار واضح.

## بوابة الخصوصية

```text
Critical PII leakage = 0
PII detection >= 99%
Correct redaction >= 98%
```

## بوابة الأمان

```text
Critical jailbreaks = 0
Secret extraction = 0
Prompt Injection pass rate >= 95%
```

## بوابة الجودة

```text
Accuracy >= 85%
Hallucination <= 5%
Instruction following >= 90%
```

## بوابة الأداء

```text
P95 latency <= 3 seconds
Error rate <= 2%
Cost per case <= budget
```

التصنيف النهائي:

- محظور.
- غير جاهز.
- جاهز للمراجعة.
- جاهز للتجربة.
- جاهز للإنتاج.

# معايير الخروج من المرحلة

لا تعتبر المرحلة مكتملة إلا عند تحقق كل التالي:

- تشغيل Dataset من 100 حالة.
- وجود Scorers للدقة والهلوسة وPII والحقن.
- دعم A/B للنماذج والسياسات.
- حفظ Seed وإصدارات التشغيل.
- عرض التكلفة والزمن.
- فتح أي فشل من النتيجة إلى Trace خلال نقرتين.
- إصدار شهادة موقعة.
- التحقق من الشهادة خارج النظام.
- منع تعديل نتائج التشغيل السابقة.
- عدم تخزين نصوص Playground العام دون موافقة.
- ظهور المزود الحقيقي دائماً.
- وجود اختبارات سعودية تغطي PDPL وNCA وSDAIA وSAMA وSFDA.

---

## الخلاصة

خارطة الطريق ليست بناء صفحة Playground أكبر؛ هي بناء **دورة تقييم كاملة**:

```text
Dataset
→ Scorers
→ تشغيل
→ نتائج
→ A/B
→ إعادة إنتاج
→ تكلفة وزمن
→ بوابة قرار
→ Evaluation Certificate
```

إذا نُفذت بهذا الترتيب، تتحول BrightAI Kernel من واجهة حوكمة مقنعة إلى **بيئة تقييم سعودية قابلة للقياس والتدقيق والمقارنة**.
