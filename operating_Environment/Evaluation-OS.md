# Evaluation OS للسوق السعودي  
## المرحلة الأولى: **الملعب القابل للقياس**

**الهدف:** تحويل Playground من تجربة تفاعلية جميلة إلى بيئة تقييم موثوقة تقيس جودة وأمان النماذج والتطبيقات الذكية في السياق السعودي، وتنتج نتيجة قابلة لإعادة التشغيل والمقارنة والتدقيق.

هذه المرحلة هي الأساس؛ بدونها ستبقى صفحات Red Team والتقارير مجرد واجهة مقنعة بلا دليل قابل للقياس.

---

## 1. النتيجة المستهدفة

بنهاية المرحلة، يستطيع المستخدم:

1. إدخال Prompt أو محادثة أو سيناريو متعدد الأدوار.
2. اختيار نموذج أو أكثر للمقارنة.
3. اختيار مجموعة اختبارات جاهزة أو بناء مجموعة مخصصة.
4. تشغيل التقييم على نص واحد أو عشرات الحالات دفعة واحدة.
5. قياس الجودة، الأمان، الخصوصية، الامتثال، التكلفة، والزمن.
6. مقارنة نموذجين أو نسختين من Prompt أو سياسة.
7. معرفة سبب نجاح أو فشل كل حالة.
8. إعادة تشغيل نفس التقييم بنفس الإصدارات والـseed.
9. إصدار **Evaluation Certificate** يحتوي على النتيجة والأدلة والـhash.

---

# 2. نطاق المرحلة

## 2.1 المدخلات

يجب أن يدعم الملعب أربعة أنواع من المدخلات:

**اختبار منفرد:** Prompt واحد مع إعدادات النموذج والسياسة.

**مجموعة اختبارات:** ملف JSON أو CSV أو جدول داخلي يحتوي على:

- `case_id`
- `input`
- `expected_output` اختياري
- `context`
- `risk_level`
- `compliance_tags`
- `department`
- `language`
- `sensitive_data`
- `metadata`

**محادثة متعددة الأدوار:** سلسلة رسائل متتابعة لاختبار الذاكرة، التصعيد، التناقض، ومحاولات الالتفاف.

**اختبار Agent:** مدخل + أدوات مسموحة + شروط تنفيذ + نقطة توقف بشرية، حتى لا يقتصر التقييم على إجابة نصية فقط.

---

## 2.2 إعداد التقييم

قبل التشغيل، يظهر للمستخدم نموذج إعداد واضح:

**النموذج:** Groq أو OpenAI أو Azure أو Anthropic أو نموذج محلي.

**إصدار النموذج:** يجب حفظ الاسم والإصدار، وليس الاسم العام فقط.

**نسخة Prompt:** رقم إصدار أو hash.

**نسخة السياسة:** السياسات المفعّلة وقت التقييم.

**القطاع:** بنوك، صحة، حكومة، اتصالات، تعليم، موارد بشرية، قانوني.

**الإطار التنظيمي:** PDPL، NCA ECC، SDAIA، SAMA، SFDA، ISO 42001.

**وضع التشغيل:** سحابي، محلي، أو Hybrid.

**Seed:** قيمة اختيارية لإعادة التشغيل والمقارنة.

**درجة العشوائية:** Temperature وTop P عند توفرها.

**حجم التشغيل:** تجربة واحدة، عينة، أو المجموعة كاملة.

يجب منع تشغيل التقييم قبل عرض ملخص واضح: **ما الذي سيُختبر، بأي نموذج، بأي سياسة، وبأي تكلفة تقديرية.**

# 3. محركات التقييم الأساسية

## 3.1 تقييم الجودة

يشمل:

- صحة الإجابة.
- الصلة بالسؤال.
- اكتمال الإجابة.
- الالتزام بالتعليمات.
- وضوح اللغة العربية.
- جودة اللهجة والسياق السعودي عند الحاجة.
- عدم اختلاق مصادر أو أنظمة أو مواد تنظيمية.
- الالتزام بتنسيق الإخراج المطلوب.

## 3.2 تقييم الأمان

يشمل:

- Prompt Injection.
- Jailbreak.
- استخراج System Prompt.
- استخراج مفاتيح API أو أسرار.
- SQL Injection.
- تجاوز الصلاحيات.
- تنفيذ أداة غير مصرح بها.
- التلاعب بسياق المحادثة.
- تسريب بيانات مستخدم آخر.
- التحايل على الموافقات البشرية.

## 3.3 تقييم الخصوصية

يشمل كشف:

- رقم الهوية الوطنية.
- رقم الجوال.
- البريد الإلكتروني.
- العنوان.
- رقم الآيبان.
- بيانات البطاقة البنكية.
- أرقام ملفات المرضى.
- السجلات الطبية.
- الرواتب.
- بيانات الموظفين والعملاء.

ويقيّم النظام في أربع حالات:

1. هل اكتشف البيانات؟
2. هل صنّفها بشكل صحيح؟
3. هل عمّاها أو حظرها؟
4. هل منع ظهورها في المخرجات؟

## 3.4 تقييم الامتثال السعودي

يجب ألا يعرض النظام عبارة عامة مثل "متوافق"، بل يربط كل نتيجة بضابط أو مادة محددة:

- **PDPL:** حماية البيانات الشخصية، الغرض من المعالجة، مشاركة البيانات، تقليل البيانات.
- **NCA ECC:** التحكم في الوصول، حماية البيانات، التسجيل والمراقبة، الاستجابة للحوادث.
- **SDAIA:** الشفافية، المساءلة، الخصوصية، الأمان، الإشراف البشري.
- **SAMA:** البيانات المالية والقرارات الائتمانية والرقابة البشرية.
- **SFDA:** البيانات الطبية، التشخيص، المرضى، والمراجعة البشرية.
- **ISO 42001:** إدارة المخاطر، السجلات، الأدوار، والتحسين المستمر.

النتيجة تكون: **ناجح، فشل، غير قابل للتقييم، أو يحتاج مراجعة بشرية**.

# 4. درجات التقييم

لا يكفي رقم واحد مثل 83%. يجب تقسيم النتيجة إلى خمس درجات:

| المجال | النتيجة |
|---|---:|
| الجودة | 0-100 |
| الأمان | 0-100 |
| الخصوصية | 0-100 |
| الامتثال | 0-100 |
| الكفاءة والتكلفة | 0-100 |

ثم تُحسب النتيجة الكلية، مع منع التجميل الحسابي:

- فشل حرج في PII يمنع الحصول على تصنيف "جاهز".
- نجاح الجودة لا يعوّض فشل الأمن.
- وجود خرق واحد لبيانات حساسة يظهر بوضوح حتى لو كانت النتيجة الكلية مرتفعة.
- يجب عرض **أسوأ نتيجة حرجة** بجانب المتوسط.

التصنيف النهائي:

- **محظور:** خرق أمني أو خصوصية حرج.
- **غير جاهز:** فشل في حد أدنى من الاختبارات.
- **جاهز للمراجعة:** النتائج مقبولة لكن تحتاج اعتماداً بشرياً.
- **جاهز للتجربة:** مناسب لبيئة تجريبية.
- **جاهز للإنتاج:** تجاوز جميع البوابات المطلوبة.

# 5. واجهة الملعب

## 5.1 لوحة الإدخال

تتضمن:

- مربع Prompt أو محادثة.
- اختيار مجموعة الاختبار.
- اختيار النموذج.
- اختيار السياسة.
- اختيار القطاع.
- اختيار حزمة الامتثال.
- عينات سعودية جاهزة.
- تحذير واضح: **لا تستخدم بيانات إنتاج حقيقية**.
- مؤشر عدد الحالات والتكلفة المتوقعة.

## 5.2 خط التنفيذ

يعرض المراحل بالترتيب:

1. استقبال الطلب.
2. فحص PII.
3. فحص الهجمات.
4. تقييم المخاطر.
5. مطابقة السياسات.
6. إرسال النموذج.
7. تقييم المخرجات.
8. إصدار النتيجة والدليل.

كل مرحلة تعرض:

- الحالة.
- الزمن.
- سبب القرار.
- البيانات التي دخلت وخرجت.
- Trace ID.
- السياسة أو المقياس المسؤول عن النتيجة.

## 5.3 لوحة النتائج

تعرض:

- الدرجة الكلية.
- درجات المجالات الخمسة.
- عدد الحالات الناجحة والفاشلة.
- الاختبارات الحرجة.
- التكلفة.
- الزمن المتوسط.
- أعلى أسباب الفشل.
- مقارنة بالإصدار السابق.
- زر إعادة التشغيل.
- زر فتح Trace.
- زر إصدار الشهادة.

---

# 6. المقارنة A/B

يجب أن يقارن المستخدم بين:

- نموذجين.
- نسختين من Prompt.
- سياستين.
- إعدادين للـTemperature.
- نموذج سحابي ونموذج محلي.
- تشغيل قبل وبعد تعديل الحماية.

تظهر المقارنة في جدول موحد:

| المؤشر | الإصدار A | الإصدار B | الفرق |
|---|---:|---:|---:|
| الجودة | 82 | 88 | +6 |
| تسريب PII | 3 | 0 | تحسن |
| Prompt Injection | 91% | 97% | +6 |
| الزمن | 1.8s | 2.4s | تراجع |
| التكلفة | 0.08 ريال | 0.14 ريال | +0.06 |
| الامتثال | 76 | 94 | +18 |

يجب تمييز **التحسن الذي جاء على حساب شيء آخر**، مثلاً: النموذج الجديد أكثر أماناً لكنه أبطأ أو أغلى.

---

# 7. إعادة الإنتاج والتدقيق

كل تشغيل يحصل على هوية كاملة:

- Evaluation ID.
- Trace ID.
- إصدار النموذج.
- إصدار Prompt.
- إصدار السياسة.
- نسخة dataset.
- Seed.
- Temperature.
- وقت التشغيل.
- المستخدم.
- البيئة.
- الـProvider.
- الـhash.

عند إعادة التشغيل، يعرض النظام:

**هل النتيجة قابلة لإعادة الإنتاج؟**

- تطابق كامل.
- اختلاف مقبول.
- اختلاف جوهري.
- لا يمكن التحقق.

لا يسمح النظام بتعديل نتيجة قديمة؛ أي تعديل ينشئ **نسخة تقييم جديدة** مرتبطة بالأصل.

---

# 8. Evaluation Certificate

بعد انتهاء التشغيل، يولّد النظام شهادة قابلة للتحميل والمشاركة تحتوي على:

- اسم التقييم.
- تاريخ التشغيل.
- نطاق التقييم.
- النموذج والإصدار.
- Prompt والسياسة.
- عدد حالات الاختبار.
- المقاييس المستخدمة.
- النتائج التفصيلية.
- حالات الفشل.
- المخاطر الحرجة.
- التكلفة والزمن.
- Trace IDs.
- hash التشغيل.
- توقيع رقمي.
- عبارة واضحة عن حدود الشهادة.

الشهادة لا تقول فقط "النموذج آمن"، بل تقول مثلاً:

> اجتاز النموذج 96 من أصل 100 اختبار، وفشل في 3 اختبارات Prompt Injection، وظهر فشل حرج واحد في تعمية رقم الآيبان. غير جاهز للإنتاج حتى معالجة الخلل وإعادة التقييم.

---

# 9. مجموعة الاختبارات السعودية الأولية

تبدأ المرحلة الأولى بمكتبة لا تقل عن **100 حالة**:

- 20 حالة PDPL وPII.
- 15 حالة NCA وPrompt Injection.
- 15 حالة مالية وSAMA.
- 15 حالة طبية وSFDA.
- 10 حالات SDAIA وشفافية المخرجات.
- 10 حالات موارد بشرية.
- 10 حالات حكومية.
- 5 حالات عربية ولهجات وصياغات محلية.

كل حالة لها:

- هدف واضح.
- النتيجة المتوقعة.
- مستوى الخطورة.
- الإطار التنظيمي.
- سبب النجاح أو الفشل.
- طريقة التقييم.
- سياسة مرتبطة بها.

يجب أن تشمل البيانات حالات **مسموحة** أيضاً، لأن النظام الذي يحظر كل شيء ليس نظاماً آمناً، بل نظاماً عديم الفائدة.

---

# 10. بوابات القبول

لا ينتقل المنتج للمرحلة الثانية حتى يحقق:

- 100% كشف وحظر للحالات الحرجة المعروفة.
- صفر تسريب لبيانات PII في المخرجات التجريبية.
- 95% على الأقل في اختبارات تصنيف المخاطر.
- 90% على الأقل في ربط النتائج بالإطار التنظيمي الصحيح.
- إعادة تشغيل موثوقة لكل تقييم محفوظ.
- إصدار شهادة قابلة للتحقق.
- مقارنة A/B تعمل بدون فقدان الإصدارات.
- ظهور التكلفة والزمن لكل تشغيل.
- عدم تخزين نصوص المستخدمين في وضع Playground العام.
- إظهار المزوّد الحقيقي بدلاً من ادعاء غير دقيق.

---

# 11. ما لا يدخل في المرحلة الأولى

حتى لا تتضخم المرحلة:

- لا يدخل Red Team التكيفي الكامل.
- لا تدخل مراقبة الإنتاج المستمرة.
- لا يدخل التكامل الكامل مع GitHub Actions.
- لا يدخل تقييم بشري جماعي متقدم.
- لا يدخل دعم كل الأطر التنظيمية العالمية.
- لا تدخل أدوات Agent المعقدة بكاملها.

هذه تأتي لاحقاً بعد تثبيت نظام القياس الأساسي.

---

# 12. مؤشرات نجاح المرحلة

**مؤشرات المنتج:**

- الوقت من إدخال الاختبار إلى النتيجة أقل من 60 ثانية للعينة الصغيرة.
- تشغيل 100 حالة بدون انهيار أو فقدان نتائج.
- إنشاء شهادة خلال 10 ثوانٍ من انتهاء التقييم.
- فتح أي فشل من النتيجة إلى Trace خلال نقرتين.
- تشغيل مقارنة A/B خلال مسار واحد واضح.

**مؤشرات تجربة المستخدم:**

- المستخدم الجديد يفهم النتيجة خلال 30 ثانية.
- يستطيع تشغيل أول تقييم خلال 3 دقائق.
- يعرف لماذا فشل الاختبار دون قراءة وثائق خارجية.
- لا يخلط بين جودة النموذج وأمانه.
- يستطيع مشاركة النتيجة مع مدير أو مدقق بدون شرح شفهي طويل.

---

## الخلاصة

المرحلة الأولى ليست بناء شاشة Playground فقط؛ هي بناء **مصدر الحقيقة لتقييم الذكاء الاصطناعي**. يجب أن تخرج منها ثلاث نتائج لا يمكن التنازل عنها: **درجة قابلة للتفسير، تشغيل قابل لإعادة الإنتاج، وشهادة قابلة للتحقق**.
