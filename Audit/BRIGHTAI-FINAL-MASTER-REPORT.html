00 — تعريف مشروع BRIGHT AI والتمييز بين ما هو مستهدف وما هو مطبق

BRIGHT AI هي العلامة المؤسسية لـمؤسسة مُشرقة، وAIGAS تخصصها في حوكمة وأمان الذكاء الاصطناعي. تحتوي المنظومة على AIGAS Kernel (الطبقة المشتركة غير المرخصة منفصلًا) وعلى خمسة منتجات مستقلة: Firewall وLedger وHuman Gate وRisk Engine وSecure Chat. يجب أن تحتفظ المنتجات بحدود تجارية ووظيفية مستقلة: تسجيل الأمان الأدنى في Kernel لا يتوقف على ترخيص Ledger، وضوابط Secure Chat الأساسية لا تتوقف على شراء Firewall، وربط المنتجات الأخرى إضافة اختيارية لا إكراه وظيفي.

المرجع الأعلى للمتطلبات المستهدفة هو docs/MASTER-PROJECT-BLUEPRINT.md مع مستندات docs/products/* الستة لكل منتج. الوثيقة المعتمدة تشرح المطلوب، ولا تثبت تشغيله. مصدر الحالة التقنية هو الكود في commit المحدد، ومصدر وجود الجداول هو Neon. لا تعتبر الأدلة المحلية القديمة أو WORKING داخل ملف حالة بديلًا عن إثبات تشغيل في الإصدار المنشور.

02 — منهج الدليل وحدوده

التصنيفات الأربعة التي يُمنع دمجها

  • APPROVED_REQUIREMENT: قرار/سياسة أو منتج مستهدف داخل Blueprint أو Product Spec؛ ليس تنفيذًا.
  • SOURCE_IMPLEMENTED: كود/صفحة/API/ترحيل موجودة في commit محدد، مع حدود تدل عليها المراجعة؛ ليس تنفيذًا منشورًا.
  • SCHEMA_PRESENT: جدول/قيد/فهرس موجود في Neon؛ ليس دليل أن المستخدم أتم إجراء.
  • RUNTIME_VERIFIED: تسجيل دخول مفوّض ومشاهدات متماسكة على إصدار منشور محدد، مع أثر قرار في قاعدة معزولة؛ غير مثبت في هذا التقرير.

المستندات المرجعية الحديثة التي فُحصت تميز غالبًا بين التنفيذ المحلي والحالة NOT_VERIFIED، لكن بعضها يحمل وصف APPROVED في عنوان «حالة التشغيل» رغم أن متنه ينفي إثبات الإتاحة؛ ينبغي حسم طريقة استعمال العلامات القانونية والتسويقية دون إعادة كتابة التاريخ أو الادعاء بإطلاق سابق.

حدود الفحص

لم أستخدم بيانات عملاء حقيقية، ولم أُنشئ مستخدمًا أو مؤسسة أو سياسة، ولم أرسل رسالة إلى نموذج AI، ولم أنفذ طلب موافقة أو تعديل بيانات في Neon. كذلك لم أقم بتشغيل Build أو اختبارات أو فحص اختراق. ظهرت ملفات Audit/* محلية في المستودع تشير إلى نتائج سابقة، لكنها أدلة مؤرخة لظروفها وليست شهادة التشغيل الحالي. فحص المتصفح المباشر لجميع مسارات /app/ أعاد 404 ولم يثبت نجاح الدخول أو التشغيل؛ لذلك كل نتيجة تشغيلية هنا لا تتجاوز حدود المصدر.

03 — طبقات المشروع ومكوناته الفعلية

03.1 Web / Marketing / Knowledge

  • الإطار: Astro 6، إعداد output:'server' و@astrojs/node standalone، trailingSlash:'always' وSitemap يرفض فهرسة /app/* و/auth/* و/kernel/ وغيرها من الصفحات الخاصة أو التوضيحية.
  • الهوية: عربية RTL، مظهر داكن، بنفسجي #8052FF، أصفر #FFB829، أخضر #15846E في موضعه. الهيرو المتحرك وConstellation والهيدر والشعار محمية بقرارات المالك السابقة.
  • الصفحات: الرئيسية، كتالوج /products/، خمس صفحات المنتجات، /kernel/ التوضيحية، أربع صفحات قطاعات، ثلاث ركائز، الخدمات، الأسعار، التواصل، الثقة، الامتثال، من نحن، الخصوصية والشروط، 404.
  • المعرفة: /docs/ و11 مقالة تحت /knowledge/. كود Command Center (knowledge-center.ts, KnowledgeReader.astro, src/server/knowledge) يدعم تصنيفات وفلاتر وبحثًا ومعاينة وقراءة وبنية FAQ؛ هذه ميزات مصدرية، مع ظهور فهرس 11 دليلًا في الويب العام.
  • ملاحظة محتوى: صفحة /docs/ تربط Firewall بثلاثة أدلة وHuman Gate بثلاثة وRisk Engine بدليلين وSecure Chat بدليلين، وتعرض 0 رابطًا مباشرًا لـKernel وLedger؛ لا تعوض ذلك بروابط مخترعة. المحتوى تعليمي ولا يثبت امتثالًا أو تشغيل API.
  • التصميم والحركة: لدى المشروع CSS Tokens وحركة داخلية ورسوم SVG وحالات تطبيق؛ التنفيذ الأخير لم يُثبت على كل أحجام الشاشات في هذه المراجعة. الخطة السابقة لتحسين الحركة ليست تصريحًا بتغيير هيرو الرئيسية ولا بمحو نصوصها.

03.2 Kernel / Identity / Data

  • مسارات /app/ و/app/kernel/ وواجهات /app/api/kernel* موجودة في المصدر، مع Services للهوية، العضويات، منح المنتجات، السياسات، الأحداث والتفويض.
  • src/server/kernel/auth.mjs يتحقق من Bearer/JWKS وissuer والخوارزمية المصرح بها؛ لا يمثل هذا وحده إثبات تدفق تسجيل دخول كامل أو قدرة على تسجيل موظف حقيقي.
  • src/server/kernel/access.mjs يميز حقوق ADMIN_NON_BILLED عن Trial/Subscription/Perpetual؛ لا يوجد نظام ترخيص تجاري نهائي مُثبت.
  • توجد بنية سياسات متدرجة، إصدارات وموافقات وتفويضات وأحداث؛ كلها فارغة في Neon المفحوصة.
  • الـtenant وdepartment وproduct وuser مستويات مطلوبة للعزل والسياسة؛ التحقق الحقيقي من وراثة الأولويات/الرفض الإلزامي/الأحداث المؤسسية لم يُنفذ في هذا الفحص.

03.3 مسار النشر

  • astro.config.mjs يحدد خادم Node SSR. package.json يحتوي start: node ./dist/server/entry.mjs، وrender.yaml يصف Node web service مع أمر npm ci && npm run build وnpm start.
  • الحقيقة المعيقة: render.yaml يضبط AIGAS_APP_ENABLED على false عمدًا إلى أن يوافق المشغل، وتعليق التكوين يوضح ضرورة تحويل الدومين إلى خادم Node بدل خدمة static. src/middleware.ts يعيد 503 APP_UNAVAILABLE للـAPI عندما تكون البوابة معطلة. Browser Use أعاد HTTP 404 على /app/ وكل صفحات المنتجات الخمسة، وليست شاشة دخول؛ هذا يثبت عدم إتاحتها على الواجهة العامة حاليًا، لكنه لا يثبت وحده أي طبقة/أصل استضافة سبب الخطأ.
  • لا تغيّر إعداد الخدمة الحية أو الدومين أو أسرارها بناءً على هذا التقرير وحده. المطلوب أولًا تطابق artifact وorigin وfeature flag في نشر مصرح.

04 — مراجعة تفصيلية للمنتجات الخمسة

المنتج ما ظهر في الكود ما ظهر في Neon ما لم يثبت بعد أولوية الإغلاق
Firewall قواعد وسياسات، تقييم، guarded execution، provider registry، escalation و5-state upgrade aigas_fw_rules, aigas_fw_decisions (فارغان) مرور طلب AI حقيقي عبر نقطة إنفاذ مُعتمدة، نتائج حظر/تنقيح مع مزود، حزم أدلة تشغيلية P0 قبل بيع الحماية
Ledger Writer، chain/digest، التحقق، التصدير، verifier منفصل في public/downloads aigas_ld_events, aigas_ld_evidence_requirements (فارغان) حدث تشغيل حقيقي، تحقق مستقل موثق بعد العبث، توقيعات/حفظ طويل متقدم P0 إذا يُباع كأدلة
Human Gate الطلبات والقرارات، الإلغاء، تفويض محدود، grants وإنفاذ مرة واحدة aigas_hg_requests/decisions/events/policies (فارغة) مراجع حقيقي مستقل، حالة عدم الرد/التوازي، تنفيذ خاضع لموافقة على أصل محدد P0 قبل تمكين موافقات حساسة
Risk Engine سجل الأصول والإصدارات، تقييمات سياقية ومعالجة ومخاطر متبقية وتصدير aigas_re_assets/assessments/asset_revisions/treatment_revisions (فارغة) تفسير نتيجة مع أصل حقيقي اصطناعي، اعتماد منهج المخاطر وحواجز التشغيل P1 لنسخة مستهدفة
Secure Chat سياسة synthetic-only، registry للنماذج، adapter، حدود استهلاك وطلب وإلغاء aigas_sc_conversations/messages/requests/cancellations (فارغة) لا نموذج معتمد؛ لا محادثة AI تشغيلية مُثبتة؛ قرار الاحتفاظ والموافقة P0 قبل أي إطلاق Chat

04.1 Firewall

  • المتاح في الكود: تقييم سياسة مسار محدد، بيانات قرار ومصدر rule، تصعيد Human Gate وحماية من تجاوز القرار في guard.mjs/binding.mjs وفق المصدر.
  • شرط الإطلاق الحقيقي: إثبات أن الطلب لا يمكن أن يتخطى نقطة التقييم، وأن BLOCK يمنع الاستدعاء الخارجي، وأن REDACT يرسل النص المنقح فقط، وأن فشل السياسة/التدقيق الإلزامي يوقف الإرسال عند وجوبه.
  • عائق خارجي: لا يوجد ما يثبت موافقة Provider أو نشر Gateway لكل تدفقات المستخدم؛ وجود endpoint لا يعني حماية كل تطبيقات AI.

04.2 Ledger

  • المتاح في الكود: تسجيل أدلة metadata، رابط تسلسلي، Digest وتصدير/تحقق مستقل داخل حدود نموذج الأدلة المحلي.
  • حدود الأمان: SHA-256 وربط سجل لا يساوي WORM أو توقيعًا مستقلًا أو حصانة كاملة ضد مسؤول قاعدة البيانات؛ لا تُعلن سلامة مطلقة أو إثباتًا قانونيًا دون بنية وموافقات.
  • شرط الإطلاق: عزل المؤسسة، تسلسل غير قابل للتجاوز بعمليات متزامنة، idempotency, سياسة احتفاظ معتمدة، ومخرجات تحقق يمكن إعادة إنتاجها دون أسرار.

04.3 Human Gate

  • المتاح في الكود: إنشاء طلب ومراجعة/رفض/إلغاء، صلاحية زمنية وتفويض محدود ومنع اعتماد ذاتي، إصدار تصريح مستخدم واحد/عملية واحدة في نطاق ضيق.
  • الشرط الحاسم: يجب إعادة فحص نطاق الطلب وهوية المراجع والحالة ونسخة السياسة وقت التنفيذ، لا وقت الضغط فقط. لا موافقة صامتة عند انتهاء المهلة أو إعادة استعمال تصريح.
  • مؤجل لا يمنع الإفراج عن نطاق صغير: محرك workflow عام وقنوات تنبيه متعددة وموافقات رسمية متعددة إذا لم تكن ضمن العقد التجاري الأول.

04.4 Risk Engine

  • المتاح في الكود: سجل أصول ونسخ وتقييم likelihood/impact، سياق بيانات/مزود، علاج/قبول مخاطر والتصدير.
  • قيد صدق المنتج: المنهج الحالي Draft يعتمد قواعد محددة؛ لا يثبت معيار ISO/IEC 42001، ولا يبرر نشر نموذج تلقائيًا، ولا توجد درجة مخاطر 0–100 معتمدة.
  • الأولوية: إيضاح المدخلات، إدارة نسخ الأصل، تفسير الأثر والاحتمال، القبول بدور مفوض وسجل المعالجة دون حذف التاريخ.

04.5 Secure Chat

  • المتاح في الكود: واجهة محادثة، تحقق من هوية المؤسسة والمنتج، Adapter مقيد بـHTTPS وChat Completions، Limits/Quota وبعض ضوابط Synthetic-only.
  • حقيقة فاصلة: APPROVED_MODELS=[] حاليًا؛ NO_APPROVED_MODEL أو PROVIDER_NOT_CONFIGURED حظر سليم، وليس عيبًا يجب الالتفاف عليه. لا تطلب من الوكيل إضافة GPT أو مفتاح أو منطقة معالجة من دون اعتماد موثق.
  • الشرط: سياسة حفظ الرسائل، عدم قدرة المسؤول على قراءتها افتراضيًا، منع تسربها إلى Audit/Analytics، ضوابط مزود تمنع التدريب، وعدم تفعيل مشاركة عامة/رفع ملفات/RAG قبل تحديد نطاق مستقل.

05 — Neon / PostgreSQL: تحليل بنيوي وأمني

05.2 تحليل RLS / الصلاحيات

  • 31/31 جداول مفعّل عليها RLS.
  • توجد سياستان مباشرتان فقط على aigas_sc_requests وaigas_sc_cancellations، تشترطان أن يساوي tenant_id وuser_id متغيري جلسة PostgreSQL aigas.sc_tenant_id/aigas.sc_user_id.
  • 29 جدولًا لا تملك سياسات pg_policies مباشرة؛ مستخدم خاضع لـRLS يرى عادة منعًا افتراضيًا للعمليات، لكن مالك الجدول أو دور BYPASSRLS لا يخضع له بنفس الطريقة.
  • دور authenticated لديه GRANT للقراءة والإضافة والتعديل والحذف على الجداول الـ31، لكنه rolbypassrls=false. دور neondb_owner لديه rolbypassrls=true. هذا يستدعي مراجعة منفصلة لمسار Data API (public schema)، وصلاحية تغيير GUCs، وعزل service role وطريقة استخدام الاتصال الإداري.
  • لا يمكن الاستنتاج من هذه البيانات وحدها أن هناك وصولًا عابرًا للمؤسسات أو أن كل الجداول مكشوفة؛ يلزم فصل فعلي لامتيازات الـData API والـBackend وإنفاذ سياسة المؤسسة. على الجانب الآخر لا يجوز اعتبار اسم RLS ENABLED شهادة عزل كافية.
  • NEON Auth موجود تقنيًا؛ عدد المستخدمين والجلسات والمنظمات والعضويات داخله صفر. هذا يحد بشدة من إمكانية وصف دورة الحسابات بأنها مثبتة.

05.3 الجاهزية التشغيلية لقاعدة البيانات

  • فرع واحد اسمه production وهو الفرع الأساسي غير المحمي وقت الفحص؛ ليس هناك فرع staging مستقل أو دليل نسخ واستعادة تم التحقق منه ضمن ما توفّر.
  • مستندات الترحيل 0001–0017 موجودة، لكن مقارنة الشيفرة بالبنية الفعلية والقيود ليست مساوية لتتبع سجل ترحيل منشور؛ يجب تحديد جدول migration history مع تاريخ/Checksum/actor لعدم الاختلاط.
  • Data API فعّالة، والتخزين S3-compatible مفعّل لكن Buckets = 0. لا تعتبر ذلك تحقيقًا فعليًا لاستراتيجية ملفات العملاء أو backup.
  • قاعدة البيانات لم تسجل طلبات تشغيل في الجداول الخاصة بالمشروع، ولا يوجد ما يثبت قدرة الاستعادة أو Disaster Recovery أو صلاحيات Operator البديلة.

07 — تجربة الاستخدام والتصميم والمحتوى والـSEO

07.1 الموقع العام

الموقع يوصل هوية العلامة ويشرح المنتجات والمبادئ، ويصرح في الصفحة الرئيسية أن المنتجات تصورات غير متحققة تشغيليًا. يجب الحفاظ على هذا الإفصاح حتى تثبت إتاحة خدمة محددة، مع تنسيق مؤسسي واضح لا يربك الزائر بين Public Demo وبين /app/.

المرجعية البصرية المحددة للمالك: الهيرو المتحرك وConstellation والهيدر لا تُغيّر، ونصوص الأقسام وترتيبها وأماكنها محفوظة. التحسينات المسموحة موجهة لبطاقات المحتوى والـTypography والألوان والأيقونات والمسافات الداخلية والـMicro-motion. لا تُطلق إعادة تصميم عامة تحت عنوان «تحسين كل شيء».

07.2 مركز المعرفة

/docs/ متاح ويعرض 11 دليلًا مع حقل بحث وتصنيفات ومعاينة وملاحظات تعليمية، كما يشرح روابط المقالات بالمنتجات ويصرح بأن التصنيف لا يعني توثيق API. هذا تقدم نوعي عن مركز صفحات ثابت، لكن هناك فجوة تغطية مباشرة لـKernel وLedger (صفر روابط مقالات)، وينبغي التمييز بين وجود قصة تعليمية عن هذين المنتجين وبين وجود وثيقة API تشغيلية مُعتمدة.

آخر تغيير في commit المصدر أعاد بناء Command Center من صفحات المقالات نفسها بدل فهرسة نتائج مخترعة. يوجد KnowledgeReader, كتالوج، فلاتر URL، وملفات Audit/knowledge-command-center/ التي تصف تحققًا محليًا. هذه الأدلة لا تغني عن مراجعة نشر وتوافق مستقلين.

07.3 SEO والبحث والتحويل التجاري

لاحظ الفحص البصري الحالي تعارضًا بين خريطتي موقع منشورتين: /sitemap-0.xml تبدو مطابقة للصفحات الحالية، بينما /sitemap.xml تعرض شجرة أوسع قديمة. كذلك /knowledge/ ليس فهرسًا ويعيد HTTP 404 بينما /docs/ هو فهرس المعرفة الصحيح؛ ينبغي إزالة الروابط والفهرسة المضللة أو توحيد التوجيهات وفق قرار SEO. لا تظهر في هذه المراجعة بيانات Google Search Console أو GA4 فعلية تقيس مرات الظهور أو CTR أو التحويل؛ فلا يمكن تحديد سبب ضعف زيارات السعودية بصورة كمية أو إعلان نجاح SEO. المطلوب: ربط بيانات التحليل المصرح بها، والتحقق من Canonicals وStructured Data وSitemap، ووضع مقاييس زيارات فعلية بحسب صفحات المنتجات والبحث العربي، مع حماية بيانات مستخدمي /app/ من Analytics.

لا تنشر شهادات/شركات عميلة/تقييمات أو أسعارًا وأرقام أداء مختلقة. يجب أن يطابق CTA الذي يفتح البريد mailto: الوظيفة الحقيقية، وأن يبين متى يكون طلب التجربة بحاجة إلى موافقة بشرية.

07.4 إمكانية الوصول والأداء

أعطِ الأولوية للقراءة العربية في RTL وbdi للأرقام/الأكواد، التباين والـfocus وprefers-reduced-motion. Browser Use على 390px لم يجد قصًّا أفقيًا مستمرًا بعد اكتمال التحميل، لكنه رصد توسعًا انتقاليًا إلى عرض 777px لمدة قصيرة في /products/ و/products/firewall/ عند بداية الحركة، ثم عودة للعرض الصحيح؛ يجب علاج تحول عنصر الحركة المسبب. خطوط عربية رفيعة بحجم 13–14px تستحق تحسين القراءة. لم يثبت التقرير الجديد استمرار تغطية فهرس «داخل الصفحة» للنص بعد اكتمال التحميل، فلا تتعامل معها كخلل باقٍ مثبت. جداول التطبيق تحتاج Empty/Loading/Error/Pending وفرقًا بين حالة المنتج ومجرد عرض معلومات عنه. لا تُخترع أرقام أداء أو Lighthouse Scores.

08 — الشؤون التجارية والتشغيل والتكامل المؤسسي

  • البيع: خمسة منتجات قابلة للترخيص منفردة، وKernel مكوّن تقني إلزامي بلا رسم منفصل؛ التسعير المعتمد كاتجاه يستهدف اشتراكًا/ترخيصًا/حد استهلاك، لا توجد أسعار نهائية مثبتة.
  • تجربة Proof of Value: 48 ساعة من التفعيل الفعلي للمؤسسة المؤهلة، لا تبدأ من إرسال الطلب أو الضغط على زر، ولا تحويل تلقائي مدفوع، ومع تقرير تنفيذي وتقني ومسار خروج بيانات واضح. النصوص التجارية مُستهدفة؛ محرك التفعيل والدفع والفوترة التجارية ليس مثبتًا.
  • التشغيل: التصميم المستهدف SaaS وOn-Premise وAir-Gapped، لكن ليس كل مخطط مرجعي دليل حزمة مُثبتة لكل بيئة؛ خصوصًا الرخص offline والمفاتيح وإدارة التحديث/التراجع.
  • المزودون والتكاملات: Provider-agnostic وAPI/SDK ومداخل MCP/A2A ضمن خارطة هدف، لكن لا تسوّق تكاملًا أو Schema تصوريًا كخدمة منشورة أو معتمدة.
  • المصادقة: SSO/MFA وأدوار قابلة للتخصيص استراتيجية، لكن تنفيذ Neon Auth الحالي لا يثبت تهيئة جميع مزودي الهوية المؤسسية.
  • الالتزام التنظيمي: PDPL، الأطر السعودية ذات الصلة، ISO/IEC 42001 وNIST AI RMF ضوابط ومراجع مستهدفة. لا توجد في الأدلة المعروضة شهادة أو تقرير اعتماد قانوني/تنظيمي يغطي تشغيل كل المنتجات. يحتاج نصوصًا متخصصة واعتماد مالك شؤون الامتثال حسب نوع العميل.
  • الدعم: لا SLA ملزم ولا إجراءات حادث/خروج بيانات/نسخ احتياطي/DR موثقة كخدمة منفذة، بناءً على الأدلة التي توفرت لهذه المراجعة.

09 — مسارات الإطلاق الأربعة: ما ينبغي أن يبقى منفصلًا

  1. إطلاق المحتوى العام: موقع تسويقي ومعرفة توعوية؛ يمكن أن يكون متاحًا قبل المنتجات، مع إفصاحات دقيقة وضوابط تحرير وSEO.
  2. إطلاق بوابة إدارة المؤسسة: يحتاج نشر SSR وهوية وTenant Guard وعضوية وجداول وأمن مفوض؛ ليس معناه أن المنتجات الخمسة جاهزة.
  3. إطلاق منتج واحد بنطاق محدود: يحتاج إثبات وظيفة محددة وData Protection وProvider/Quota عند الحاجة، وتصريح إتاحة لهذا المنتج دون بقية المنتجات.
  4. إطلاق تجاري مؤسسي: يحتاج تجارب/عقود/تراخيص/فواتير/بيانات عملاء ودعم وحوادث واتفاقيات، مع موافقات إطلاق مستقلة؛ لا تُخلط الخطوات السابقة به.

10 — أولويات الإغلاق قبل الإطلاق

P0 — وقف أي إطلاق مؤسسي قبل إغلاقها

  1. حسم مكان تقديم بوابة /app/ وقرار AIGAS_APP_ENABLED ومصدر الـNode service، مع منع تسرب المحتوى الخاص أو cache.
  2. إعداد فرع Neon تطوير مستقل ونسخة استعادة معتمدة وحماية الإنتاج ومراجعة اعتماد وصول DB والتدوير السري.
  3. تفسير RLS/GRANT/Owner/Data API وربطها بالمؤسسة والعضوية على مستوى الخادم والقاعدة، مع منع أي مسار لتجاوز الضوابط.
  4. إدارة حساب/مؤسسة/عضوية حقيقية في بيئة تجربة اصطناعية مصرح بها، بما يكفي لإثبات المسارات الأساسية دون بيانات عملاء.
  5. ضبط نموذج التمكين المستقل لكل منتج، وعدم فتح Chat أو موصل AI بلا موافقة مزود وسياسة No-Training معتمدة.
  6. امتلاك معيار قبول محدد النطاق لما يُقال «يعمل» مع مصدر نسخة/تاريخ/بيئة/دليل، وعدم إعلان منتج جاهز من وثائق Target فقط.

P1 — إغلاق مكوّنات المنتج ونموذج الأعمال

  1. إكمال اتصال Firewall أو التصريح بنطاق المختبر فقط.
  2. إغلاق تصدير/تحقق Ledger وسيناريو فشل التسجيل الإلزامي.
  3. إغلاق Human Gate داخل عملية محدودة موثّقة، بإذن يستخدم مرة واحدة.
  4. إغلاق Asset Lifecycle وRisk Treatment مع قواعد مسؤوليات واضحة.
  5. إغلاق Secure Chat بالاعتماد الصريح للنموذج، أو إبقاؤه غير متاح وشرحه بوضوح.
  6. إكمال دورة PoV 48h والعقود والموافقات والتراخيص والإشعارات دون دفع تلقائي.

P2 — اكتمال تجربة العرض والمحتوى والمراقبة

  1. اتساق UX والموبايل والـRTL وPerformance دون إعادة بناء الرئيسية المحمية.
  2. تغطية مقالات Kernel/Ledger وروابطها الحقيقية داخل مركز المعرفة، وقياس SEO من أدوات مصرح بها.
  3. تشغيل مراقبة احترافية، سجل حوادث واستعادة بيانات/نسخ احتياطي وتوثيق واجهات المطور بحسب النطاق المعتمد.

بعد اكتمال تحميل الشاشات عند عرض 390px لم يُلاحظ Overflow دائم في الصفحات العامة المستهدفة. لكن خلال ما يقارب 0.9 ثانية من أول حركة على /products/ و/products/firewall/ وصل عرض الوثيقة مؤقتًا إلى نحو 777px قبل أن يعود إلى 390px، ما قد يسبب سحبًا أفقيًا لحظيًا أو اهتزازًا أوليًا. ظهرت عناصر الوصول الأساسية — اللغة ar-SA واتجاه RTL، ورابط Skip، وتسميات الحقول وAlt — في الصفحات المفحوصة، مع وجود نصوص 13–14px وأوزان عربية رقيقة قد تقلل سهولة القراءة. هذا ليس اعتمادًا عامًا لإمكانية الوصول.
