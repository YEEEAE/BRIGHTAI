# خطة نشر مشروطة ومراجعة مستقلة

1. **مالك الإصدار والأمن** يثبتان SHA المرشح ونتائج البناء والاختبارات، ويغلقان مانع سلسلة التوريد من السجل المعتمد، وعقد أخطاء Firewall/Human Gate، وفشل رحلة Auth في `/products/`. يعاد تشغيل التحققات نفسها وتوثق مقارنة Hero بمرجع مرئي معتمد.
2. **مشغّل البيانات** يحدد Staging منفصلًا بعد التفويض، ويختبر استعادة نسخة اصطناعية ويقيس RPO/RTO، ثم يوثق parity والترحيلات المنطبقة حتى `0045` من نفس SHA. يشغّل التطبيق عبر دور محدود غير مالك بلا BYPASSRLS ويفحص FORCE RLS والمنح وData API وعضويات A/B وقراءة Secure Chat للمشاركين حصريًا. لا ترحيل للإنتاج قبل تمرين معتمد.
3. **الخصوصية والأمن والمالية** يوقعون اعتماد حساب Groq والمشروع والمنطقة الفعلية للمعالجة، وفئات البيانات والاحتفاظ وعدم التدريب والأسعار والحدود. يدور المشغّل أي مفتاح يحتمل انكشافه ويستخدم مفتاحًا خادميًا مخصصًا عبر `AIGAS_SC_GROQ_API_KEY`. يطابق `GROQ_MODEL` سجل اعتماد غير منتهٍ، ويثبت صلاحية بارامترات النموذج. يهيئ مخزن ميزانية دائمًا مشتركًا لجميع عمال الحساب، ويختبر فقده وازدحامه والمصالحة بعد الانقطاع. عند توزيع العمال على مضيفين بلا مخزن مشترك، يلزم مخزن معاملات مركزي واختبار قبول قبل أي إرسال.
4. **مشغّل المنصة** يطلب تفويض نشر Staging مستقلًا لخدمة Node على SHA المحدد. يثبت هوية التشغيل من `/healthz/` وجاهزية JSON من `/readyz/` ورفض الطلبات الخاصة بلا جلسة. يبقى المختبر العام للمزود مغلقًا. بعد اعتماد التكلفة والنطاق، ينفذ المشغّل طلبًا اصطناعيًا واحدًا بلا إعادة محاولة من مؤسسة اختبار معتمدة، ويحفظ الحالة والمدة والاستهلاك دون نص أو مفتاح.
5. **مدقق مستقل** يعيد scorecard على الإصدار المستهدف ويثبت ≥80% لكل محور ومنتج و4/4 رحلات E2E مستهدفة وكافة الشروط الحرجة. يراجع تجربة 48 ساعة في نفس البيئة بما يشمل عدم التجديد والانتهاء والعزل. يتطلب التجاري توقيع UAT وعقد دعم وسياسات خصوصية واستعادة ونطاق ادعاء Ledger.
6. **مالك الإصدار** يقرر cutover منفصلًا مع صلاحية التغيير المطلوبة، ثم يعيد مجسات الأصل والحافة من نقطتين. عند فشل readiness أو RLS أو ظهور P0، يوقف فتح الوصول ويُغلق egress عبر `AIGAS_GROQ_DISABLED=true` ويرجع إلى آخر إصدار سليم معتمد. استعادة البيانات إجراء مستقل بعد تقييم الأثر.
