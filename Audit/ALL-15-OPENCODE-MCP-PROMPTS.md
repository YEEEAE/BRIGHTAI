# FINAL DESIGN EXECUTION PROMPT 06 / 15 — تحسين التنقل داخل الصفحات والفهارس دون تغيير الهيدر

**المشروع:** BRIGHT AI / AIGAS، الموقع `https://brightai.live`، المستودع `YEEEAE/BRIGHTAI` — النسخة المحلية الحالية هي مرجع التنفيذ.

## المهمة وصلاحية التنفيذ — مستقلة تمامًا

أنت **Senior Arabic RTL Product Designer + Astro UI Engineer + Motion Designer**، وتعمل داخل **نسخة محلية** من `YEEEAE/BRIGHTAI` وليس داخل محادثة ChatGPT هذه. **نفّذ تحسينات الكود المحلي الآن**؛ لا تكتفِ بكتابة خطة. كل المتطلبات الجوهرية لهذه الدفعة مكتوبة هنا. اقرأ `AGENTS.md` و`.agents/mind/01-mind-latest.md` و`docs/BRAND-AND-DESIGN-SYSTEM.md` وملفات القسم المستهدف، واستوعب سلوك المكونات الموجودة قبل تعديلها. أنت تعمل في OpenCode مع MCPs متصلة وفق إفادة المالك: `21st` و`Figma` و`chrome-devtools` و`Lazyweb` و`Made Good Designs`. استخدمها بوعي حسب بروتوكول هذه الدفعة أدناه؛ ليس مطلوبًا استخدام MagicPath أو Awwwards، ولا تعتمد على أدوات غير متاحة أو أسماء دوال متخيّلة.

**قاعدة التجميد:** احتفظ **بالهيدر الرئيسي كاملًا** (`Header.astro` وما يملكه من CSS/JS)، والشعار المعتمد `BrandLogo.astro`/الأصول، و**Hero الصفحة الرئيسية** ومشهد `Constellation.astro` وحركته وتوقيته وألوانه ونصوصه وأزراره دون تعديل مباشر أو جانبي. احتفظ بنص كل قسم موجود، وعناوينه وأزراره وروابطه وترتيبه ومكانه وعدد مكوناته وغرضه. لا تعيد بناء الموقع في React أو تستبدل هيكلة Astro أو تنقل الأقسام. يمكن إضافة قسم **مستقل في آخر محتوى الصفحة** فقط إذا طلبته هذه الدفعة صراحة وكان له نفع موثق وليس نسخة ثانية من عنصر قائم؛ الإضافة لا تحذف ولا تعيد ترتيب الأقسام الحالية.

**الهوية:** Dark-only + Arabic RTL، خلفية `#000000`، أبيض `#FFFFFF`، ثانوي `#BDBDBD`، بنفسجي `#8052FF` للإجراء، كهرماني `#FFB829` للاهتمام/Focus، أخضر `#15846E` لحالة نجاح حقيقية فقط. استعمل خط IBM Plex Arabic المحلي، وSVG icons متجانسة، وCSS منطقيًا (`padding-inline`, `inset-inline`) مع `bdi` لأسماء المنتجات والرموز الإنجليزية. لا تقلّب العربية ولا تقطع الحروف إلى spans. لا تدع «التحسين» يغير معنى حالات تشغيلية أو يخلق محتوى تجاريًا أو منظومة امتثال وهمية.

**الحركة:** Hover/press 120–160ms، state 180–260ms، explanatory reveal 350–480ms عند الحاجة، map path 550–900ms عند تفاعل صريح، لا loader وهمي ولا loop مزخرف ولا scroll hijacking. النص الأساسي ظاهر فورًا حتى دون JS؛ احترم `prefers-reduced-motion`. لا global `h1` أو `button` أو `section` overrides قد تصل للهيدر/الهيرو.

**حدود الصلاحيات:** لا Commit، لا Push، لا Merge، لا PR، لا نشر، لا تعديل GitHub أو Neon أو قواعد الإنتاج، لا API/Auth/Backend migrations بسبب التصميم، ولا بيانات مستخدم حقيقية في mockups أو أدوات خارجية. لا تنشئ اختبارات جديدة أو تشغّل مجموعات اختبارات backend في هذه المرحلة؛ يسوغ فحص الـDiff والكود ولقطات بصرية محلية غير حساسة في دفعة التسليم فقط إذا كانت البيئة متاحة. لا تدّعِ نجاح فحص لم يجرَ.

**تسليم هذه الدفعة:** نفّذ التعديلات المحددة، ثم اذكر أسماء الملفات التي عُدّلت، وتغييرات فعلية 3–6 أسطر، وأي قيد/عنصر تركته دون تغيير. لا تكرر التقرير ولا تبدأ دفعة أخرى بنفسك.

## بروتوكول OpenCode + أدوات MCP الخمس — طبّقه داخل هذه الدفعة

**هذا تكليف تنفيذ مخصص لـOpenCode، والأدوات التالية متصلة به بحسب المالك. لا تعتمد على محادثة أخرى أو صيغة أسماء أدوات مفترضة.** ابدأ باكتشاف أسماء السيرفرات والدوال المتاحة فعلًا في جلسة OpenCode، ثم استخدم الأداة المناسبة من كل خادم. أي اختلاف تسمية (مثل `21st`/`21st-dev` أو `Made Good Designs`/`mgd-inspiration`) يُحل عبر `tools/list`/واجهة OpenCode الفعلية؛ **ممنوع اختراع اسم دالة أو اعتبار الأداة استُخدمت دون استجابة حقيقية.** لا تطلب إعادة تثبيت MCP متصل أصلًا، ولا تعرض أو تنقل مفاتيح اتصاله.

**وظيفة الأدوات — مع الفصل بين المرجع والتنفيذ:**

- **`21st` (21st.dev):** ابحث في مكتبة مكونات UI عن *نمط* مناسب لهذه الدفعة (Cards / Tabs / Controls / Tables / Graph)، واطّلع على البنية والتفاعل وحالات المكوّن. بعض النتائج React/TSX: **لا تلصق TSX مباشرة في Astro ولا تحوّل Astro إلى React ولا تثبّت حزم/UI kits جديدة تلقائيًا**؛ استخرج مبادئ هندسة المكوّن وطبّقها في `.astro`/CSS الحالي ما لم يتطلب مكوّنًا مستقلًا صغيرًا متوافقًا من دون تعقيد. راعِ تراخيص المحتوى.
- **`Figma`:** اقرأ فقط ملفات/Frames/Components/Variables المتاحة والمناسبة لـBRIGHT AI إن كانت موجودة ويمكن الوصول إليها. استخدمها لفهم hierarchy وspacing وvariants والعلاقات بين الشاشات. **لا تنشئ ملف Figma أو تحدّث تصميمًا خارجيًا أو تستبدل هوية الموقع** بلا إذن منفصل. إذا لم يوجد ملف ملائم، المصدر المرجعي هو CSS/HTML الحالي، وليس إطارًا متخيّلًا.
- **`chrome-devtools`:** افحص **الموقع العام قراءة فقط** وموقع المعاينة المحلي، بمقاسي `1440px` و`390px` (واستخدم 320px عند خطر القص). التقط baseline قبل التعديل ومعاينة بعده باستخدام الأدوات الموجودة فعليًا مثل `take_snapshot`, `take_screenshot`, `resize_page`, `list_console_messages`/ما يقابلها؛ استخدم فحص CSS وDOM والتحقق المرئي لحالات العنصر المتأثر. **لا تتعامل مع عميل فعلي أو تسجيل دخول أو نموذج إرسال أو مفاتيح/كوكيز أو إجراء تغييري، ولا تُشغّل اختبارات مؤتمتة أو Build/CI**؛ يمكن تشغيل `dev` محليًا للمعاينة فقط وفق تعليمات المستودع.
- **`Lazyweb`:** ابحث في أمثلة تطبيقات حقيقية عن نوع المكوّن أو Flow المطلوب، 1–3 أمثلة وثيقة الصلة فقط. استخرج لماذا نجح ترتيب المعلومات والانتقالات، **ولا تنقل شكل شاشة أو نصوصها أو علامتها التجارية حرفيًا**.
- **`Made Good Designs`:** استخدم مكتبة المراجع للطباعة والهوية والمساحات واللوحات البصرية والرسوم التوضيحية. ابحث بحسب موضوع الدفعة، وسجّل مرجعًا مناسبًا. **لا تنسخ artwork أو صورًا أو شعارات بحقوق غير مسموحة، ولا تستبدل ألوان BRIGHT AI الموثقة بلوحة جديدة**.

**ترتيب التنفيذ الإلزامي:** (1) اقرأ ملفات Astro/CSS المحلية وتعليمات AGENTS، (2) افحص الحالة الحالية بصريًا بـChrome DevTools إذا أمكن، (3) استخدم أدوات البحث/التصميم المطلوبة أدناه لدليل محدد، (4) قرر أقل تحسين ذي قيمة مع الحفاظ على التخطيط والنصوص والهيرو والهيدر، (5) **عدّل الكود المحلي بالفعل**، (6) قارن النتيجة بصريًا بـChrome DevTools. لا تعوّض تحرير الكود بصورة Figma أو مكوّن معروض في 21st أو لوحة Moodboard.

**سجل تنفيذ صغير في الرد النهائي:** `MCP | نمط/شاشة أو Frame شاهدته | القرار الذي انعكس في الكود | التحقق المتاح`، بحد أقصى سطر واحد لكل خادم مستخدم. اذكر الاسم الفعلي لنتيجة البحث أو رابط المصدر إن أعادته الأداة، لا روابط ملفقة. إذا أخفق خادم أو لم يجد نتائج مناسبة، اكتب `NOT AVAILABLE/NOT APPLICABLE` والسبب واستكمل العمل بما هو متاح. **لا تستدع أدوات خارجية بحمولة أسرار، أو بيانات عميل، أو كود خاص، أو URL داخلي خاص**. جميع الملفات المتغيرة محليًا فقط: لا Commit/Push/PR/Deploy ولا تعديلات Neon أو GitHub عن بعد.

## خطة استخدام MCPs المطلوبة لهذه الدفعة — إجراءات فعلية لا أسماء شكلية

كل MCP موصوف أدناه مطلوب للجزء المناسب من هذه المهمة، ولا يجوز أن يكون استدعاؤه لمجرد إثبات أنه متصل. اختر الاستعلام الواقعي الأقصر، واطلع على نتيجة واحدة ذات صلة، ثم نفّذ التغيير المحلي الذي يبرره. لا تجعل البحث أطول من تنفيذ المهمة.

- **21st — **أساسي لهذه الدفعة**:** ابحث `table of contents sidebar` و`breadcrumbs` و`article navigation`، وكيّف النمط مع `.section-compass` الحالي.
- **Figma — **أساسي لهذه الدفعة**:** راجع مكوّنات navigation أو toc في ملفات BRIGHT AI إن وجدت، وأبقِ global Header كما هو.
- **chrome-devtools — **أساسي لهذه الدفعة**:** افحص ثابت/Sticky عنصر `داخل الصفحة` في `/products/..` على 390px ومكان focus في TOC؛ امنع أي تراكب دون نقل الأقسام.
- **Lazyweb — **أساسي لهذه الدفعة**:** ابحث `documentation table of contents` و`mobile document navigation` للتعرف على مسارات التنقل البسيطة.
- **Made Good Designs — **أساسي لهذه الدفعة**:** ابحث `editorial navigation typography hierarchy` لاستنتاج وزن الفواصل وحالات الرابط فقط.
  **مخرجات قابلة للتحقق:** لا يكفي ذكر أن الاستعانة بالمراجع تمت. اذكر مكوّن Astro/CSS الذي تغيّر فعليًا بعد الاطلاع على نتيجة MCP (أو سبب عدم وجود تغيير)، وصف الشاشة/حالة التفاعل بصريًا، وما بقي محفوظًا من HTML والنصوص. إن كانت واجهة Chrome المنشورة مختلفة عن الملفات المحلية، فصف ذلك بأنه فرق نشر، ولا تعِد بناء الكود اعتمادًا على شاشة قديمة.

## خطة التنفيذ التفصيلية — نفّذ بالترتيب

1. حافظ على `Header.astro` بنيويًا وبصريًا دون تغيير، وركّز على `section-compass`, `document-toc`, Breadcrumbs، والانتقال بين الأقسام ضمن `PageShell`.
2. فحص الموقع الحي بتاريخ 2026-11-03 كشف أن Compass يختفي على الجوال ولا يغطي الصفحة؛ **لا تُعد مشكلة التراكب عطلًا حاليًا**. حسّن وسيلة الوصول للقسم في عرض 320/360/390px، وعالج أي تداخل **إذا ظهر فعليًا**: استخدم تصميماً يراعي ارتفاع الهيدر ويكشف روابط القسم داخل عنصر منفصل يمكن إغلاقه؛ لا تنقل قسمًا ولا تقص نصًا أو زرًا. راجع تأثير `position:fixed/sticky` وz-index وsafe-area.
3. عند الضغط على Anchor: Scroll موقع العنوان صحيح دون اختفاء خلف الترويسة، URL يعكس العنوان، :focus و:target واضحان، وبقاء رابط العودة إلى نتائج المعرفة إن وجد.
4. توحيد عنصر Active Section Indicator على الصفحات التي فيها فهرس أصلاً؛ لا تضف TOC مكرر على صفحة فيها `KnowledgeReader` أو فهرس خاص.
5. في الهواتف استعمل Disclosure مختصرًا للفهرس الثانوي فقط، قابلًا لفتح/إغلاق لوحة المفاتيح ولا يغطي CTA. البنية العامة للأقسام محفوظة، والهيدر الأعلى غير معدّل.
6. لا تفترض أن مشكلة التنقل تُحل بزيادة روابط الهيدر؛ تجنب DOM duplicates وعناصر تنقل بلا ARIA أو نسخة بلا JS.

**قاعدة التجميد:** احتفظ **بالهيدر الرئيسي كاملًا** (`Header.astro` وما يملكه من CSS/JS)، والشعار المعتمد `BrandLogo.astro`/الأصول، و**Hero الصفحة الرئيسية** ومشهد `Constellation.astro` وحركته وتوقيته وألوانه ونصوصه وأزراره دون تعديل مباشر أو جانبي. احتفظ بنص كل قسم موجود، وعناوينه وأزراره وروابطه وترتيبه ومكانه وعدد مكوناته وغرضه. لا تعيد بناء الموقع في React أو تستبدل هيكلة Astro أو تنقل الأقسام. يمكن إضافة قسم **مستقل في آخر محتوى الصفحة** فقط إذا طلبته هذه الدفعة صراحة وكان له نفع موثق وليس نسخة ثانية من عنصر قائم؛ الإضافة لا تحذف ولا تعيد ترتيب الأقسام الحالية.

**الهوية:** Dark-only + Arabic RTL، خلفية `#000000`، أبيض `#FFFFFF`، ثانوي `#BDBDBD`، بنفسجي `#8052FF` للإجراء، كهرماني `#FFB829` للاهتمام/Focus، أخضر `#15846E` لحالة نجاح حقيقية فقط. استعمل خط IBM Plex Arabic المحلي، وSVG icons متجانسة، وCSS منطقيًا (`padding-inline`, `inset-inline`) مع `bdi` لأسماء المنتجات والرموز الإنجليزية. لا تقلّب العربية ولا تقطع الحروف إلى spans. لا تدع «التحسين» يغير معنى حالات تشغيلية أو يخلق محتوى تجاريًا أو منظومة امتثال وهمية.

**الحركة:** Hover/press 120–160ms، state 180–260ms، explanatory reveal 350–480ms عند الحاجة، map path 550–900ms عند تفاعل صريح، لا loader وهمي ولا loop مزخرف ولا scroll hijacking. النص الأساسي ظاهر فورًا حتى دون JS؛ احترم `prefers-reduced-motion`. لا global `h1` أو `button` أو `section` overrides قد تصل للهيدر/الهيرو.

**حدود الصلاحيات:** لا Commit، لا Push، لا Merge، لا PR، لا نشر، لا تعديل GitHub أو Neon أو قواعد الإنتاج، لا API/Auth/Backend migrations بسبب التصميم، ولا بيانات مستخدم حقيقية في mockups أو أدوات خارجية. لا تنشئ اختبارات جديدة أو تشغّل مجموعات اختبارات backend في هذه المرحلة؛ يسوغ فحص الـDiff والكود ولقطات بصرية محلية غير حساسة في دفعة التسليم فقط إذا كانت البيئة متاحة. لا تدّعِ نجاح فحص لم يجرَ.

**تسليم هذه الدفعة:** نفّذ التعديلات المحددة، ثم اذكر أسماء الملفات التي عُدّلت، وتغييرات فعلية 3–6 أسطر، وأي قيد/عنصر تركته دون تغيير. لا تكرر التقرير ولا تبدأ دفعة أخرى بنفسك.

## بروتوكول OpenCode + أدوات MCP الخمس — طبّقه داخل هذه الدفعة

**هذا تكليف تنفيذ مخصص لـOpenCode، والأدوات التالية متصلة به بحسب المالك. لا تعتمد على محادثة أخرى أو صيغة أسماء أدوات مفترضة.** ابدأ باكتشاف أسماء السيرفرات والدوال المتاحة فعلًا في جلسة OpenCode، ثم استخدم الأداة المناسبة من كل خادم. أي اختلاف تسمية (مثل `21st`/`21st-dev` أو `Made Good Designs`/`mgd-inspiration`) يُحل عبر `tools/list`/واجهة OpenCode الفعلية؛ **ممنوع اختراع اسم دالة أو اعتبار الأداة استُخدمت دون استجابة حقيقية.** لا تطلب إعادة تثبيت MCP متصل أصلًا، ولا تعرض أو تنقل مفاتيح اتصاله.

**وظيفة الأدوات — مع الفصل بين المرجع والتنفيذ:**

- **`21st` (21st.dev):** ابحث في مكتبة مكونات UI عن *نمط* مناسب لهذه الدفعة (Cards / Tabs / Controls / Tables / Graph)، واطّلع على البنية والتفاعل وحالات المكوّن. بعض النتائج React/TSX: **لا تلصق TSX مباشرة في Astro ولا تحوّل Astro إلى React ولا تثبّت حزم/UI kits جديدة تلقائيًا**؛ استخرج مبادئ هندسة المكوّن وطبّقها في `.astro`/CSS الحالي ما لم يتطلب مكوّنًا مستقلًا صغيرًا متوافقًا من دون تعقيد. راعِ تراخيص المحتوى.
- **`Figma`:** اقرأ فقط ملفات/Frames/Components/Variables المتاحة والمناسبة لـBRIGHT AI إن كانت موجودة ويمكن الوصول إليها. استخدمها لفهم hierarchy وspacing وvariants والعلاقات بين الشاشات. **لا تنشئ ملف Figma أو تحدّث تصميمًا خارجيًا أو تستبدل هوية الموقع** بلا إذن منفصل. إذا لم يوجد ملف ملائم، المصدر المرجعي هو CSS/HTML الحالي، وليس إطارًا متخيّلًا.
- **`chrome-devtools`:** افحص **الموقع العام قراءة فقط** وموقع المعاينة المحلي، بمقاسي `1440px` و`390px` (واستخدم 320px عند خطر القص). التقط baseline قبل التعديل ومعاينة بعده باستخدام الأدوات الموجودة فعليًا مثل `take_snapshot`, `take_screenshot`, `resize_page`, `list_console_messages`/ما يقابلها؛ استخدم فحص CSS وDOM والتحقق المرئي لحالات العنصر المتأثر. **لا تتعامل مع عميل فعلي أو تسجيل دخول أو نموذج إرسال أو مفاتيح/كوكيز أو إجراء تغييري، ولا تُشغّل اختبارات مؤتمتة أو Build/CI**؛ يمكن تشغيل `dev` محليًا للمعاينة فقط وفق تعليمات المستودع.
- **`Lazyweb`:** ابحث في أمثلة تطبيقات حقيقية عن نوع المكوّن أو Flow المطلوب، 1–3 أمثلة وثيقة الصلة فقط. استخرج لماذا نجح ترتيب المعلومات والانتقالات، **ولا تنقل شكل شاشة أو نصوصها أو علامتها التجارية حرفيًا**.
- **`Made Good Designs`:** استخدم مكتبة المراجع للطباعة والهوية والمساحات واللوحات البصرية والرسوم التوضيحية. ابحث بحسب موضوع الدفعة، وسجّل مرجعًا مناسبًا. **لا تنسخ artwork أو صورًا أو شعارات بحقوق غير مسموحة، ولا تستبدل ألوان BRIGHT AI الموثقة بلوحة جديدة**.

**ترتيب التنفيذ الإلزامي:** (1) اقرأ ملفات Astro/CSS المحلية وتعليمات AGENTS، (2) افحص الحالة الحالية بصريًا بـChrome DevTools إذا أمكن، (3) استخدم أدوات البحث/التصميم المطلوبة أدناه لدليل محدد، (4) قرر أقل تحسين ذي قيمة مع الحفاظ على التخطيط والنصوص والهيرو والهيدر، (5) **عدّل الكود المحلي بالفعل**، (6) قارن النتيجة بصريًا بـChrome DevTools. لا تعوّض تحرير الكود بصورة Figma أو مكوّن معروض في 21st أو لوحة Moodboard.

**سجل تنفيذ صغير في الرد النهائي:** `MCP | نمط/شاشة أو Frame شاهدته | القرار الذي انعكس في الكود | التحقق المتاح`، بحد أقصى سطر واحد لكل خادم مستخدم. اذكر الاسم الفعلي لنتيجة البحث أو رابط المصدر إن أعادته الأداة، لا روابط ملفقة. إذا أخفق خادم أو لم يجد نتائج مناسبة، اكتب `NOT AVAILABLE/NOT APPLICABLE` والسبب واستكمل العمل بما هو متاح. **لا تستدع أدوات خارجية بحمولة أسرار، أو بيانات عميل، أو كود خاص، أو URL داخلي خاص**. جميع الملفات المتغيرة محليًا فقط: لا Commit/Push/PR/Deploy ولا تعديلات Neon أو GitHub عن بعد.

## خطة استخدام MCPs المطلوبة لهذه الدفعة — إجراءات فعلية لا أسماء شكلية

كل MCP موصوف أدناه مطلوب للجزء المناسب من هذه المهمة، ولا يجوز أن يكون استدعاؤه لمجرد إثبات أنه متصل. اختر الاستعلام الواقعي الأقصر، واطلع على نتيجة واحدة ذات صلة، ثم نفّذ التغيير المحلي الذي يبرره. لا تجعل البحث أطول من تنفيذ المهمة.

- **21st — **أساسي لهذه الدفعة**:** ابحث `search command palette`, `filter chips`, `article TOC`, `quick preview panel`؛ استوحِ States لا تثبّت React search library.
- **Figma — **أساسي لهذه الدفعة**:** استخدم مخططات/Frames Docs عند توفرها للمقارنة، لا تنشئ نسخة مركز معرفة جديدة في Figma.
- **chrome-devtools — **أساسي لهذه الدفعة**:** افحص `/docs/` عند 1440/390؛ تحقق بصريًا من scrollbar الداخلي، فلاتر الجوال، نتائج المعاينة، وحالات البحث المتاحة محليًا. لا تعتبر disabled الابتدائي خطأ؛ سكربت JS يفعّل عناصر التحكم.
- **Lazyweb — **أساسي لهذه الدفعة**:** ابحث `docs search filters` و`article reading sidebar` و`knowledge base`; اختَر أسلوبًا يجعل النتائج أولًا من أمثلة حقيقية مثل منصات الوثائق.
- **Made Good Designs — **أساسي لهذه الدفعة**:** ابحث `long form editorial typography`, `dark documentation information hierarchy` لتحسين القراءة والفواصل.
  **مخرجات قابلة للتحقق:** لا يكفي ذكر أن الاستعانة بالمراجع تمت. اذكر مكوّن Astro/CSS الذي تغيّر فعليًا بعد الاطلاع على نتيجة MCP (أو سبب عدم وجود تغيير)، وصف الشاشة/حالة التفاعل بصريًا، وما بقي محفوظًا من HTML والنصوص. إن كانت واجهة Chrome المنشورة مختلفة عن الملفات المحلية، فصف ذلك بأنه فرق نشر، ولا تعِد بناء الكود اعتمادًا على شاشة قديمة.

7. جوال 360/390px: لا Overlay يغطي input أو فهرس المقال، مع نتائج قابلة للمسح والفهم. لا scroll animation على فقرات القراءة.

**قاعدة التجميد:** احتفظ **بالهيدر الرئيسي كاملًا** (`Header.astro` وما يملكه من CSS/JS)، والشعار المعتمد `BrandLogo.astro`/الأصول، و**Hero الصفحة الرئيسية** ومشهد `Constellation.astro` وحركته وتوقيته وألوانه ونصوصه وأزراره دون تعديل مباشر أو جانبي. احتفظ بنص كل قسم موجود، وعناوينه وأزراره وروابطه وترتيبه ومكانه وعدد مكوناته وغرضه. لا تعيد بناء الموقع في React أو تستبدل هيكلة Astro أو تنقل الأقسام. يمكن إضافة قسم **مستقل في آخر محتوى الصفحة** فقط إذا طلبته هذه الدفعة صراحة وكان له نفع موثق وليس نسخة ثانية من عنصر قائم؛ الإضافة لا تحذف ولا تعيد ترتيب الأقسام الحالية.

**الهوية:** Dark-only + Arabic RTL، خلفية `#000000`، أبيض `#FFFFFF`، ثانوي `#BDBDBD`، بنفسجي `#8052FF` للإجراء، كهرماني `#FFB829` للاهتمام/Focus، أخضر `#15846E` لحالة نجاح حقيقية فقط. استعمل خط IBM Plex Arabic المحلي، وSVG icons متجانسة، وCSS منطقيًا (`padding-inline`, `inset-inline`) مع `bdi` لأسماء المنتجات والرموز الإنجليزية. لا تقلّب العربية ولا تقطع الحروف إلى spans. لا تدع «التحسين» يغير معنى حالات تشغيلية أو يخلق محتوى تجاريًا أو منظومة امتثال وهمية.

**الحركة:** Hover/press 120–160ms، state 180–260ms، explanatory reveal 350–480ms عند الحاجة، map path 550–900ms عند تفاعل صريح، لا loader وهمي ولا loop مزخرف ولا scroll hijacking. النص الأساسي ظاهر فورًا حتى دون JS؛ احترم `prefers-reduced-motion`. لا global `h1` أو `button` أو `section` overrides قد تصل للهيدر/الهيرو.

**حدود الصلاحيات:** لا Commit، لا Push، لا Merge، لا PR، لا نشر، لا تعديل GitHub أو Neon أو قواعد الإنتاج، لا API/Auth/Backend migrations بسبب التصميم، ولا بيانات مستخدم حقيقية في mockups أو أدوات خارجية. لا تنشئ اختبارات جديدة أو تشغّل مجموعات اختبارات backend في هذه المرحلة؛ يسوغ فحص الـDiff والكود ولقطات بصرية محلية غير حساسة في دفعة التسليم فقط إذا كانت البيئة متاحة. لا تدّعِ نجاح فحص لم يجرَ.

## بروتوكول OpenCode + أدوات MCP الخمس — طبّقه داخل هذه الدفعة

**هذا تكليف تنفيذ مخصص لـOpenCode، والأدوات التالية متصلة به بحسب المالك. لا تعتمد على محادثة أخرى أو صيغة أسماء أدوات مفترضة.** ابدأ باكتشاف أسماء السيرفرات والدوال المتاحة فعلًا في جلسة OpenCode، ثم استخدم الأداة المناسبة من كل خادم. أي اختلاف تسمية (مثل `21st`/`21st-dev` أو `Made Good Designs`/`mgd-inspiration`) يُحل عبر `tools/list`/واجهة OpenCode الفعلية؛ **ممنوع اختراع اسم دالة أو اعتبار الأداة استُخدمت دون استجابة حقيقية.** لا تطلب إعادة تثبيت MCP متصل أصلًا، ولا تعرض أو تنقل مفاتيح اتصاله.

**وظيفة الأدوات — مع الفصل بين المرجع والتنفيذ:**

- **`21st` (21st.dev):** ابحث في مكتبة مكونات UI عن *نمط* مناسب لهذه الدفعة (Cards / Tabs / Controls / Tables / Graph)، واطّلع على البنية والتفاعل وحالات المكوّن. بعض النتائج React/TSX: **لا تلصق TSX مباشرة في Astro ولا تحوّل Astro إلى React ولا تثبّت حزم/UI kits جديدة تلقائيًا**؛ استخرج مبادئ هندسة المكوّن وطبّقها في `.astro`/CSS الحالي ما لم يتطلب مكوّنًا مستقلًا صغيرًا متوافقًا من دون تعقيد. راعِ تراخيص المحتوى.
- **`Figma`:** اقرأ فقط ملفات/Frames/Components/Variables المتاحة والمناسبة لـBRIGHT AI إن كانت موجودة ويمكن الوصول إليها. استخدمها لفهم hierarchy وspacing وvariants والعلاقات بين الشاشات. **لا تنشئ ملف Figma أو تحدّث تصميمًا خارجيًا أو تستبدل هوية الموقع** بلا إذن منفصل. إذا لم يوجد ملف ملائم، المصدر المرجعي هو CSS/HTML الحالي، وليس إطارًا متخيّلًا.
- **`chrome-devtools`:** افحص **الموقع العام قراءة فقط** وموقع المعاينة المحلي، بمقاسي `1440px` و`390px` (واستخدم 320px عند خطر القص). التقط baseline قبل التعديل ومعاينة بعده باستخدام الأدوات الموجودة فعليًا مثل `take_snapshot`, `take_screenshot`, `resize_page`, `list_console_messages`/ما يقابلها؛ استخدم فحص CSS وDOM والتحقق المرئي لحالات العنصر المتأثر. **لا تتعامل مع عميل فعلي أو تسجيل دخول أو نموذج إرسال أو مفاتيح/كوكيز أو إجراء تغييري، ولا تُشغّل اختبارات مؤتمتة أو Build/CI**؛ يمكن تشغيل `dev` محليًا للمعاينة فقط وفق تعليمات المستودع.
- **`Lazyweb`:** ابحث في أمثلة تطبيقات حقيقية عن نوع المكوّن أو Flow المطلوب، 1–3 أمثلة وثيقة الصلة فقط. استخرج لماذا نجح ترتيب المعلومات والانتقالات، **ولا تنقل شكل شاشة أو نصوصها أو علامتها التجارية حرفيًا**.
- **`Made Good Designs`:** استخدم مكتبة المراجع للطباعة والهوية والمساحات واللوحات البصرية والرسوم التوضيحية. ابحث بحسب موضوع الدفعة، وسجّل مرجعًا مناسبًا. **لا تنسخ artwork أو صورًا أو شعارات بحقوق غير مسموحة، ولا تستبدل ألوان BRIGHT AI الموثقة بلوحة جديدة**.

**ترتيب التنفيذ الإلزامي:** (1) اقرأ ملفات Astro/CSS المحلية وتعليمات AGENTS، (2) افحص الحالة الحالية بصريًا بـChrome DevTools إذا أمكن، (3) استخدم أدوات البحث/التصميم المطلوبة أدناه لدليل محدد، (4) قرر أقل تحسين ذي قيمة مع الحفاظ على التخطيط والنصوص والهيرو والهيدر، (5) **عدّل الكود المحلي بالفعل**، (6) قارن النتيجة بصريًا بـChrome DevTools. لا تعوّض تحرير الكود بصورة Figma أو مكوّن معروض في 21st أو لوحة Moodboard.

**سجل تنفيذ صغير في الرد النهائي:** `MCP | نمط/شاشة أو Frame شاهدته | القرار الذي انعكس في الكود | التحقق المتاح`، بحد أقصى سطر واحد لكل خادم مستخدم. اذكر الاسم الفعلي لنتيجة البحث أو رابط المصدر إن أعادته الأداة، لا روابط ملفقة. إذا أخفق خادم أو لم يجد نتائج مناسبة، اكتب `NOT AVAILABLE/NOT APPLICABLE` والسبب واستكمل العمل بما هو متاح. **لا تستدع أدوات خارجية بحمولة أسرار، أو بيانات عميل، أو كود خاص، أو URL داخلي خاص**. جميع الملفات المتغيرة محليًا فقط: لا Commit/Push/PR/Deploy ولا تعديلات Neon أو GitHub عن بعد.

## خطة استخدام MCPs المطلوبة لهذه الدفعة — إجراءات فعلية لا أسماء شكلية

كل MCP موصوف أدناه مطلوب للجزء المناسب من هذه المهمة، ولا يجوز أن يكون استدعاؤه لمجرد إثبات أنه متصل. اختر الاستعلام الواقعي الأقصر، واطلع على نتيجة واحدة ذات صلة، ثم نفّذ التغيير المحلي الذي يبرره. لا تجعل البحث أطول من تنفيذ المهمة.

- **21st — **أساسي لهذه الدفعة**:** ابحث `risk matrix dashboard`, `chat composer`, `message bubbles`, `model selector states` وحافظ على Data flow القائم.
- **Figma — **أساسي لهذه الدفعة**:** اقرأ frames موثقة لـRisk/Chat عند وجودها فقط، لا تضف مزود ذكاء اصطناعي أو أدوات جديدة.
- **chrome-devtools — **أساسي لهذه الدفعة**:** افحص صفحات العمل المحلية بأمثلة Synthetic فقط، وحالات `NO_APPROVED_MODEL`/No Access إذا ظهرت؛ لا تجبر إرسال أو تسجيل دخول أو نقل محادثة.
- **Lazyweb — **أساسي لهذه الدفعة**:** ابحث `AI chat interface enterprise` و`risk assessment software dashboard` لتحسين هيكل القراءة.
- **Made Good Designs — **أساسي لهذه الدفعة**:** ابحث `technical interface hierarchy` و`calm security palette` كمرجع لأسلوب سطح مكونات المحادثة.
  **مخرجات قابلة للتحقق:** لا يكفي ذكر أن الاستعانة بالمراجع تمت. اذكر مكوّن Astro/CSS الذي تغيّر فعليًا بعد الاطلاع على نتيجة MCP (أو سبب عدم وجود تغيير)، وصف الشاشة/حالة التفاعل بصريًا، وما بقي محفوظًا من HTML والنصوص. إن كانت واجهة Chrome المنشورة مختلفة عن الملفات المحلية، فصف ذلك بأنه فرق نشر، ولا تعِد بناء الكود اعتمادًا على شاشة قديمة.

## خطة التنفيذ التفصيلية — نفّذ بالترتيب

1. **Risk Engine:** صفوف الأصول، Tags مستويات الخطر، matrix legend، محاور المصفوفة، التفاصيل/مراجعات التقييم، تواريخ وموارد؛ تحسين قابلية القراءة دون تغيير خوارزمية المخاطر أو ترتيب الأعمدة أو قيمة التقييم.
2. أظهر نتيجة high-risk بوصف وظيفي لا أحمر وحده؛ لا تجعل حالات blocked أو pending تبدو كأنها نجاح.
3. **Secure Chat:** صقل مساحة Sidebar/Chat/Composer/Policy notes وتباين user/assistant messages، مع line-wrap عربي/لاتيني صحيح وبقاء وظيفة إرسال الرسالة كما هي.
4. عند `NO_APPROVED_MODEL` أو فقدان التكوين، الحالة تظهر **كما هي** دون زر إرسال فعّال أو chatbot تجريبي مزيف. لا تضف محادثات عيّنة إلى قاعدة بيانات/Analytics.
5. عند تغير حالة شبكة أو Timeout، Form feedback واضح داخل العنصر؛ لا تغير model provider أو مفاتيح env أو تخزين النصوص.
6. تجنب Motion في body المحادثة يسبب تأخر ظهور الرسالة؛ Auto-scroll لا يتغير، والنص يُقرأ فور ظهوره الحقيقي.

- **`chrome-devtools`:** افحص **الموقع العام قراءة فقط** وموقع المعاينة المحلي، بمقاسي `1440px` و`390px` (واستخدم 320px عند خطر القص). التقط baseline قبل التعديل ومعاينة بعده باستخدام الأدوات الموجودة فعليًا مثل `take_snapshot`, `take_screenshot`, `resize_page`, `list_console_messages`/ما يقابلها؛ استخدم فحص CSS وDOM والتحقق المرئي لحالات العنصر المتأثر. **لا تتعامل مع عميل فعلي أو تسجيل دخول أو نموذج إرسال أو مفاتيح/كوكيز أو إجراء تغييري، ولا تُشغّل اختبارات مؤتمتة أو Build/CI**؛ يمكن تشغيل `dev` محليًا للمعاينة فقط وفق تعليمات المستودع.
- **`Lazyweb`:** ابحث في أمثلة تطبيقات حقيقية عن نوع المكوّن أو Flow المطلوب، 1–3 أمثلة وثيقة الصلة فقط. استخرج لماذا نجح ترتيب المعلومات والانتقالات، **ولا تنقل شكل شاشة أو نصوصها أو علامتها التجارية حرفيًا**.
- **`Made Good Designs`:** استخدم مكتبة المراجع للطباعة والهوية والمساحات واللوحات البصرية والرسوم التوضيحية. ابحث بحسب موضوع الدفعة، وسجّل مرجعًا مناسبًا. **لا تنسخ artwork أو صورًا أو شعارات بحقوق غير مسموحة، ولا تستبدل ألوان BRIGHT AI الموثقة بلوحة جديدة**.

**ترتيب التنفيذ الإلزامي:** (1) اقرأ ملفات Astro/CSS المحلية وتعليمات AGENTS، (2) افحص الحالة الحالية بصريًا بـChrome DevTools إذا أمكن، (3) استخدم أدوات البحث/التصميم المطلوبة أدناه لدليل محدد، (4) قرر أقل تحسين ذي قيمة مع الحفاظ على التخطيط والنصوص والهيرو والهيدر، (5) **عدّل الكود المحلي بالفعل**، (6) قارن النتيجة بصريًا بـChrome DevTools. لا تعوّض تحرير الكود بصورة Figma أو مكوّن معروض في 21st أو لوحة Moodboard.

**سجل تنفيذ صغير في الرد النهائي:** `MCP | نمط/شاشة أو Frame شاهدته | القرار الذي انعكس في الكود | التحقق المتاح`، بحد أقصى سطر واحد لكل خادم مستخدم. اذكر الاسم الفعلي لنتيجة البحث أو رابط المصدر إن أعادته الأداة، لا روابط ملفقة. إذا أخفق خادم أو لم يجد نتائج مناسبة، اكتب `NOT AVAILABLE/NOT APPLICABLE` والسبب واستكمل العمل بما هو متاح. **لا تستدع أدوات خارجية بحمولة أسرار، أو بيانات عميل، أو كود خاص، أو URL داخلي خاص**. جميع الملفات المتغيرة محليًا فقط: لا Commit/Push/PR/Deploy ولا تعديلات Neon أو GitHub عن بعد.

## خطة استخدام MCPs المطلوبة لهذه الدفعة — إجراءات فعلية لا أسماء شكلية

كل MCP موصوف أدناه مطلوب للجزء المناسب من هذه المهمة، ولا يجوز أن يكون استدعاؤه لمجرد إثبات أنه متصل. اختر الاستعلام الواقعي الأقصر، واطلع على نتيجة واحدة ذات صلة، ثم نفّذ التغيير المحلي الذي يبرره. لا تجعل البحث أطول من تنفيذ المهمة.

- **21st — **أساسي لهذه الدفعة**:** راجع أي Pattern استلهمته المراحل السابقة؛ لا تثبّت package أو Component جديدًا في المرحلة النهائية.
- **Figma — **أساسي لهذه الدفعة**:** قارن مع ملفات الهوية المتاحة قراءة فقط وتحقق أن المقترح لم يتحول إلى Theme أو IA جديدة. لا تنشئ ملفات أو تتجاوز الصلاحية.
- **chrome-devtools — **أساسي لهذه الدفعة**:** اجمع مقارنة before/after لنفس routes والـstates عند 1440 و390، وفحص التركيز وkeyboard/أخطاء console والحواف وresponsive 320/768 عند الخطر. يمكن استخدام Performance trace على موقع محلي لا يحوي بيانات حساسة إذا توفر؛ لا تدّعِ أن هذا اختبار أمن أو إصدار جاهز.
- **Lazyweb — **أساسي لهذه الدفعة**:** استخدم مراجع النتائج السابقة فقط لضمان عدم نسخ Layout أو شعار أو أصول مرخّصة، لا بحث جديد لمجرد تزيين.
- **Made Good Designs — **أساسي لهذه الدفعة**:** راجع إن لم تتغير قيم الألوان والخطوط الرسمية بغير موافقة، وتحقق من صحة attribution للمراجع البحثية.
  **مخرجات قابلة للتحقق:** لا يكفي ذكر أن الاستعانة بالمراجع تمت. اذكر مكوّن Astro/CSS الذي تغيّر فعليًا بعد الاطلاع على نتيجة MCP (أو سبب عدم وجود تغيير)، وصف الشاشة/حالة التفاعل بصريًا، وما بقي محفوظًا من HTML والنصوص. إن كانت واجهة Chrome المنشورة مختلفة عن الملفات المحلية، فصف ذلك بأنه فرق نشر، ولا تعِد بناء الكود اعتمادًا على شاشة قديمة.

## خطة التنفيذ التفصيلية — نفّذ بالترتيب

1. الفحص السابق يوم 2026-11-03 لم يرصد تمريرًا أفقيًا في الصفحات العامة عند 390 و1440px؛ حافظ على ذلك ولا تعالج overflow افتراضيًا دون دليل. بعد تنفيذ الدفعات 01–14 على نسخة العمل المحلية، افحص بصريًا *إن توفرت أدوات العرض* 320/360/390/768/1024/1440px، Keyboard/Focus، RTL وLTR، تكبير النص، no-JS، Reduced Motion. لا تنشئ اختبارات backend أو suites جديدة. لا تدّعِ تأكيد حالة لم ترها.
2. قارن المحتوى وترتيب الأقسام والروابط والأزرار من النسخة الأصلية إلى الحالية؛ أي حذف/نقل يعود قبل التسليم. Hero/Header/Constellation/الشعار يجب أن يبقوا كما هم تمامًا.
3. افحص `:focus-visible`, interactive target ~44px، تباين النص (4.5:1 حيث ينطبق)، أسماء SVG وأيقونات، حزم المساحات، long words والتفاف العناوين. لا تجعل الحركة تخفي المحتوى عند JS disabled.
4. حافظ على أهداف AGENTS: LCP<2s هدف (حد2.5s)، INP<200ms (حد500)، CLS<0.05 (حد0.1)، JS gzip<200KB وCSS gzip<50KB؛ إذا لا يمكن القياس في البيئة لا تضع PASS وهميًا.
5. حدد أي UI مكتمل لكنه غير متاح للمستخدم بسبب `404` أو إعداد نشر/هوية، وافصله عن جودة التصميم؛ لا تعالج ذلك بتخطي Auth أو تحويل route محمي إلى صفحة مفتوحة.
6. سلّم جدول Design Handoff: صفحة/الملف المالك/التغيير/الحالات/المسارات المحمية/ما تحقق بصريًا/ما لم يُتحقق. **لا Commit أو Push أو Deploy أو تغيير قاعدة الإنتاج.**
7. يكتفي الخاتم بقائمة أوجز 5 تحسينات مؤثرة وحدود الفحص، دون عبارة «تصميم 100%» أو «جاهز إطلاق» من دون بينة.
