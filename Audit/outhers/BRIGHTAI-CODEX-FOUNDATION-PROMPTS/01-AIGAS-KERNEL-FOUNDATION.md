# CODEX EXECUTION PROMPT 01 — AIGAS Kernel | تأسيس بوابة النظام ونقطة الدخول

> **مرحلة التنفيذ:** تأسيس حقيقي + تفاعل محدود فقط، وليس تنفيذ جميع مواصفات المنتج.  
> **المستودع:** `YEEEAE/BRIGHTAI` — تنفيذ على نسخة Codex المحلية فقط.  
> **الهدف:** واجهة نظام داخل `/app/` متصلة بالخادم والبيانات عندما تكون التهيئة متاحة، مع عدم ادعاء وظائف لم تُنفذ.

## تعليمات مشتركة إلزامية — مختصرة وعملية

1. **نفّذ، لا تكتفِ بالتحليل.** اعمل على نسخة المشروع المحلية فقط. اقرأ `AGENTS.md` و`.agents/mind/01-mind-latest.md` ثم `docs/MASTER-PROJECT-BLUEPRINT.md` و`docs/PRODUCT-MASTER-CATALOG.yaml`، والمستندات ذات الصلة إذا كانت موجودة. افحص الكود قبل إنشاء ملفات جديدة. إذا اختلفت مسارات المشروع الحالية، تكيف معها ولا تنسخ بنية موازية.
2. اكتشف الـSkills وMCPs والإضافات الموجودة لدى Codex واستخدم المناسب فقط، مع أولوية **Neon MCP** لفهم قاعدة البيانات. لا تفترض أن أداة غير ظاهرة متاحة؛ إن لم توجد، استخدم اتصال Neon من جهة الخادم بعد إعداد البيئة. استخدم أدوات المتصفح للتحقق البسيط عند توفرها، بلا جولات تصوير أو فحوص مرهقة.
3. **إعداد البيئة:** افحص `.env` و`.gitignore` قبل أي عمل. استعمل بيانات اتصال Neon/Postgres وStorage وAuth وData API التي سلّمها مالك المشروع في الرسالة المنفصلة؛ ضعها **محليًا فقط** داخل `.env` غير المتعقب، باستخدام الأسماء المناسبة مثل `NEON_PROJECT_ID`, `DATABASE_URL`, `AWS_ENDPOINT_URL_S3`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_REGION`, `NEON_DATA_API_URL`, `NEON_AUTH_URL`, `NEON_JWKS_URL`. لا تنقل القيم السرية إلى ملفات `.md`، أو `.env.example`، أو الواجهة، أو تقارير الوكيل، أو Git. لا تكتب قيمًا وهمية وتقول إنها متصلة. إذا لم تتوفر القيم عندك فاطلبها من المالك بطريقة آمنة، وأكمل ما يمكن بدونها.
4. **القاعدة:** افحص الجداول والأسماء الموجودة أولًا عبر Neon MCP، ثم استخدم الجداول المناسبة إن كانت موجودة. أي تعديل مطلوب يكون صغيرًا وإضافيًا، وبترحيل قابل للفهم/المراجعة. استخدم فرع تطوير معزول إن توفر؛ لا تمسح أو تغيّر بيانات حالية ولا تطبّق تغييرات غير معتمدة على قاعدة إنتاج. إذا لم يوجد مسار آمن للترحيل، جهّز SQL محليًا واذكر ما يحتاج موافقة، ولا توقف بقية التنفيذ.
5. احفظ الفصل بين **الموقع التسويقي** و**بوابة النظام**؛ صفحات النظام تحت `/app/`، وبياناتها من الخادم فقط. Astro الحالي بنمط Node standalone؛ استفد منه بدل إعادة كتابة المشروع أو إدخال إطار عمل ضخم. لا تعدّل الرئيسية أو Hero أو Header أو Constellation أو الملفات المشتركة المحمية دون ضرورة صريحة. أنشئ Layout خاصًا بالنظام إذا احتجت؛ عربي RTL ومتوافق مع هوية BRIGHT AI.
6. احمِ كل استعلام/عملية تعديل بهوية المستخدم الموثّقة ونطاق مؤسسته من **جهة الخادم**؛ ممنوع الثقة بـ`tenant_id` المرسل من المتصفح، أو كشف مفاتيح Neon أو التخزين في JavaScript بالعميل. استخدم Neon Auth إذا توفر وتم التحقق من تكامله؛ لا تنشئ تسجيل دخول شكليًا أو تحقق JWT غير آمن. عند تعذر التهيئة، اعرض حالة «يلزم إعداد الدخول» بدل إتاحة API عامة.
7. أبقِ بيانات العملاء خارج تدريب نماذج AI؛ لا ترسل محتوى إلى مزود غير معتمد، ولا تضف أدوات Analytics إلى `/app/`. لا تستخدم بيانات عملاء حقيقية في أمثلة التطوير. لا تخترع أسعارًا، حصصًا، أوقات SLA، شهادات أو خصائص لم تُنفذ.
8. **مهم:** هذه مرحلة تأسيسية/أعلى قليلًا، وليست مشروعًا لإكمال كل ما في مواصفات المنتج. اختر أبسط تنفيذ سليم باستخدام الاعتماديات الموجودة. ما لم يُذكر صراحةً أدناه **خارج نطاق هذا البرومبت**. لا تشتت الجهد في Microservices أو Kubernetes أو Redis أو اشتراكات مدفوعة أو تصميم نظام تراخيص معقّد.
9. ممنوع `git commit` أو `git push` أو نشر أو تعديل GitHub عبر MCP. التعديلات المسموحة لوكيل Codex هي في **مساحة العمل المحلية** فقط. في النهاية أعطني أسماء الملفات المتغيرة، ما يعمل فعليًا، ما يحتاج تهيئة، وأي اعتماد أو قرار متبقٍ. لا تنقل الأسرار إلى تقرير الإنهاء.

## النتيجة المطلوبة

ابنِ **نواة تشغيلية بسيطة** للمنظومة تحت `/app/kernel/`، وليست صفحة تعريفية. الهدف: يدخل مستخدم موثّق، يُحدد مؤسسته، يشاهد بطاقات المنتجات الخمسة وحالتها داخل مساحة عمله، ويفتح كل منتج من بطاقة واضحة. يتوفر أساس تقني يمكن للبرومبتات الخمسة البناء فوقه.

## المطلوب تنفيذه الآن (حد أقصى 5 مهام)

1. **مدخل النظام وهوية أساسية:** أنشئ `/app/` و`/app/kernel/` وLayout مشتركًا. اربط الجلسة بـNeon Auth بعد التحقق من أدواته وتهيئته؛ عند عدم توفره نفذ صفحة إعداد آمنة ولا تفتح الوصول لغير الموثّقين. أدوار بسيطة فقط: `OWNER`, `ADMIN`, `MEMBER`. لا تبنِ منظومة IAM متقدمة الآن.
2. **مؤسسة واحدة قابلة للتوسع:** دعم إنشاء مساحة عمل لمستخدم جديد موثّق، واختيار المؤسسة التي ينتمي إليها. عند وجود عضويات، لا تسمح للمستخدم بإضافة نفسه لمؤسسة قائمة أو منح نفسه دور المدير. استخدم أربع كيانات صغيرة بحد أقصى إن لم يوجد بديل مناسب: `aigas_tenants`, `aigas_memberships`, `aigas_product_access`, `aigas_audit_events`، بمفاتيح وعلاقات وفهارس بسيطة؛ لكل مستخدم علاقات عضوية فعلية. إنشاء سجل الوصول لا يعني تفعيل اشتراك مدفوع تلقائيًا.
3. **لوحة Kernel كاملة بصريًا:** عنوان وحالة المساحة، بطاقة معلومات المؤسسة، مؤشر حالة الربط، منطقة «المنتجات» بخمس بطاقات منفصلة: Firewall وLedger وHuman Gate وRisk Engine وSecure Chat. لكل بطاقة: الاسم، الفائدة بجملة، الأولوية (الموجة الأولى/الثانية)، حالة الإتاحة **المأخوذة من بيانات النظام** لا من نص ثابت مضلل، زر فتح المسار `/app/<slug>/` عند توافره، أو «لم يجهز بعد» عند غيابه. أضف مخططًا SVG/CSS بسيطًا يشرح علاقة Kernel بالمنتجات، وليس 3D ثقيلًا.
4. **أساس Backend مشترك:** طبقة اتصال DB من الخادم، استعلام عضويات محمي، حارس صلاحيات/tenant قابل لإعادة الاستخدام، دوال Audit لعمليات حساسة. يكفي Endpoint محمي للوحة وحالة المنتجات، مع معالجة الأخطاء ورسائل عربية واضحة. عند غياب منتج يظهر «قيد التأسيس» بدون بيانات مزيّفة. اعرض Empty/Loading/Error/Unauthorized بوضوح.
5. **تهيئة بسيطة للمطور:** وثّق أسماء متغيرات البيئة اللازمة في `.env.example` **بدون قيم حساسة**، ومسار تشغيل محلي، وترتيب المنتجات المرتبط بالبرومبتات التالية. تحقق من Build وتشغيل الصفحة والحماية بأبسط الوسائل المتاحة.

## لا تنفذه الآن

لا اشتراكات أو دفع أو تفعيل Trial تلقائي أو إصدار رخص دائمة أو MFA مخصص أو SSO شامل أو محرك سياسات هرمي متكامل أو SIEM أو نشر سحابي. لا تضع نموذج محادثة داخل Kernel أو تكرر صفحات التسويق. Kernel مشترك ضمن المنتجات **وليس منتجًا سادسًا مدفوعًا**.

## شروط الإنجاز لهذه المرحلة

- يوجد `/app/kernel/` كواجهة نظام حقيقية، وليس `/kernel/` التوضيحية الموجودة سابقًا؛ أبقِ الأخيرة دون تغيير ما لم يتطلب الربط رابطًا صغيرًا آمنًا.
- تظهر بطاقات المنتجات الخمسة وتنقلك إلى مساراتها الصحيحة دون ادعاء التشغيل عند غيابها.
- بيانات المؤسسة تأتي من DB عبر Backend محمي؛ لا يُستقبل tenant_id من مدخل العميل كسلطة.
- لا يستطيع المستخدم غير الموثّق عرض بيانات المؤسسة. فشل Auth أو DB ينتج حالة واضحة وآمنة.
- لا تعديل للموقع الرئيسي ولا أي أسرار داخل Git؛ يعرض التقرير قائمة ملفات وتحقق خفيف وناقص الإعداد فقط.
