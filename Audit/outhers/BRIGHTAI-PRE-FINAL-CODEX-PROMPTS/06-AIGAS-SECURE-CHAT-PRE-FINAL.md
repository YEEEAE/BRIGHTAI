## نتائج التدقيق التي يجب الانطلاق منها
- موجود: `/app/secure-chat/`, `/app/api/secure-chat/models`, `/messages`, و`src/server/secure-chat/service.mjs`.
- API النماذج تُعيد قائمة فارغة والرسائل تُرفض بـ`NO_APPROVED_MODEL`؛ هذا fail-closed مقصود، لا خلل UI فقط.
- لا يوجد دليل على اعتماد نموذج أو مزود أو اتفاق No-Training، ولا يجوز استبدال الرفض بإجابة ثابتة تشبه ChatGPT.

## التنفيذ المحدد — 4 وحدات
1. **واجهة محادثة عملية:** تحسين واجهة RTL عربية، محادثة مؤقتة داخل جلسة المستخدم، إدخال، إرسال، حالات loading/failure/retry/empty، ومؤشر عداد الأحرف وحد استهلاك واجهي أولي. لا تستخدم بيانات عميل حقيقية ضمن عروض الواجهة أو logs.
2. **إدارة نماذج معتمدة:** افصل قائمة النماذج المعتمدة server-side عن المقترحات. جهز registry إعدادات للنماذج المصرح بها فقط، مع شروط مزود/سياسة No-Training/منطقة المعالجة وحدود طلب. يبقى registry فارغًا إن لم توجد موافقة فعلية. لا تسحب نموذجًا عشوائيًا من أي Gateway.
3. **مسار Backend آمن قابل للتوسعة:** صمّم adapter واحدًا مستقبليًا خلف إعدادات البيئة المحمية، ويمكن تنفيذه فقط إذا كان هناك مزود معتمد ومفتاح متوفر. ارفض الطلب `NO_APPROVED_MODEL` بصورة واضحة عند غياب الاعتماد، لا تخترع اتصالًا حقيقيًا. اضبط زمن الطلب والـerror handling ومنع تسرب مفاتيح، واحفظ Audit metadata فقط.
4. **الخصوصية والمصاريف:** أبقِ المشاركة والتصدير معطلين افتراضيًا، ولا تضع سجل محتوى المحادثة في Ledger/Audit. أظهر نموذج الاستخدام الافتراضي والتكلفة إن كان مصدرها موثوقًا، وإلا "غير متاح". أضف حدود استهلاك قابلة للتهيئة بدل أرقام سوقية مخترعة.

## معيار الإنجاز
- مسار UI إلى Backend آمن جاهز للاتصال عند اعتماد نموذج؛ إن توفر نموذج معتمد وبيئة تطوير، محادثة حقيقية معه. دون ذلك تكون حالة عدم التوفر حقيقية وواضحة، بلا ردود وهمية، وتقرير النواقص المحددة لما قبل الإطلاق.
