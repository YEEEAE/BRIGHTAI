## Firewall — معمل سياسات متصل

1. إنشاء قاعدة اصطناعية على `/app/api/firewall/rules/` مع action وpattern حرفي وحدود المشروع، ثم readback يعرض ID وversion من DB.
2. إرسال سيناريو إلى evaluate؛ الخادم يتحقق من الهوية والمؤسسة والاستحقاق وKernel قبل المحرك.
3. تغطية ALLOW/DENY/REDACT/WARN/ESCALATE. النتيجة تظهر السبب والقاعدة ونسختها وpolicyVersion وdecision/evidence reference. واجهة عامة تغيّر الألوان لا تحتسب عملية.
4. guarded execution لا يمرر DENY/WARN/ESCALATE تلقائيًا. REDACT يمرر المنقح فقط، وALLOW النص المقيم. local sandbox يمكن استخدامه إذا سُمّي تنفيذًا محليًا؛ لا يسمى رد AI خارجيًا.
5. registry المراجعة الحالي فارغ: لتمكين ESCALATE الحقيقي يلزم عقد operation وpayload/binding يربط القرار والمراجع والمهلة والنسخة، وطلب PENDING محفوظ ضمن المعاملة. لا تعِد بأن التصعيد يعمل قبل ذلك.
6. إغلاق القبول: عمليات HTTP مع DB وقراءة لاحقة لكل قرار، وحالتا مؤسستين، وفشل حفظ الدليل، ورفض تكرار fingerprint أو موافقة لقرار آخر. إرسال خارجي يحتاج اعتمادًا منفصلًا.

## Ledger — حدث ودليل يمكن التحقق منه

1. اختيار حدث اصطناعي مسموح وإنشاؤه عبر `/app/api/ledger/events/` مع idempotency key.
2. عرض الحدث المحفوظ وتسلسله وhash profile والحدث السابق من قراءة جديدة.
3. التصدير من endpoint الخاص بالحدث إلى bundle يحتوي prefix اللازم للتحقق؛ لا يُنشأ ملف واجهة يعيد بناء نتائج ثابتة.
4. تشغيل `public/downloads/aigas-ledger-verifier.mjs` في عملية مستقلة على bundle صادر فعليًا؛ ملف معدل يعطي mismatch، وملف ناقص يعطي حالة غير جازمة ملائمة.
5. لا ادعاء توقيع موثوق أو صحة مصدر/زمن أو منع تلاعب DB admin أو إثبات أحدث tail أو Legal Hold من سلسلة hash وحدها.
6. إغلاق القبول: دوام بعد إعادة الطلب، تزامن دون fork، replay متطابق، conflict مختلف، عزل A/B، تصدير وفحص مستقل موثق.

## Human Gate — طلب وقرار وأثر واحد

1. إنشاء طلب بمراجع ثانٍ مخول، وعرض PENDING من الخادم، مع سبب وسياق ومدة ونسخة سياسة.
2. منع self-review حيث تلزم السياسة، واختبار سحب المراجع أو تغير سياسة/هدف أثناء الانتظار.
3. اعتماد أو رفض بسبب محفوظ، لا مجرد تغيير badge.
4. اختيار أثر داخلي محدود: `KERNEL_WORKSPACE_RENAME` على مساحة اصطناعية. `INTERNAL_DEMO_NOTE` يثبت مسار ملاحظة فقط ولا يثبت تنفيذًا خارجيًا.
5. التنفيذ يستهلك permit واحدًا داخل معاملة الأثر والتدقيق؛ إعادة الطلب أو انتهاء المهلة لا يعيدان الأثر. تُقرأ النتيجة ونسخة الهدف بعد commit.
6. إغلاق القبول: حساب طالب وحساب مراجع، accept/reject/cancel/expire، طلبان متزامنان للتنفيذ ينتجان أثرًا واحدًا، وفشل audit يرد الأثر وفق السياسة.

## Risk Engine — سجل مخاطر اصطناعي

1. إنشاء أصل اصطناعي مع model/version/data classification والسياق المسموح، ثم قراءة revision محفوظة.
2. تقييم likelihood/impact وفق إصدار منهج التجربة المعتمد؛ المنهج مسودة داخلية ولا يوصف بأنه معتمد من ISO أو جهة تنظيمية.
3. حفظ المعالجة ومسؤولها وموعد المراجعة، ثم residual likelihood/impact/score/level المحسوبة بخادم موثوق.
4. عند طلب قبول الخطر تطبق السياسة الموقعة، وتمنع الموافقة غير المستقلة حسب الحالة؛ قبول الخطر لا يجيز النشر ولا يتجاوز Kernel.
5. تصدير register من أحدث البيانات ضمن المؤسسة مع توضيح النطاق والحقول المحذوفة، وإظهار الحاجة لإعادة التقييم عند تغير الأصل.
6. إغلاق القبول: اختبار خلايا المنهج والحدود وتعارض النسخ، residual readback، قبول/رفض الصلاحيات، تصدير مطابق وعزل A/B.

## Secure Chat — رد نموذج فعلي أو إرسال مغلق

1. قائمة نماذج من registry خادمي معتمد للمؤسسة؛ لا اختيار URL أو مفتاح من المتصفح.
2. إن لم توجد موافقة أو مفتاح صالح يعرض الخادم `NO_APPROVED_MODEL` أو `PROVIDER_NOT_CONFIGURED` وتتعطل وظيفة الإرسال مع شرح واضح. لا رد ثابت بديل.
3. قبل كل egress: هوية وعضوية واستحقاق وKernel/Firewall وحدود مدخلات وحجز حصة. لا إرسال قبل نجاح الحراس.
4. الطلب يصل فقط إلى endpoint/model/region المعتمدين، دون redirect أو fallback غير معتمد. الرد وusage حقيقيان، مع timeout وإلغاء وتسوية الحصة.
5. تسجيل أكواد نتيجة ومراجع مسموحة فقط؛ لا محتوى محادثة أو prompt أو response في Sentry/PostHog.
6. إغلاق القبول: رد مزود حقيقي على بيانات اصطناعية، وDENY دون egress، وREDACT يُفحص في request مصرح، وتزامن وحصة وإلغاء وفشل، ورفض مستخدم آخر ومالك غير مشارك.

## سياسة الخروج والحذف

قبل تشغيل تجربة: يقرر مالك البيانات والأمن مدة الاحتفاظ، نطاق التصدير، كيفية التعامل مع audit/immutable Ledger، ومن يطلب وينفذ ويعتمد الحذف. لا تُحذف الأدلة عشوائيًا لتسهيل purge. يُنفذ dry-run بعدّ الكائنات، ثم عملية محدودة للمؤسسة والتجربة، idempotent وقابلة للمراقبة؛ نتيجة الحذف/الاحتفاظ توثق دون المحتوى. اختبار الاستعادة منفصل وبإذن، ولا يعيد تجربة منتهية إلى ACTIVE.
