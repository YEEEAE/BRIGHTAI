فرضيات معقولة يجب التحقق منها

05

التحليل التقني ومسار النماذج والخصوصية

هنا أهم نقاط الخلل أو التعارض التي يمكن توجيهها مباشرة إلى المطور مع مسار الملف.

P0 · مؤكد في الكود

حفظ بيانات اتصال الزوار في sessionStorage

في lead-form-handler.js تُستبعد قيمة pdpl_consent فقط، ثم تُخزَّن بقية قيم الحقول ذات data-field ومنها الاسم والبريد وبيانات المؤسسة وفق الحقول المستخدمة.

المطلوب: إزالة التخزين الافتراضي لبيانات التعريف الشخصي، أو جعله محدودًا ومبررًا بوضوح وبعد تقييم الخصوصية؛ ومراجعة الحاجة للحقول ومدة بقائها.

ملاحظة: sessionStorage ليس مساويًا لتسريب بيانات إلى طرف خارجي، لكنه يزيد سطح تخزين بيانات شخصية داخل المتصفح ويخالف وصف «non-sensitive fields only» الموجود في التعليق.
P1 · معماري

قناتان مختلفتان لتجميع العملاء المحتملين

نماذج التسويق ترسل إلى FormSubmit وفق marketing.ts وLeadForm.astro، بينما يوجد مسار داخلي /api/lead.ts يتضمن ضوابط تحقق وCSRF وحد معدل وQueue.

المطلوب: رسم مسار كل نموذج فعلًا؛ ثم اختيار قناة موثوقة موحدة أو توثيق سبب الفصل. لا تُنقل النماذج للمسار الداخلي دون التحقق من جاهزية الإنتاج واستقرار الاستقبال.

P1 · تجربة التسليم

HTTP 200 ليس إثباتًا نهائيًا لوصول الرسالة

منطق التعامل مع الإرسال يقبل رد HTTP ناجحًا حتى لو تعذر تحليل جسم الاستجابة في بعض الحالات؛ بذلك قد تظهر حالة إرسال ناجح دون إثبات تسليم البريد أو تسجيل Lead تجاريًا.

المطلوب: فصل مراحل «قبل الطلب»، «تم استلامه»، «تم قبوله في النظام»، «تم توجيهه للفريق»، و«فشل الإرسال»، مع Logging ورقم متابعة عند الإمكان.

src/scripts/lead-form-handler.js
P1 · اتساق العلامة

البريد التجاري الظاهر ليس موحدًا

صفحة Contact تعرض بريد Gmail شخصيًا في موضع جهة التواصل، في حين تستخدم نماذج الموقع info@brightai.live. هذا لا يثبت تعطلًا، لكنه يضعف الانطباع المؤسسي ويربك المتابعة.

المطلوب: بريد عمل رسمي واحد ومعرّف هوية جهة التواصل ومسار رد مناسب.

src/pages/contact/index.astro
P1 · تحقق مطلوب

ترويسات الأمان وطرق نشرها

وجود تعليمات ترويسات في public/_headers أو تكوين Static لا يضمن تطبيقها تلقائيًا على Render Node Web Service. كما أظهر المتصفح تحذيرًا أن X-Frame-Options لا يُطبق من عنصر meta، بل من HTTP header.

المطلوب: فحص استجابة HTTP الفعلية لترويسات CSP وHSTS وX-Frame-Options وغيرها، ثم مطابقتها مع middleware.ts وقواعد CDN الفعلية. لا نجزم بغيابها جميعًا من التحذير وحده.

P2 · توثيق

تعليمات README لا تطابق الواقع التشغيلي بالكامل

ملف README يتضمن تعليمات Render Static ومعرف قياس قديم، بينما بنية التشغيل الحالية تحتوي Render Node SSR واسم معرف GA4 مختلف في src/data/site.ts.

المطلوب: مزامنة تعليمات التشغيل وأدلة القياس لتقليل أخطاء التسليم. لا يعني ذلك وجود معرفي GA4 نشطين في الموقع الحقيقي.

تقرير UX/UI: المشاكل المرئية وتجربة الجوال

المشكلة المركزية في أول شاشة هي كثرة العناصر المتنافسة على انتباه الزائر، وليس ضعف جودة الألوان.

نقاط قوة قائمة

ما يجب المحافظة عليه

  • لوحة ألوان كحلي داكن مع تركوازي مناسبة لمنتج مؤسسي.
  • تباين جيد للنص الأساسي والعناصر التي قِيست.
  • دعم RTL واضح في الواجهة.
  • عدم ظهور تمرير أفقي على المقاس المختبر.
  • أزرار لمس كبيرة نسبيًا في مكونات رئيسية.
  • وجود Product Preview بدل الاقتصار على كلام تسويقي.
نقاط ضعف مؤثرة

ما يجب تغييره

  • اختصار النص عبر إخفاء الأسطر بدل تحرير المحتوى.
  • تعدد CTAs: واتساب وحجز واستكشاف وتجربة Kernel، فضلًا عن أزرار داخل العرض.
  • تكدس الشارة المتحركة والشعار الكبير والعنوان والنص والشعارات.
  • ظهور 10 مزايا بجوار Hero أو قربه يقلل التركيز.
  • شريط الكوكيز يحجب مساحة كبيرة في أول زيارة.
  • شعارات ثقة صغيرة/داكنة وتفاصيلها لا تظهر بسهولة على اللمس.
مشكلة مؤكدة

إخفاء الفقرة في 3 أسطر على الجوال

الملف SplitHero.astro يحدد -webkit-line-clamp: 3 ثم overflow: hidden لنص المقدمة. النص لم يُختصر تحريريًا؛ تم قصّه بصريًا.

.split-hero__lead {
  display: -webkit-box;
  -webkit-line-clamp: 3;
  -webkit-box-orient: vertical;
  overflow: hidden;
}

التصحيح: أعِد صياغة فقرة لا تتجاوز تقريبًا 30–45 كلمة، ودعها تظهر كاملة دون حد أسطر. اجعل ارتفاع العنصر مرنًا، ولا تخفِ محتوى يشرح قيمة المنتج لمجرد ضمان ظهور زر داخل أول شاشة.

مشكلة مرصودة

Cookie Consent يأخذ نحو 22% من ارتفاع شاشة الجوال المختبرة

المكون CookieConsent.astro يظهر أسفل الشاشة بشكل ثابت، ويغطي جزءًا من Hero أو الأزرار.

التصحيح: تقليل النص الظاهر مع إبقاء المعلومات الأساسية، اعتماد ارتفاع مرن وحد أقصى مع إتاحة التمرير للمحتوى الداخلي عند الحاجة، أزرار متساوية الوضوح لـ«قبول» و«رفض»، مراعاة Safe Area، والتحقق بصريًا من iPhone الصغير وتكبير النص.

تشتت القرار

غياب إجراء رئيسي واحد واضح في Hero

داخل SplitHero.astro توجد أربعة روابط CTAs مباشرة، إضافة إلى روابط التفاعل داخل لوحة Kernel. هذا ليس خطأ وظيفيًا بحد ذاته، لكنه يزيد القرار المعرفي.

التصحيح: زر أساسي واحد «احجز عرضًا توضيحيًا» وزر ثانوي «استكشف المنصة». ويمكن الاحتفاظ بواتساب في الهيدر أو قرب نموذج التواصل بوزن بصري أقل.
